# Agent Note: SSH Tunnel Reconnect Resilience Uses a Persistent Supervisor, a Round-Trip Probe, a Desired-Running Watchdog and a Wake/Window Retry Poke

Status: implemented

English | [中文](2026-09-30-ssh-tunnel-reconnect-resilience.zh.md)

## Problem

The previous SSH tunnel runtime was one-shot: a connected forwarding thread ended when its link dropped and the startup path surfaced the error without continuing supervision, so a transient outage, a half-open link or a system sleep left the tunnel down until the user reconnected it by hand. The keepalive-only health check returned success on a blackholed link, wake and window display did not interrupt an in-progress wait, and a runtime thread that ended unexpectedly was never restarted. Automatic recovery therefore had to keep retrying retryable failures, tell a dead transport from an unreachable forward target, start a tunnel again only while the user still wants it running and no supervision exists, and stop retrying failures only a user can fix — all without changing the persisted format, any command signature or any event contract.

## Decision

- `spawn_runtime_thread` runs every local, remote and dynamic runtime under the persistent supervisor in `forwarding_runtime/supervisor.rs`. Each runtime returns a `RuntimeOutcome` (`Stopped`, `FailedAtStartup { kind, message }`, `DroppedAfterConnected { kind, message }`) with a `FailureKind` (`Transport`, `Auth`, `HostKey`, `Config`, `Port`, `Target`); `is_retryable` treats transport, port and target as retryable and auth, host key and config as terminal. Every outcome other than `Stopped` persists `last_error`, records one deduplicated `auto-connect` (`FailedAtStartup`) or `auto-reconnect` (`DroppedAfterConnected`) message with dedupe key `ssh-tunnels:{category}:{id}` and emits `ssh-tunnels-updated`; a terminal kind or a disabled `auto_reconnect` clears the desired flag and stops in `error`; on a continuing retry, `DroppedAfterConnected` rewinds the attempt counter so the next delay starts over.
- `next_retry_delay(attempt, jitter_fraction)` computes `base = min(RECONNECT_INITIAL_BACKOFF * 2^attempt, SUPERVISOR_RETRY_MAX_BASE_DELAY)` with `RECONNECT_INITIAL_BACKOFF` at 2 seconds and `SUPERVISOR_RETRY_MAX_BASE_DELAY` at 48 seconds, and returns `base * (1 + jitter_fraction)`; production passes `rand::random::<f64>() * SUPERVISOR_RETRY_JITTER_RATIO` with the ratio fixed at 0.25, so a retry starts at 2 seconds, carries 0–25% jitter and never exceeds 60 seconds. The supervisor sets `reconnecting` before each attempt's backoff sleep.
- `session_probe.rs` implements a two-step round-trip probe bounded by `PROBE_TIMEOUT` (5 seconds): step one opens and closes an SSH session channel and must receive the server answer; step two runs only after step one succeeded, so its failure is classified `Target`. `apply_probe_outcome` drops the runtime after two consecutive transport failures, records a target failure only as the runtime `last_error` without touching the counter, and clears a recorded error on the next success. Local and dynamic runtimes probe every `PROBE_INTERVAL` (10 seconds) through the pooled session — local opens a `direct-tcpip` channel to the forwarding target and dynamic runs a temporary SOCKS round trip when a probe target is configured — while the remote runtime probes the forwarding session from its accept tick and classifies the accept error by `io::ErrorKind` (`TimedOut` and `WouldBlock` are the periodic tick) instead of matching the "timed out" message text.
- The process-memory desired-running set (`DESIRED_TUNNEL_IDS` with mark, clear and snapshot helpers) records what the user wants running: every connect path marks the tunnel desired and every stop path — manual, group and all-tunnel disconnect, delete and upsert — clears it. A per-id start claim is checked and inserted while holding the runtime-manager lock first and the claims lock second, an in-flight instance is inserted into the manager before the first startup result is awaited so it is visible as `connecting`, and `start_tunnel_watchdog` scans every `TUNNEL_WATCHDOG_INTERVAL` (30 seconds) to restart only a desired id that has no instance and no claim, re-checking both under the lock immediately before spawning. Every exit that does not continue retrying clears the desired flag, so the watchdog and the pokes never resurrect a stopped or terminal tunnel.
- The retry-poke epoch is bumped by the sleep-gap heartbeat, the macOS wake observer and the new cheap `ssh_tunnels_poke` window-show poke called from `show_main_window`. The supervisor backoff sleep (`sleep_respecting_stop_and_poke`) returns early on a poke and the remote probe tick probes immediately on a poke (`probe_tick_due`), so wake and window display interrupt the wait instead of leaving it to run out. `mark_system_resume` still feeds the gateway resume grace unchanged, and the `ssh-tunnel-window-reconnect-start` / `ssh-tunnel-window-reconnect-done` events, the synchronous window-show reconnect and their constants are deleted while the existing frontend listeners stay inert.

## Alternatives considered

- Classify probe failures by matching error-message strings: declined because message text varies by provider and locale; classification now uses the typed `FailureKind` returned by the two-step helper and `io::ErrorKind` on the remote accept path.
- Keep the sleep/wake full reconcile in `reconnect.rs`: declined because reconciling every tunnel at wake duplicates the supervisor's own retry loop and can race a live restart, while the poke epoch interrupts only the waits that are already running.
- Probe on every client connection: declined because it adds a round trip to every bridged connection and would misattribute a client's own target failure to the tunnel; probes stay on the fixed 10-second interval.
- Persist the desired-running set: declined because it would add a persisted field, a migration and lifecycle rules over `state.enc.json`; the set is process memory only and after a restart `auto_connect` alone decides what starts.

## Consequences

- Recovery is continuous: a retryable failure of the first attempt enters the same supervised retry loop, retries continue with bounded jittered backoff until one attempt succeeds, and only a user stop, a terminal classification (auth, host key, config) or a disabled `auto_reconnect` ends supervision in `error` with one deduplicated message. A successful connection resets the attempt counter, so the next drop retries from 2 seconds.
- A half-open link is detected by the second consecutive transport probe failure and reconnects; an unreachable forward target only records `last_error` on a still-connected tunnel and the error is cleared once the target answers again, with no reconnect in either direction. Remote mode no longer depends on matching an error message.
- Supervision stays unique: an in-flight connect is visible as `connecting` before its startup result arrives, a watchdog restart and a manual connect for one id yield exactly one instance, and a manually disconnected tunnel is never restarted by the watchdog, the wake poke or the window poke.
- Everything added is process memory only: the desired set, start claims, retry attempts and the poke epoch are never persisted, so after an application restart only `auto_connect` decides what starts; `state.enc.json`, the `SshTunnelStatus` values, the command names and argument shapes and the `ssh-tunnels-updated` event are unchanged, and rollback restores the previous behavior without invalidating saved tunnels.
- Honest scope deviation: the poke-aware probe tick is wired for the remote accept path only, because `local_dynamic.rs` and `session_probe.rs` were outside task-003's frozen write scope; local and dynamic wake probes therefore remain bounded by the 10-second `PROBE_INTERVAL` instead of probing immediately on a poke.
- Supersession assessment: no supersession of [Gateway Auto-Disable Recovery Uses a Cooldown Half-Open Probe, a Post-Resume Transport Grace and a Transition Broadcast](../architecture/2026-09-23-gateway-auto-disable-recovery.md), whose resume-signal facts stand because `mark_system_resume` still runs at the sleep-gap heartbeat and the macOS wake observer and keeps feeding the gateway grace unchanged; no supersession of [Tray menu ownership and contract](../architecture/2026-09-22-tray-menu-ownership-and-contract.md), whose `ssh_tunnels_connect_all` / `ssh_tunnels_disconnect_all` batch behavior, batch identity and result contract are unchanged. `MEMORY.md` and the `ssh-tunnels-backend` entry in `.ai-workflow/index/navigation.json` carry the supervision standards in the same change, and `navigation.md` was regenerated from the authoritative JSON.
