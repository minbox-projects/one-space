# Agent Note: BLE Lock Retries a Failed Connection and Opens the Device Chooser Only for Explicit User Discovery

Status: implemented

English | [中文](2026-10-12-ble-lock-reconnect-and-device-discovery.zh.md)

## Problem

After the [BLE Lock Tool Automates Mac Session Actions for One Bluetooth Device](../feature/2026-10-10-ble-lock-tool.md) shipped, two "device returns" defects remained. On the backend, the runtime retried the connection only from the `Disconnected` callback, so a quick connection failure inside the 5000 ms retry window was discarded with no periodic-tick retry and the connection could stay down even after the device returned; a manual rescan without reselecting the device was the only way to restore it. On the frontend, the device chooser's visible scan state was read from the native monitor's `status.scanning`, which is also true for passive advertisement monitoring, and a background device event could open the chooser on its own; dismissing the chooser with the footer button, the dialog close control or Escape could therefore leave user discovery running or misreport it.

## Decision

- Backend retry: `state.rs` adds `RECONNECT_RETRY_INTERVAL_MS = 5_000` and `last_connect_retry_ms`. `BleLockMonitor::tick` emits `BleLockEffect::Connect` when the selection is active, the radio state is `PoweredOn` and the last error is `device_unavailable`, throttled to at most one retry every 5000 ms (with the first retry when none has been recorded). The retry never resets presence history, timers or manual-lock eligibility, and `reset_history` clears the retry timestamp, so a quick failure cannot busy-loop and a later tick past the window retries again without a new scan or reselection.
- Backend dispatch and bridge: `native.rs` collects the emitted `Connect` into `retry_connect`, releases the runtime lock and reuses the background-aware `hardware_plan` through `dispatch_sync_central`, so the main-thread dispatch happens outside the runtime lock; the `Disconnected` callback only records `device_unavailable` and the periodic tick owns the retry. In `central.rs`, `select` compares the requested id with the current selection, so re-applying the same UUID does not cancel an in-flight request (a CoreBluetooth pending connect has no timeout) while a replacement still cancels; `connect_selected` issues `connectPeripheral:` only when the peripheral state is `Disconnected`, retaining pending `Connecting` and established states, and `request_rssi` calls `readRSSI` only on a `Connected` peripheral.
- Radio-state sync after a monitor rebuild: `dispatch_sync_central` reads the retained manager's real `central.state()` once and calls `guard.monitor.set_bluetooth_state(state)` before it applies the mode and connection, so a same device and mode save that rebuilds the monitor as `Unknown` cannot leave the powered-on retry guard disabled forever.
- Recovery: a valid selected active `ConnectionRead` clears only a `device_unavailable` last error; unrelated stable errors survive the recovery reading.
- Frontend user discovery: `BleLockTool.tsx` adds a local `userScanning` flag separate from the native `status.scanning`. The chooser opens only from an explicit user scan/find/change action, which sets `userScanning`, opens the dialog and calls `bleLockScanStart`; the `ble-lock-devices-updated` event only refreshes the device list and never opens the chooser. The footer close button, the dialog close control, Escape and a successful selection all end user discovery through the existing `bleLockScanStop`, and a delayed `bleLockScanStart` settlement after the chooser closes does not reopen the chooser or revive the `userScanning` indicator, though its status snapshot is still consumed. Passive background monitoring keeps its own scan per configuration and is not governed by `userScanning`.
- No new public contract: the commands, events, `BleLockStatus`, `BleLockConfig` and the fixed error code set are unchanged.

## Alternatives considered

- Relying on a manual rescan without reselecting to restore the connection. Declined because the persisted selection must recover on its own when the device returns; the manual rescan was the defect, not the intended workflow.
- Cancelling and restarting the pending connection on every monitoring tick. Declined because a CoreBluetooth pending connect has no timeout, so cancelling abandons the in-flight request and a periodic cancel/restart can interrupt a connection that was about to complete; a legitimate clear, passive-mode switch, replacement or shutdown still cancels.
- Deriving the chooser visibility and the user-discovery lifecycle from the total hardware scan flag or from device events. Declined because the native monitor already reports `status.scanning` for passive advertisement monitoring and streams device events continuously, so the chooser would open without user intent; an explicit `userScanning` intent is required.

## Consequences

- A selected active device whose transport reported it unavailable now recovers automatically: the monitor retries the connection at most once every five seconds while the radio is on, a quick failure cannot stop the retry, and a returning device's valid connected reading clears the transient `device_unavailable` error without disturbing unrelated errors.
- The user's selection and monitored presence survive the outage without a reselect, and manual-lock eligibility is untouched by the retries.
- A monitor rebuilt by a same device and mode save is immediately given the retained manager's real radio state, so the powered-on retry guard resumes as soon as the radio is on instead of staying disabled after an `Unknown` rebuild.
- The chooser opens only for explicit user discovery; background device updates refresh the list without opening it, and the footer button, the dialog close control, Escape and selection all stop user discovery exactly once through `bleLockScanStop` while passive monitoring continues unchanged.
- No public contract changed: no command, event, status field, configuration field or error code was added, renamed or removed.
