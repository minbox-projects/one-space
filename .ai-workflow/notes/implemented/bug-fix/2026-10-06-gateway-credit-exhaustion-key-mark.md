# Agent Note: Gateway Credit-Exhaustion Responses Mark the Attempted Key as Quota

Status: implemented

English | [中文](2026-10-06-gateway-credit-exhaustion-key-mark.zh.md)

## Problem

The key-pool classification only upgraded a quota-message 429 into a key-scoped quota failure: `selection::classify_failure_with_message` returned `FailureClass::Retryable` and `runtime_http::key_failure_kind` returned `Some(KeyFailureKind::Quota)` only for HTTP 429 whose sanitized text matched `selection::is_quota_exceeded_message`. CommandCode's current credit-exhaustion answer is HTTP 400 with `insufficient credits` text, and a 402 credit response follows the same shape, so both were classified as ordinary client errors: the attempted key received no runtime mark, the exhausted key stayed in selection for later requests, and the upstream error was returned to the client even though another key or candidate could still serve the request.

## Decision

A sanitized quota-message classifier hit (`selection::is_quota_exceeded_message`) on HTTP 400, 402 or 429 is now a key-scoped quota failure. `selection::classify_failure_with_message` returns `FailureClass::Retryable` for those three statuses instead of `ReturnToClient`, and `runtime_http::key_failure_kind` returns `Some(KeyFailureKind::Quota)` for the same statuses. The attempted enabled key is marked `quota` through the existing runtime fields (`auto_marked`, `failure_kind`, `marked_at`, sanitized `reason`), the mark is persisted, and the same request immediately continues on the next unattempted usable key or candidate without a backoff wait, without consuming the per-request retry budget and without registering mapping-row health. A request never returns such an upstream response to the client while another candidate can serve it.

The status is the only new part of the decision. HTTP 400 or 402 without a quota-message classifier hit keeps `FailureClass::ReturnToClient` with no key mark; 401 and credential-text 403 stay `authentication`; a bare rate-limit 429 without quota text still rotates within the pass without persisting any mark; network errors, 5xx, 404 and other 4xx keep their previous behavior; and a streaming failure after the first forwarded byte keeps the truncation path and marks nothing. Because the classifier is keyword-based and shared with the established 429 handling, a 400 whose text contains a quota keyword but is not account exhaustion (for example `insufficient permissions`) also follows the key-mark path; this accepted breadth is bounded by the untouched recovery paths below.

Recovery is unchanged. A quota mark produced by this signal recovers only through `KEY_QUOTA_MARK_TTL_SECS = 1800` normal list-order selection (clear-on-selection, re-mark when still exhausted), the single `KEY_PROBE_COOLDOWN_SECS = 60` half-open probe when no usable key remains, or `ai_gateway_reenable_provider_key`. No TTL, probe, background traffic or manual path was added, and the `enabled` flag, mapping rows, provider state, prices, terminal sync and the usage-database schema are untouched.

## Alternatives considered

- Auto-disable the mapping row or the provider on a credit-exhaustion response: declined because the condition belongs to the account credential, not the model; another key of the same provider can still serve, and the existing key runtime mark already carries TTL, probe and manual recovery without taking other models or keys out of service.
- Trigger the mark from the CommandCode quota snapshot instead of the forwarding response: declined because the quota query is provider-specific, read-only and non-authoritative (an undocumented endpoint with a five-minute cache that is not cached on failure); forwarding must react to the actual upstream response and stay status-plus-text based.
- Use a longer or manual-only TTL for credit marks: declined because the existing 1800-second TTL and all-marked probe already bound recovery, and a longer or manual-only window would keep a recovered account out of service or add operator toil with no new evidence.
- Add provider-specific or host-specific rules: declined because classification stays status plus sanitized error text, as authentication classification already does; host rules would not cover every upstream and would duplicate the shared classifier.

## Consequences

- A credit-exhaustion response on HTTP 400/402/429 is a key-scoped quota failure: the attempted key is marked and persisted, the request rotates immediately to the next usable key or candidate, and the upstream error is never returned while a candidate can serve.
- Every other judgment boundary is unchanged: a non-quota 400/402 stays return-to-client with no mark, 401 and credential-text 403 stay authentication, a bare 429 rotates within the pass without persisting, network/5xx/404/other 4xx keep their class, and streaming keeps its first-byte boundary.
- Recovery is untouched: the 1800-second TTL re-selection, the single 60-second probe and `ai_gateway_reenable_provider_key` are the only paths, and a mark changes no `enabled` flag, mapping row, provider state, price, terminal sync or usage schema.
- The visible surface is the existing provider-card marked-key block with the existing `quota` state label, marking time, sanitized reason and re-enable control; no frontend type, component or i18n key changed.
- Verification: the behavior suites in `src-tauri/src/ai_gateway/tests.rs` cover the quota-400 mark-and-fall-back, the two-key rotation, the all-marked skip and its `no usable upstream key (1 quota exhausted)` summary, the non-quota 400 counterexample, the 400/402/429 classification matrix with and without a matching message and the keyword-breadth case, and the unchanged TTL, probe and manual-re-enable regression suites; `cargo test --manifest-path src-tauri/Cargo.toml --lib ai_gateway` exited 0 with 602 tests passed and the frontend AI-gateway regressions passed with 505 tests.
