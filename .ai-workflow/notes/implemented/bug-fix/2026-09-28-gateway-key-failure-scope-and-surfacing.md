# Agent Note: Gateway Key Authentication Marks Are Credential-Scoped and Surfaced per Provider

Status: implemented

English | [中文](2026-09-28-gateway-key-failure-scope-and-surfacing.zh.md)

## Problem

On 2026-09-28, two 403 responses whose bodies never named a credential problem marked healthy upstream keys as authentication-failed: at 12:53 a `MODEL_NOT_IN_PLAN: GPT-6 Sol available in Pro and above plans or extra on demand usage` rejection, and at 14:12 a Cloudflare `error code: 1010` rejection. A marked key is excluded from its pool, so both incidents drained usable credentials, and the incident produced 101 recorded 502s for requests the same keys could still have served. The operator could not see or repair the damage either: the no-usable-key 502 and the synthetic terminal log row said only `no usable upstream key` without counts, a no-candidate request's synthetic terminal row stored an empty error message, an open AI Gateway view kept stale key state because key runtime marks emitted no config-update event, no message or toast announced an authentication failure, and a provider card showed only a key count with no way to see or re-enable the marked keys.

## Decision

`selection::is_authentication_error_message` gates 403 key marking on explicit credential signals matched case-insensitively — `invalid api key`, `api key not valid`, `incorrect api key`, `invalid key`, `unauthorized`, `unauthenticated`, `authentication`, `auth failed`, `invalid token`, `token expired`, `invalid credentials` and `invalid authorization` — and absent or empty text is never a signal. `runtime_http::key_failure_kind` marks a 401 as authentication always, a quota-classified 429 as quota, and a 403 only when that predicate fires. `selection::classify_failure` still maps 401/403 to `DisableImmediately`, so a non-credential 403 never marks, rotates, disables or removes a key: it auto-disables only the resolved mapping row immediately with the `HTTP 403` reason, and the provider's sibling models keep being served with the same keys. Credential 401/403 keep the existing key-scoped behavior.

Both no-usable-key reasons became a per-provider `excluded_key_summary`: excluded keys are counted in the fixed order authentication failed, quota exhausted, user disabled, listing only non-zero categories, for example `no usable upstream key (1 authentication failed, 1 quota exhausted)`; `enabled = false` counts as user disabled even when a stale runtime mark exists; when no candidate provider has any enabled key the reason is `no usable upstream key (no enabled key)`. The full 502 message appends `re-enable authentication-failed keys manually in the AI Gateway` only when a reported provider excludes an authentication-failed key. `ForwardCapture` now carries the 502 message and `synthetic_terminal_row` records it, so the no-candidate path and the no-completed-attempt path — non-streaming and streaming alike — write a non-empty terminal `error_message` instead of an empty one.

`ai_gateway.rs` declares `AI_GATEWAY_KEY_AUTH_FAILED_EVENT = "ai-gateway-key-auth-failed"` with the snake_case `GatewayKeyAuthFailedPayload` (provider_id, provider_name, key_id, key_name, reason, marked_at). `persist_key_runtime_state` compares the persisted key before and after the mutation and emits the existing `ai-gateway-config-update` event exactly when the persisted state actually changed — marks, TTL clears and key probe re-arms across the non-streaming and streaming paths — while a mutation that changes nothing emits nothing. A transition from a non-authentication kind into the authentication mark centrally emits the notification event and builds exactly one message-center input: source `ai_gateway`, category `key_auth_failed`, severity warning, localized title `AI 网关密钥鉴权失败` / `AI Gateway key authentication failed`, a localized summary naming the provider, the key and the sanitized reason, the provider-scoped dedupe key `ai_gateway_key_auth_failed:<provider_id>` and target tab `ai-gateway` with the provider id as entity id; repeated transitions inside the existing dedupe window increment the entry's occurrences instead of adding one. Quota marks produce only the config-update event — no notification event, payload or message. No payload, message, log row or toast carries a key value. `messages.rs` gained the runtime-generic `create_message_with_app` and `list_messages_with_app`, which `messages_create`, `messages_list` and `record_message_silent` delegate to, so tests persist and list through a `tauri::test::mock_app()` handle against the isolated application directory.

`src/lib/aiGateway.ts` exports the event literal, the `GatewayKeyAuthFailedEvent` payload type, `AI_GATEWAY_KEY_AUTH_TOAST_WINDOW_MS = 1500` and `providerMarkedKeys` (pool order, only `auto_marked === true`). `AiGateway/index.tsx` subscribes in Tauri only and aggregates per provider: the first event opens a window, same-provider events inside it increment a count and push nothing, window expiry pushes exactly one warning toast naming the provider and the count, a later event opens a new window and pushes a new toast, and timers are cleared on unmount; the toast carries no key value. `UpstreamProviderList.tsx` renders a marked-key block per provider (key name, derived state label, marking time, sanitized reason and a Re-enable button calling the existing single-key re-enable command) while keeping the key-count summary, and `ProviderDetailDialog.tsx` shows the sanitized reason next to the existing state badge and marking time. The new bilingual keys are `aiGatewayProviderMarkedKeys` (en "Marked keys" / zh "已标记密钥"), `aiGatewayProviderKeyReasonLabel` (en "Reason" / zh "原因"), `aiGatewayKeyAuthFailedToastTitle` (en "Key authentication failed" / zh "密钥鉴权失败") and `aiGatewayKeyAuthFailedToastDescription` (en `{{provider}} has {{count}} key(s) failing authentication; re-enable them in the AI Gateway.` / zh `{{provider}} 有 {{count}} 个密钥鉴权失败，请在 AI Gateway 中手动重新启用。`).

Verification: the Rust behavior suites cover the 401/403 classification matrix and rotation, the mapping-scoped non-credential 403, the per-provider diagnostics and hint condition, the recorded terminal messages, the config-update and notification emissions, the provider-scoped message entry with occurrences 2 and the literal pin; the focused Vitest suites cover the marked-key card, the re-enable call, the detail reason and the per-provider toast aggregation, expiry and redaction. `cargo test --manifest-path src-tauri/Cargo.toml` exited 0 with 1075 lib tests passed and 2 pre-existing ignored, `npm test` passed with 1235 tests, `npx tsc -b` and `npm run lint` exited 0. The two truncated-body 403 suites became mapping-scoped because their fixture delivers a content-length-mismatched body, so with no readable credential text the spec requires no key mark, while the 401 truncation case stays key-scoped.

## Alternatives considered

- Keep marking the attempted key on any 401/403 as before: declined because the 2026-09-28 incidents show plan-scope and service-policy 403s (`MODEL_NOT_IN_PLAN`, `error code: 1010`) exhausting healthy key pools and producing 101 recorded 502s; marking must stay gated on an explicit credential signal.
- Treat only the exact phrase `invalid api key` as a credential signal: declined because upstreams phrase credential rejections differently; the conservative signal list covers the observed phrasings while absent, empty or non-credential text still never marks.
- Leave the resolved mapping row enabled on a non-credential 403 and let the client retry: declined because the model genuinely cannot be served while the upstream policy rejects it, so the resolved row leaves service until the operator re-enables it. This is the accepted trade-off: a genuinely key-scoped 403 with no credential text no longer marks the key, so repeated failures disable sibling mapping rows one by one; those rows stay re-enableable with the existing commands, and providers that report credential problems in text still mark keys.
- Emit one message-center entry per key transition or add a new entry for every transition: declined because a provider with several revoked keys would flood the message center; the provider-scoped dedupe key aggregates transitions into one entry with an occurrence count. Per-provider aggregation keeps only the latest key, reason and count in the message, so the provider card lists every marked key to preserve the individual key history.
- Push one toast per event: declined because several keys failing inside one request would stack toasts; the 1500 ms per-provider window pushes exactly one toast carrying the count, and a mark after the window opens a new one.
- Emit the config-update event on every key mutation, including no-ops: declined because a mutation that changes nothing must not rewrite the file or signal a refresh; only a real persisted state change emits.
- Include the key value or the full upstream body in the payload, message or toast: declined because the contract forbids a key value in any event, message, log row or toast; the payload names the provider and key label and carries only the sanitized reason.

## Consequences

- A non-credential 403 leaves the key pool untouched: no key is marked, rotated, disabled or removed, only the resolved mapping row auto-disables immediately with the `HTTP 403` reason, and sibling models of the provider keep serving on the same keys. Credential 401/403 keep the key-scoped rotation, and the quota-classified 429 marking is unchanged.
- The no-usable-key 502 and the terminal log row now name each excluded provider's non-zero key counts in the fixed order and append the manual re-enable hint only when an authentication-failed key is excluded; a provider with no enabled key reports `no enabled key`, and the no-candidate and no-completed-attempt paths record their message instead of an empty error.
- Key runtime state changes surface immediately: a mark, a TTL clear or a key probe re-arm that actually changes persisted state emits the config-update event, a no-op stays silent, and an open AI Gateway view refreshes without a manual reload.
- Authentication transitions notify exactly once per provider inside the dedupe window — one message-center entry and one aggregated toast — while quota marks stay silent; no event, message, log row or toast contains a key value.
- Provider cards list every runtime-marked key with its name, derived state, marking time, sanitized reason and a Re-enable button while keeping the count summary, and the detail editor shows the reason next to the badge and marking time.
- No persisted field, schema version or migration changed: keys already marked authentication-failed before the change stay marked and become visible and re-enableable, and rollback reverts the routing, diagnostics, emissions and interface only while stored configuration and message history stay valid.
