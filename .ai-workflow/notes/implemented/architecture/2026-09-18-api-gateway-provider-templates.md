# Agent Note: API Gateway Provider Templates and Incremental Model Sync

Status: implemented

English | [中文](2026-09-18-api-gateway-provider-templates.zh.md)

## Problem

Building an upstream provider for OpenCode Zen or CommandCode was manual and error-prone: the operator copied dozens of upstream model names, four-tier prices, peak/off-peak windows and reasoning-effort lists out of the official sources into the provider and price forms. Official data drifts, nothing kept the local copy in step, and a wholesale replacement on refresh would re-enable models the user disabled, resurrect models the user deleted and overwrite prices the user edited. The price model could not express weekday-scoped peak/off-peak schedules (for example the CommandCode DeepSeek windows, whose off-peak hours differ between weekdays and weekends), and no provider carried a machine-readable link to the catalog it came from.

## Decision

Provider templates ship as an in-app snapshot. `src-tauri/src/api_gateway/templates.rs` parses `src-tauri/src/api_gateway/provider_templates.json`, embedded with `include_str!`, into `ProviderTemplate` and `ProviderTemplateModel`; `parse_template_snapshot` treats invalid JSON, an empty template id and a duplicate template id as fatal, while model-level problems are non-fatal: a model with an empty identifier or an unknown protocol is dropped, a duplicate `upstream_model` keeps the first entry, and a blank `models_url` normalizes to none. Two templates ship: `opencode-zen` (base URL `https://opencode.ai/zen/v1`, model-list URL `https://opencode.ai/zen/v1/models`) and `commandcode` (base URL `https://api.commandcode.ai/provider/v1`, model-list URL `https://api.commandcode.ai/provider/v1/models`). [Provider Templates Drop Built-in Model Catalogs and Prices](2026-09-19-provider-template-manual-model-sync.md) removed the built-in 103/62-model catalogs with their prices, peak/off-peak windows, reasoning efforts and `snapshot_version`, so the snapshot now declares each template's model-list URL with an empty `models` list, and only models the gateway can serve enter a synced template: an entry whose declared `supported_endpoints` contains neither `/chat/completions` nor `/responses` is dropped, while an entry without endpoint information is kept and inherits the template protocol. `api_gateway_provider_templates` returns the built-in templates in snapshot order, appends persisted custom templates and reports `synced_at`, `source` and `from_snapshot`, where a persisted sync result wins over the snapshot. `api_gateway_sync_provider_template` is now the manual model-list fetch described by the replacement record: it requires a non-blank `models_url` (otherwise an actionable error and no write), fetches that URL with `reqwest` (15-second timeout, no credentials) and replaces the template's model list wholesale with source-wins display name and protocol and a locally owned `enabled` flag. A network failure, a non-2xx response, a non-JSON payload, a missing model array, an entry without an identifier and an empty effective model set are fatal and return an actionable error naming the URL and the reason; new models start enabled and a source that omits a display name or protocol keeps the local value. Parsed template state persists as `GatewayConfig.provider_templates: Vec<ProviderTemplateState>` with `#[serde(default)]`, so an older `api_gateway.json` still deserializes and is upgraded once by the version-gated migration ([Gateway Migration Is Permanent and Version-Gated](2026-09-24-version-gated-gateway-migration.md)).

A sync propagates incrementally and never replaces a derived provider wholesale. `apply_template_sync_with` stages a clone of the configuration, updates every provider whose `template_id` matches, persists the clone once through the existing encrypted `write_config`, and only commits it to memory after persistence succeeds; a failed write leaves the configuration untouched, and several providers derived from the same template each receive the update independently. A field updates only while it still equals the previous template value: the provider `name`, `base_url` and `protocol`, and the mapping `display_name` and `protocol`. The mapping `local_model` is never touched and a sync disables but never enables a mapping: the derived mapping of every model the previous template carried and the new list removed is disabled while the row is kept, so a model the user disabled is not re-enabled and a retired model stops serving. A manual provider has no `template_id`, so every field and mapping stays field-for-field unchanged after any sync. An enabled new template model is added as an enabled mapping unless its name is in the provider's `ignored_models`, and a template-disabled model is never added; because templates carry no price data, a sync never creates or modifies a price row. Deleting a model on a template-bound provider removes its mapping, records the upstream model in `ignored_models` exactly once and removes its provider-scoped price row, so a later sync cannot resurrect it; on a manual provider deletion removes the mapping and that model's price row and writes no ignored record. Restoring an ignored model rebuilds only the mapping from the template's current data, leaves the ignored set and reports an actionable error when the template no longer carries the model. A model the official source retired keeps its mapping on every derived provider and is marked deprecated by `isMappingDeprecated` in the UI; the sync disables that mapping, so it leaves the forwarding candidates, `GET /v1/models` and the aggregated view under the existing enabled-flag rules until the operator explicitly re-enables it. [Gateway Template Model Retirement](2026-09-20-gateway-template-model-retirement.md) records this rule.

A provider created from a template is bound to it. `api_gateway_create_provider_from_template(template_id, name, base_url, protocol, api_key)` rejects a blank API key before anything is staged, falls back to the template name and base URL when they are blank, and always takes the protocol argument. The new provider carries `template_id`, leaves `default_model` empty, and receives one enabled mapping per enabled template model (`local_model` equals `upstream_model`, the official display name when present, the model protocol or the template protocol) with no price row. `api_gateway_delete_provider_model` and `api_gateway_restore_provider_model` implement the deletion and ignored-set lifecycle above; on a manual provider, deletion only removes the mapping and its provider-scoped price row and writes no ignored record. Five commands land in total: `api_gateway_provider_templates`, `api_gateway_sync_provider_template`, `api_gateway_create_provider_from_template`, `api_gateway_delete_provider_model` and `api_gateway_restore_provider_model`.

Peak/off-peak windows can be scoped to weekdays. `OffPeakPrice` gains `days: Option<Vec<u8>>`, an optional UTC+8 weekday set where `0` is Sunday and `6` is Saturday; absent or empty means every day, and the set is normalized on read and write (out-of-range values dropped, duplicates removed, ascending order) and serialized normalized. `is_off_peak_with_days` keeps the existing `[start, end)`, overnight (`start_time > end_time`) and zero-duration semantics and additionally requires the request's UTC+8 weekday to be in the set, `compute_cost_at_time` prices by the first matching window. The legacy single `off_peak` value no longer exists: the version-gated migration folds it into `off_peaks` before it could be read ([Gateway Migration Is Permanent and Version-Gated](2026-09-24-version-gated-gateway-migration.md)), and an older configuration is upgraded once and produces identical results. [Provider Templates Drop Built-in Model Catalogs and Prices](2026-09-19-provider-template-manual-model-sync.md) removed the snapshot's curated CommandCode peak/off-peak data, so no template ships windows and the field is maintained by hand on provider-scoped price rows. The frontend edits and displays the set through `MappingPriceEditor` and the `formatOffPeakDays` and `normalizeReasoningEfforts` helpers in `src/lib/apiGateway.ts`.

The feature keeps the existing vocabulary. It is named 「服务商模板」 in Chinese, "Provider Template" as the English concept and "Provider Templates" as the section title, while 「上游服务商 / Upstream providers」 stays the name of a configured forwarding target; no backend type, navigation id or configuration field was renamed. The template area renders through `ProviderTemplateSection` and `TemplateCreateDialog`, and the mapping reasoning efforts of a template-bound provider are shown and edited in `ProviderDetailDialog` and are written into the opencode terminal-sync model entry as `variants` (see [Gateway Reasoning Efforts Sync to OpenCode Model Variants](2026-09-20-gateway-reasoning-efforts-in-terminal-sync.md)).

## Alternatives considered

- Name the feature 预设服务商 / Provider Presets or 模型目录 / Model Catalog: declined because the app already uses presets for pre-filled AI Environment providers and a catalog misstates what the template now is — an endpoint definition with an optional model-list URL that binds derived providers and directly creates one, while prices, peak/off-peak windows and reasoning efforts live on provider mappings.
- Rename 「上游服务商 / Upstream providers」 to a generic 服务商 and reserve 服务商模板 for the catalog: declined because the existing navigation, backend types and documentation all use the upstream-provider vocabulary, and the rename would break it with no benefit.
- Replace derived providers wholesale on sync (snapshot wins, no incremental rule): declined because it would re-enable disabled models, resurrect deleted models and overwrite hand-edited prices, contradicting the user-intent-first requirement.
- Delete a model without recording it in an ignored set: declined because the next sync would silently resurrect it, and the user would have to delete it again after every sync.
- Auto-disable or auto-delete models the official source retired: declined because official absence is not the user's decision; the mapping is kept and marked deprecated. [Gateway Template Model Retirement](2026-09-20-gateway-template-model-retirement.md) later adopted the disable half — a template sync now disables the derived mapping of a removed model while keeping the row — so auto-delete remains declined and an explicitly re-enabled mapping is not disabled again.
- Sync automatically in the background or on a schedule: declined because this feature's sync is an explicit user action and automatic writes would change local configuration without consent. [Provider Templates Refresh Automatically on a Persisted Interval](../feature/2026-09-23-template-auto-refresh.md) later adopted this alternative — URL-backed templates now refresh on a persisted interval while the app runs, reusing the unchanged manual sync path — so an explicit click is no longer the only trigger and the incremental merge still preserves user intent.
- Support third-party or user-customized templates and template detach/rebind in v1: declined as v1 scope; only the two built-in templates ship, and the data structure stays extensible for later.
- Fetch CommandCode prices and reasoning efforts from an unofficial scraping path, or omit them while keeping the curated snapshot: declined because there is no public machine-readable source; [Provider Templates Drop Built-in Model Catalogs and Prices](2026-09-19-provider-template-manual-model-sync.md) later removed the curated template price data, so prices, peak/off-peak windows and reasoning efforts are now maintained manually on provider mappings.
- Make `days` mandatory or model weekday scoping as a separate window type: declined because the optional set is additive, keeps the existing serialization and behavior for old configurations, and needs zero migration.

## Consequences

- Template data is available offline until the first sync: the in-app snapshot carries the two built-in templates' metadata and model-list URLs with an empty catalog, the template card shows the model count, the source and the last-sync time, and a sync failure keeps the template's current state rather than clearing it; [Provider Templates Drop Built-in Model Catalogs and Prices](2026-09-19-provider-template-manual-model-sync.md) removed every curated model, price, peak/off-peak and reasoning-effort entry, so the catalog follows its endpoint or the operator's manual edits.
- A sync is manual, per-template and offered only while the template declares a model-list URL: only the syncing template's action is disabled and shows a progress state, fatal source problems return an actionable error naming the URL and the reason and write nothing, and the whole update is persisted once through the encrypted atomic `write_config`; the template-sync stage's write boundary is the template state and the derived providers' fields and mappings, never local keys, `terminal_syncs`, forwarding runtime state, price rows or historical usage records.
- User intent survives every sync: template-disabled models are never added, mapping disabled flags are not re-enabled, deleted models stay in `ignored_models` and are not restored, hand-edited prices, reasoning efforts, display names, provider names, base URLs and protocols keep the user values because the sync writes no price or reasoning data, enabled new models are added, models retired by the official source are kept and marked deprecated while the sync disables their derived mappings, manual providers are field-for-field unchanged, and multiple derived providers of one template receive updates independently.
- A provider created from a template carries the binding, an empty `default_model` and one enabled mapping per enabled template model with no price row; deletion removes the mapping and the provider-scoped price row and records the ignored model on a bound provider, and restore rebuilds the mapping without a price row or reports an actionable error when the template no longer has it; the five commands `api_gateway_provider_templates`, `api_gateway_sync_provider_template`, `api_gateway_create_provider_from_template`, `api_gateway_delete_provider_model` and `api_gateway_restore_provider_model` are exported from `lib.rs` and registered in `app_runtime/run_app.rs`.
- Weekday-scoped pricing is additive: a window without `days` means every day, older configurations are upgraded once by the version-gated migration and keep identical results, the legacy `off_peak` single value is folded into `off_peaks` by that migration, `MappingPriceEditor` displays and edits weekdays (empty means every day), and reasoning efforts are maintained on mappings and written into the opencode terminal-sync model entry as `variants` while templates carry none ([Gateway Reasoning Efforts Sync to OpenCode Model Variants](2026-09-20-gateway-reasoning-efforts-in-terminal-sync.md)); the built-in CommandCode peak/off-peak windows were curated snapshot data and were removed by [Provider Templates Drop Built-in Model Catalogs and Prices](2026-09-19-provider-template-manual-model-sync.md).
- Compatibility and rollback: `provider_templates`, `template_id`, `ignored_models`, `reasoning_efforts` and `days` all have serde defaults, so an older `api_gateway.json` remains readable and is upgraded once by the version-gated migration ([Gateway Migration Is Permanent and Version-Gated](2026-09-24-version-gated-gateway-migration.md)), while an older build ignores the new fields and keeps relaying with its existing mappings and prices; after rollback the old version's next save drops the template state and ignored records while mappings, price rows and usage history are retained, historical amounts are not recomputed, and a new price row carrying `days` is interpreted by the old version as every day, which can only affect peak/off-peak decisions for new requests after rollback and must be recorded in the rollback note; removing the template area entry and the new commands' UI calls stops feature use, and because no type, navigation id or config field was renamed, reverting the naming is a copy-only change with no data migration.
- `MEMORY.md`, `navigation.json` and the regenerated `navigation.md` describe the template shape and model-list URLs, the binding and ignored set, the incremental merge, the weekday price semantics and the five commands in the same change.
- Supersession: `ai-workflow notes list` shows no full or partial supersession of [API Gateway Usage Stats and Request Logs](2026-09-17-ai-gateway-usage-logs.md) or [Gateway Per-Model Mapping Disable Is an Explicit Exclusion](2026-09-18-gateway-per-mapping-disable.md), so both records are retained; the logging, record-time price freeze and retention decisions of the usage record remain in force while its price-entry and global-matching decisions were partially superseded by [Gateway Model Prices Move Into Provider Mappings](2026-09-19-gateway-model-prices-in-provider-mappings.md); the weekday field is additive (absent means every day, old results unchanged), while the mapping-level `enabled` semantics, the provider/mapping independence and the explicit-exclusion rule of the mapping record remain in force — a retirement sync only ever disables the derived mapping of a removed model and never enables one — and deletion/ignored/deprecated is a separate lifecycle; [Provider Templates Drop Built-in Model Catalogs and Prices](2026-09-19-provider-template-manual-model-sync.md) partially supersedes this record by replacing its built-in 103/62-model catalog, its models.dev/CommandCode-specific parsing, its sync price propagation and its create/restore price rows, while the naming, the template binding, the ignored-model lifecycle, the deprecated marking, the incremental untouched-only merge and the weekday price semantics noted above remain in force; [Template Sync Best-Effort Refreshes Previously Synced Terminal Tools](../feature/2026-09-23-template-terminal-resync.md) partially supersedes this record's sync write boundary, which now excludes the delegated terminal-refresh stage: after a successful sync the shared command best-effort refreshes previously synced terminal tools through the existing terminal pipeline, so `terminal_syncs` and tool records can be written by that delegated stage while this record's template-sync-stage boundary and all other decisions remain in force; the remaining active records are unrelated because this change only adds optional fields, a snapshot module and new commands without changing relay, terminal sync, logging, compatibility-cleanup or process decisions. The version-gated cleanup corrects only this record's no-migration claims and its legacy singular `off_peak` path ([Gateway Migration Is Permanent and Version-Gated](2026-09-24-version-gated-gateway-migration.md)); the template decisions here stand.
