# Agent Note: Gateway Per-Model Auto-Disable Settles Health on the Mapping Row

Status: implemented

English | [中文](2026-09-20-gateway-per-model-auto-disable.zh.md)

## Problem

The gateway expressed automatic availability only at provider level: after failures the provider's `auto_disabled` flag took every model of that provider out of candidate selection, `GET /v1/models`, the aggregated views and the terminal-sync model lists at once, and the only recovery path cleared the provider's state as a whole. Upstream providers usually expose several models with independent health, so one failing model silently removed its healthy siblings, and the settled failure was not attributable to a model. The per-mapping `enabled` flag delivered earlier expressed the user's intent to exclude one row, but runtime health had no row-level state to settle on: the operator could neither see which model was failing nor restore only that model.

## Decision

`ModelMapping` gains five serde-defaulted runtime fields — `auto_disabled`, `disabled_reason`, `disabled_at`, `consecutive_failures` and `last_error_at` — next to the user's `enabled`; an older `api_gateway.json` reads every row as healthy. Runtime health is identified by `selection::MappingTarget`, the provider id plus the trimmed `(local_model, upstream_model)` pair, and settles through `register_mapping_failure`, `register_mapping_success`, `clear_mapping_runtime_state` and `mapping_matches_key`. `MappingTarget::for_request` resolves the row a served attempt belongs to and returns `None` when the requested model is blank, matches no row, or the attempt was served through the provider's `default_model`; such an attempt therefore records no health outcome.

Settlement keeps the existing failure classes and counting at row scope. `runtime_http::RequestHealth` still accumulates one outcome per row per inbound request and applies it once when the request ends normally: a 401/403 disables the row immediately, a `FAILURE_THRESHOLD` of 3 consecutive failed requests disables it otherwise, 404/429 and other 4xx alone never count as health failures, and a request the row completes resets its counter and last-error value without touching sibling rows. Since [Gateway Auto-Disable Recovery Uses a Cooldown Half-Open Probe, a Post-Resume Transport Grace and a Transition Broadcast](2026-09-23-gateway-auto-disable-recovery.md), an immediate auth disable no longer increments `consecutive_failures` (it still disables the row and stamps its last error, plus its reason and time on a fresh disable), so the counter keeps meaning consecutive retryable failures. The inbound requested model is carried to every settlement site so a retry attempt's failure is recorded on the row it actually used.

A row with `auto_disabled` is treated exactly like a row with `enabled = false` wherever a mapping is selected or exposed: `selection::resolve_model_for_protocol` skips it, so it never serves as a healthy candidate, never produces a `ProtocolMismatch` and never forwards its `upstream_model`; the one exception is the cooldown half-open probe recorded by [Gateway Auto-Disable Recovery Uses a Cooldown Half-Open Probe, a Post-Resume Transport Grace and a Transition Broadcast](2026-09-23-gateway-auto-disable-recovery.md), which forwards the row's `upstream_model` exactly once after every healthy candidate and bounded retry has failed, or as the only attempt of a zero-candidate request that has an eligible probe; a request whose only matching rows are user-disabled, or auto-disabled without an eligible probe, returns no candidate (`all_providers_unavailable`) instead of falling back to `default_model`; `runtime_http::local_model_names` for `GET /v1/models`, `commands::build_gateway_provider` for terminal sync, and the frontend `aggregateModels` all skip auto-disabled rows. No provider-level runtime field exists in the type — provider selection is `enabled` alone, and a row contributes only while `enabled && !auto_disabled`.

Recovery is row-scoped. `api_gateway_reenable_provider_model(provider_id, local_model, upstream_model)` clears the runtime state of the rows matching the trimmed key, clearing duplicate matching keys together; `api_gateway_reenable_provider_models(provider_id)` clears every auto-disabled row of one provider. Both return the updated config, never change a row's `enabled` intent — a user-disabled row stays disabled — and return an actionable error without writing when the provider or the key matches nothing. The provider-level `api_gateway_reenable_provider` was removed. Since [Gateway Auto-Disable Recovery Uses a Cooldown Half-Open Probe, a Post-Resume Transport Grace and a Transition Broadcast](2026-09-23-gateway-auto-disable-recovery.md), a threshold-disabled row can also return to service without operator action: once its 60-second cooldown elapses and a request cannot be served by any healthy candidate, the cooldown half-open probe attempts it once, and a successful attempt clears its runtime state, while a row disabled immediately by 401/403 stays manual-only.

Provider-level runtime state no longer exists in the type: the version-gated migration clears the legacy provider-level keys once when it rewrites a configuration older than the current schema version ([Gateway Migration Is Permanent and Version-Gated](2026-09-24-version-gated-gateway-migration.md)), and no path can write provider-level runtime state anymore. `api_gateway_upsert_provider` preserves a row's runtime state only while its trimmed `(local_model, upstream_model)` key is unchanged, starts a new or changed key healthy and drops the state of a deleted row with the row it replaces; template creation and template sync write no runtime state, so every mapping they produce starts healthy.

`GatewayStatus.auto_disabled_count` now counts auto-disabled rows instead of providers. `RuntimeStatusCard` counts providers by `enabled` alone and keeps the auto-disabled model count from `status.auto_disabled_count`; the provider card shows a read-only count hint of its auto-disabled rows; `ProviderDetailDialog` marks an auto-disabled row with `data-auto-disabled` (visually distinct from the user-disable `data-disabled`), offers a per-row re-enable action and a provider-level re-enable-all action when the provider has any auto-disabled row. The copy lives in `src/i18n.ts` as `apiGatewayProviderAutoDisabledModelsHint`, `apiGatewayReenableMapping` and `apiGatewayReenableAllMappings` in both languages.

## Alternatives considered

- Keep automatic availability provider-level and take a whole provider offline when one of its models fails: declined because the healthy models of that provider then stop serving, and the settled failure is attributable to one model while the mapping rows already provide the granularity to say so.
- Disable the whole provider when any single row crosses the threshold: declined for the same reason; a provider-wide disable would also hide which model failed and would clear only through the provider-wide recovery path.
- Delete the failing row or turn its `enabled` flag off: declined because runtime health must stay independent of the user's intent, a transient upstream failure must not rewrite an exclusion the user did not ask for, and deletion discards the row's remote model, protocol and display name.
- Keep both the provider-level and the row-level counters as parallel sources of truth: declined because one condition must not have two owners; the provider-level fields were kept only for deserialization compatibility and have since been removed, with the version-gated migration clearing the legacy keys.
- Settle a `default_model` attempt on the provider or on an arbitrary row: declined because such an attempt has no row identity; settling it would disable a row the request never used.
- Keep `api_gateway_reenable_provider` as the only recovery entry: declined because recovery must target the model that failed; the provider-wide helper remains as `api_gateway_reenable_provider_models` only to clear every auto-disabled row of one provider.

## Consequences

- A failing model now disappears alone: after settlement only the auto-disabled row leaves candidate selection, `GET /v1/models`, the aggregated views and the terminal-sync model lists, while the provider's other rows keep serving; the row stays user-enabled and returns to service when its model recovers and either the delayed half-open probe clears its runtime state or the operator clears it per row or for the whole provider.
- `default_model` attempts record no health outcome, so a request served through the unmapped fallback can neither disable a row nor reset one.
- Older configurations are upgraded once by the version-gated migration: every new field is serde-defaulted, the legacy provider-level runtime keys are cleared from the rewritten file, and a reverted build ignores the row fields under best-effort downgrade.
- `auto_disabled_count` changed meaning from providers to rows; the runtime status card, the provider card, the provider dialog and the new copy were updated with it, and the frontend marks an auto-disabled row with `data-auto-disabled` and calls `api_gateway_reenable_provider_model` or `api_gateway_reenable_provider_models`, with the `apiGatewayReenableProvider` wrapper removed.
