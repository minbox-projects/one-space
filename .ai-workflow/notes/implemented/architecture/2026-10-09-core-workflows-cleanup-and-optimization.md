# Agent Note: Core Workflows Cleanup and Optimization

Status: implemented

English | [中文](2026-10-09-core-workflows-cleanup-and-optimization.zh.md)

## Problem

GUI session creation and resume and the `onespace ai` / `onespace resume` CLI entry points had drifted into different implementations. The installed CLI narrowed session names (spaces and dots to underscores), assembled its own launch commands, wrote plaintext session JSON and invented native session IDs, while the GUI used a separate new-terminal adapter. The `resume` branch hardcoded a per-tool resume command in the Shell script and ignored the shared provider and runtime environment. Provider activation and `onespace env use` likewise diverged, and OpenCode's active provider was represented by a single slot rather than its real multi-active set. This record documents the delivered facts of plan `20261009-core-workflows-cleanup-and-optimization`; its current body covers the first two steps, and later steps of that plan are not described here.

## Decision

- Make `src-tauri/src/app_store/session_service.rs` the AppHandle-free canonical session entry point shared by GUI and internal CLI. `create_session<F, T>(SessionInput, launch) -> Result<(ApiOk<SessionRecord>, T), ApiErr>` takes an adapter that returns a discovered real native ID and its own output. `create_session_in_current_terminal(SessionInput, &[String]) -> Result<(ApiOk<SessionRecord>, ExitStatus), ApiErr>` and `create_cli_session(&[String]) -> Result<(ApiOk<SessionRecord>, ExitStatus), ApiErr>` build on it. `create_cli_session` reads its tool, optional display name and native argv from the forwarded arguments, uses the invoking terminal's working directory, and consumes an optional paired `--permission-mode <mode>` so it never becomes the display name or reaches the native tool.
- Add `LaunchOptions::launch_create_in_current_terminal` in `src-tauri/src/ai_sessions/terminal.rs`. It inherits the current terminal's stdin, stdout and stderr, preserves a successfully started child's nonzero exit status, and returns `Err` only when the spawn itself fails.
- A created record keeps the supplied name verbatim, starts as `pending_bind`, and becomes active only when history discovers a real native session ID; a display name never substitutes for that ID. Workspace MCP preparation runs before the pending record is published. A spawn failure removes the record; a started child that later exits nonzero stays.
- Keep one canonical writer for sessions and providers. Concurrent creates are still deduplicated per `(tool, working_dir, runtime_mode, runtime_profile_id, preset_id)` scope through `acquire_session_create_lock`/`release_session_create_lock`. Cross-process serialization comes from `src-tauri/src/app_store/storage_engine.rs`: `CanonicalStateWriteLease` holds a persistent exclusive OS file lock on the profile's `canonical-state.lock` sidecar, the process thread mutex `SESSIONS_STATE_WRITE_LOCK`, and the locked path, while the thread-local `CANONICAL_STATE_WRITE_LEASE` (a `RefCell` `Weak` upgraded to an `Rc` lease) makes nested acquisitions by the same thread reentrant and blocks other threads and processes. Unix takes an exclusive `flock` and retries `EINTR`; Windows takes `LockFile` on one byte of the sidecar and retries `ERROR_LOCK_VIOLATION`. `lock_sessions_state_write` (`types/api_session_types.rs`) and `lock_service_provider_operation` (`service_provider_commands.rs`) both route to `lock_canonical_state_write`, the `providers_storage` loaders, migration and writes join the same gate, and changing profile during a transaction is rejected. `StorageEngine::atomic_write` publishes through a unique `tmp-<pid>-<counter>` file opened with `create_new`, then `write`, `sync_all` and `rename`, and removes the temporary file on failure. Public APIs are unchanged.
- Share the resume entry point too: `resume_session<F, T>(session_id, permission_mode, initial_prompt, launch) -> Result<(ApiOk<SessionRecord>, T), ApiErr>`, `resume_session_in_current_terminal(session_id, permission_mode) -> Result<(ApiOk<SessionRecord>, ExitStatus), ApiErr>` and `resume_cli_session(&[String]) -> Result<(ApiOk<SessionRecord>, ExitStatus), ApiErr>` accept `resume <id> [--permission-mode default|full_access]` and look up the record by `tool_session_id` then canonical `id`. `LaunchOptions::launch_resume_in_current_terminal` reuses `build_resume_command`, merges the provider/runtime/permission environment, inherits the current terminal I/O and preserves a started child's nonzero exit status. `resume_session` resolves a pending/unbound or empty native ID from native history by working directory and time window, refuses with `SESSION_ID_MISSING` when it still cannot, checks `SESSION_ID_CONFLICT` against other records of the same tool, and leaves the record unmodified when the spawn fails.
- Make `src-tauri/src/app_store/provider_activation.rs` the shared AppHandle-free provider entry point. `activate_provider(tool, provider_id)`, `use_cli_environment(tool, target)` and `cli_environment_listing()` back both GUI activation and `onespace env use`/`env list`.
- OpenCode activation appends to the `active_opencode` set (deduplicated, multiple entries allowed), while the other tools keep their single active provider. `onespace env use` still performs no CLI projection, and `env list` reads only `active_opencode`, including an empty set, and never the legacy OpenCode single slot.
- The generated `onespace` script forwards to the backend instead of resolving commands itself. Its `ai` branch `exec`s `"$APP_BIN" __onespace_cli_create_session "$@"` and its `resume` branch `exec`s `"$APP_BIN" __onespace_cli_resume_session "$@"`; the help and usage text documents `--permission-mode default|full_access` for both `ai` and `resume`. Create still resolves the launch command from `config::ai_model_launch_commands` (the Settings -> AI Terminal launch command templates) through `build_create_command`/`configured_create_command`.
- Resolve permission modes in one place: `validate_and_resolve_permission_mode` rejects `full_access` when the tool is configured `default`, requires an explicit choice when the tool is configured `full_access` and otherwise returns `PERMISSION_CONFIRMATION_REQUIRED` without launching or changing state, and runs an explicit `default` unprivileged. The CLI flag is parsed and validated on both create and resume and never weakens the configured boundary.
- Pass the provider profile path exactly as the backend resolves it. The earlier self-created `resolve_path_with_home_spelling` helper was removed, and tests verify the returned config directory's identity with `canonicalize` instead of home-spelling rewriting.
- Consolidate frontend session and service-provider contracts. `src/lib/aiSessions.ts` holds `AiSession`, `AiSessionListItem`, `SessionInput`, `AiModelLaunchCommands`, `AiSessionStorageConfig` and the `getAiSessionStorageConfig`, `sessionsList`, `sessionsCreate`, `sessionsUpdate`, `sessionsLaunch`, `sessionsDelete`, `sessionsSetFavorite`, `checkCliInstalled`, `installCli`, `hideQuickAiWindow` and `resizeQuickAiWindow` wrappers. `src/lib/serviceProviders.ts` carries the provider DTOs, `CliTool`, `getActiveProviderIds` and the `serviceProviders*` command wrappers. `AiSessions`, `AiSessionsList`, `QuickAiSessionBar` and `AiEnvironments` consume those typed wrappers and keep re-exporting existing DTO types for current imports. The New Session provider summary lists every active provider for the selected tool instead of a single slot and shows nothing for an empty OpenCode set.

- Step 2 — Own automatic template refresh in the process: `src-tauri/src/ai_gateway/auto_refresh.rs` owns the schedule for the whole application process. `start_scheduler` is installed exactly once from `app_runtime/run_app.rs` after gateway autostart; install reads the persisted interval, so a positive value arms the schedule and runs exactly one immediate startup batch while `0` installs a parked control that a later `request_rearm` can arm without running a batch. `ai_gateway_template_auto_refresh_save` only re-arms and never runs an immediate batch. One batch runs at a time (a tick arriving during a batch is skipped) and iterates the templates whose trimmed `models_url` is non-empty sequentially in template order. The interval contract is unchanged: `DEFAULT 60`, `MIN 10`, `MAX 1440`.
- Step 2 — Expose per-template failures and share same-template work: per-template failures live in process memory and are set on failure, cleared on success and empty on restart. They are exposed by `ai_gateway_template_auto_refresh_status() -> TemplateAutoRefreshStatus { failures: [{ template_id, reason }] }` and by `AI_GATEWAY_TEMPLATE_AUTO_REFRESH_UPDATED_EVENT = "ai-gateway-template-auto-refresh-updated"`, emitted only when the failure set actually changes; automatic failures never toast. Manual `ai_gateway_sync_provider_template` and the automatic batch share `start_template_op` / `TemplateOpOwner` / `TemplateOpFollower`: an automatic contender skips a busy template while a manual contender awaits and reuses the owner's in-flight result instead of fetching again, and the guard entry is removed only while it still points at the finishing operation.
- Step 2 — Produce the additions-only message in the backend: after a successful sync whose configuration write stood, `templates::template_sync_addition_notices` counts only mappings whose `upstream_model` was absent from the same provider before the sync, and `commands` records exactly one `template_sync` info message per changed template in event-time language. Retirement notices, ignored-model handling, retired-price and default-model cleanup and the best-effort terminal refresh keep their existing order and semantics.
- Step 2 — Tie listener status to task identity and stop cleanly: `RunningServer` carries a monotonic `generation`; `run_server` retires the slot and publishes `running=false` (the existing `ai-gateway-status-update` event) only while the slot still holds the same generation, so a faulted old task can never clear a replacement listener and the same port can restart. `shutdown_runtime_services` idempotently stops the gateway listener and the template schedule and is called from tray quit, `quit_app` and `RunEvent::Exit`.
- Step 2 — Demote the frontend to a read/subscription adapter: `useTemplateAutoRefresh`, mounted in `src/App.tsx`, now performs one `ai_gateway_template_auto_refresh_status` read on mount and one subscription to `ai-gateway-template-auto-refresh-updated`. It keeps no timers, makes no sync calls, has no in-flight registry and builds no messages, and `useTemplateAutoRefreshFailures` keeps its map shape. `src/lib/aiGateway.ts` adds `aiGatewayTemplateAutoRefreshStatus`, the `TemplateAutoRefreshFailure` / `TemplateAutoRefreshStatus` types and the event literal; the AI Gateway manual sync keeps its local spinner and relies on the backend guard and snapshot.

## Alternatives considered

- Keep the Shell script writing plaintext session JSON and only patch names or IDs. Declined because it cannot share canonical registration, writer coordination, pending binding or spawn-failure rollback with the GUI.
- Keep the hardcoded per-tool resume command in the Shell script. Declined because resume would not share native-ID resolution, provider and runtime environment, permission handling or writer coordination with the GUI.
- Route `onespace ai` through the GUI new-terminal adapter. Declined because the CLI runs in the caller's terminal and must inherit its I/O and exit status rather than open a new terminal window.
- Treat a nonzero-exit child as a creation failure and delete the record. Declined because a started process that later exits nonzero is a valid outcome that must be preserved; only a spawn failure invalidates the record.
- Let `--permission-mode full_access` elevate a `default`-configured tool. Declined because any caller could then bypass the configured permission boundary.
- Represent OpenCode activation as a replacement of one active provider. Declined because OpenCode supports several active providers and the GUI and CLI must present the same set.
- Project CLI configuration from `env use` as `Apply to CLI` does. Declined because `env use` is documented as a no-projection binding update and projection stays a separate explicit action.
- Step 2 — Keep the frontend scheduler and add a backend loop only for hidden windows. Declined because two owners would have to reconcile timing, failure state and notifications; one process scheduler removes the duplicate ownership instead of coordinating it.
- Step 2 — Let an automatic contender wait for a busy same-template manual sync. Declined because a timed batch should not block on operator work; the automatic contender skips while the manual contender reuses the in-flight result.

## Consequences

- GUI and `onespace ai` now register, prepare and bind sessions through one canonical path, and a record can stay `pending_bind` until a real native ID is discovered.
- `onespace ai` preserves the supplied name, uses the invoking directory and current terminal, forwards extra arguments verbatim, and returns the child's exit status; `onespace resume` resolves the same canonical record, native ID, working directory, environment and permission mode that the GUI uses.
- Concurrent GUI and separately launched `onespace ai` processes serialize on the profile-scoped `canonical-state.lock`, so an activation or registration completed by one process survives the other's overlapping update. The gate is reentrant per thread and joins nested loaders and saves instead of taking provider or session locks in reverse order.
- Verified evidence: a provider activation regression failed twice with both workers reporting success while one update was lost, and passes after the gate (`concurrent_gui_and_cli_opencode_activation_keep_both_changes`). The corrected `concurrent_independent_registrations_preserve_sessions_and_rollback` uses a fully migrated fixture where two separate workers' native stubs are both launched and held before either releases and a failing spawn rolls back while another live successful native child is still held; the public listing then shows three successful pending records, no failed record and a complete encrypted state.
- Real debug-binary smokes are GREEN: `onespace resume` uses the canonical provider `CLAUDE_CONFIG_DIR` (canonical path identity), the original working directory and the discovered native ID, and refuses a pending/unbound record; the dev profile lifecycle writes only `$HOME/.config/onespace-dev` while the release `$HOME/.config/onespace` sentinel is unchanged, a stub writes a real `$HOME/.claude/history.jsonl`, create binds `native-claude-777` and resume uses that ID; the permission smoke shows a `full_access`-configured tool with no explicit choice refusing `PERMISSION_CONFIRMATION_REQUIRED` without launching or changing state, `--permission-mode default` succeeding unprivileged, `--permission-mode full_access` carrying `--dangerously-skip-permissions`, and a `default`-configured plain run staying unprivileged.
- OpenCode can hold multiple active providers in both GUI and CLI listings; an empty set stays empty instead of falling back to the legacy slot, while the other tools remain single-active.
- Provider and session DTOs and command wrappers now live in `src/lib/`, so touched components call typed wrappers instead of dynamic `any` interpretation.

- Step 2 partial supersession: [Provider Templates Refresh Automatically on a Persisted Interval](../feature/2026-09-23-template-auto-refresh.md), [Template Auto Refresh Runs One Batch at App Start](../bug-fix/2026-09-29-template-autorefresh-startup-batch.md) and [Automatic Template Sync Notifies the Message Center on Real Mapping Changes](../feature/2026-09-24-ai-gateway-template-auto-sync-notification.md) are retained and cross-linked. No note is fully superseded, so none is archived.

Later steps of the plan have not started and are intentionally not described here.
