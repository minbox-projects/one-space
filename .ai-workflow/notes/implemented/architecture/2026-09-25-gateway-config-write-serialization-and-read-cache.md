# Agent Note: Gateway Configuration Writes Serialize on One Lock and Reads Cache by File Identity

Status: implemented

English | [中文](2026-09-25-gateway-config-write-serialization-and-read-cache.zh.md)

## Problem

Every configuration mutation — mapping-health settlement after a request, key mark, re-arm and clear writes, user command saves and template sync — was a whole-file read-modify-write: `read_config` decrypted and parsed all of `ai_gateway.json`, the caller mutated its snapshot, and `write_config` re-encrypted and renamed a replacement over the file. Two concurrent writers could read the same base state, and the later rename silently discarded the earlier writer's change; a settlement that changed nothing still rewrote the encrypted file; and every attempt-time read decrypted the file again. The read-path lazy migration made it worse, because a reader could migrate and rewrite the file while a writer was publishing, clobbering the writer's newer configuration. The fixed temporary path (`path.with_extension("tmp")`) also let two concurrent writers collide on one temp file, and a panic inside a mutation could poison a lock held across the sequence, risking a permanently disabled gateway.

## Decision

`storage::modify_config(mutate)` is the serialized configuration read-modify-write entry point. It takes the process-global `CONFIG_WRITE_LOCK: Mutex<()>`, recovering a poisoned lock through the recovered guard; loads the current configuration from the read cache when it is warm, otherwise through `read_config_locked`, which performs no nested lock acquisition and no nested rewrite; runs the caller's `FnOnce(&mut GatewayConfig) -> Result<(bool, T), String>`; persists only when the closure reports a change or the in-lock file still needed the legacy migration; and returns the closure's value. The closure must stay local and must never wait on the network, so the lock is never held across an upstream wait.

Every production mutation now runs through this primitive: mapping-health settlement (`RequestHealth::apply` and `apply_failure`), key mark and clear writes (`persist_key_runtime_state`, including the TTL clear-on-selection), provider upsert, delete, enable and re-enable commands, local key upsert, delete, default and local-key-mutation commands, the gateway enabled flag, usage retention, template auto refresh, template sync, derived-provider creation and removal, and the terminal-sync ledger write. `ai_gateway_sync_provider_template` fetches the template model list and reads the service-provider payload outside the lock, applies `apply_template_sync_from_body` to the latest configuration inside the lock, and then runs the best-effort terminal refresh after that mutation; the refresh persists its ledger through its own serialized mutation, so no upstream network wait is ever under the lock.

Writes are suppressed when a mutation changes no actual state. `RequestHealth::apply` and `apply_failure` compare a `MappingRuntimeState` snapshot of the affected rows before and after settlement, `persist_key_runtime_state` compares the mutated key with its clone, and `persist_enabled` reports no change when the flag already matches; a no-op mutation still warms the read cache with the fresh parse but leaves the encrypted file byte-identical.

Publication is atomic and collision-free. `write_config_through_temp` canonicalizes, encrypts and writes the payload to a caller-owned temporary file, then renames it over the configuration path; `modify_config` and `write_config` derive that path through `unique_config_temp_path`, which appends the process id and a process-monotonic counter (`CONFIG_TEMP_COUNTER`) to the file name, so no two writes can pick the same temp file. `write_config_through_temp` returns the normalized value that actually landed on disk, and the caller stores that value — not the pre-normalization input — in the read cache. After a successful publication, provider ids that existed before the write and are absent from the published configuration have their scheduler entries pruned by [API Gateway Scheduler Accounts per Provider, Local Model and Protocol and Prunes Deleted Providers](2026-09-25-gateway-scheduler-accounting-scope.md); a failed write prunes nothing.

Reads are served from a process-memory cache keyed by file identity. `CONFIG_READ_CACHE` holds one `CachedConfig` per configuration path — the normalized configuration plus the path, the file's byte length and its modification time — and `read_config_file` returns the cached value while `file_identity` still matches, so a warm read never decrypts. Every in-process write stores the published normalized value under the file's new identity; a direct on-disk rewrite that changes length or modification time invalidates the entry through the identity check alone, with no invalidation helper required; and a missing or empty file drops the entry.

The lazy migration stays atomic and one-shot under the same lock. When `read_config_locked` reports that the stored version is older, `read_config_file` takes `CONFIG_WRITE_LOCK`, re-reads the file and re-checks the version under the lock, and only then stamps the current version and rewrites it through `write_config`; if a concurrent writer already published a current-version configuration, the reader serves that configuration and writes nothing. A failed migration rewrite keeps the previous complete bytes on disk and the next read retries it.

## Alternatives considered

- Keep the whole-file read plus atomic rename per mutation: declined because concurrent writers still lose each other's changes and a no-op settlement still rewrites the encrypted file; serialization must span the entire read-modify-write, not only the rename.
- Lock per provider, per command kind or per field: declined because the persisted unit is one encrypted file rewrite, so any two writers replace the whole file; finer locks would still interleave, while one process-global lock is uncontended at human-edit frequency.
- Synchronize with an OS file lock or a lock file instead of a process-global mutex: declined because the process is the only writer, and a file lock can go stale after a crash while a poisoned in-process mutex is recovered on the next call.
- Invalidate the read cache through explicit helper calls only: declined because a direct on-disk rewrite would leave a stale cache; path plus length plus modification time observes every change, including one made outside the production write path, without an invalidation API.
- Keep the fixed temporary path (`path.with_extension("tmp")`): declined because concurrent writers can collide on one temp file; the process id plus a monotonic counter makes every temp path unique.
- Fail permanently on a poisoned lock: declined because a panicking mutation must not disable the gateway; every lock site recovers through the poisoned guard.
- Hold the lock across the template model fetch to simplify the write: declined because a slow or hanging upstream would block every configuration mutation; the fetch runs outside and only the staged application runs inside.
- Take the migration lock without re-reading and re-checking the version: declined because a concurrent writer may already have published a migrated, stamped configuration; the in-lock re-check keeps the migration one-shot and never overwrites newer content.

## Consequences

- Concurrent configuration writers no longer lose each other's changes: concurrent key marks, a key mark racing a mapping-health settlement, repeated writers and a user edit racing a settlement all leave a complete, readable configuration.
- A settlement that changes nothing leaves the encrypted file byte-identical, and a no-op mutation still leaves the next read decryption-free through the warmed cache; a poisoned lock is recovered and the gateway keeps serving.
- The write lock is never held across an upstream network wait: the template fetch happens before the mutation and the terminal refresh after it, and concurrent mutations complete while a relay request waits on a slow upstream.
- Warm reads never decrypt and any file-identity change makes the next read observe the new content, including a direct on-disk rewrite that calls no invalidation helper; missing and empty files invalidate the entry.
- Every write uses a unique temporary file and an atomic rename, so a partial write can never be published and a failed write keeps the previous complete bytes; the version-gated lazy migration stays atomic and one-shot with its version re-checked under the lock.
- A successful publication stores the normalized value in the read cache and drives the diff-based scheduler prune; a failed write leaves the cache and the scheduler untouched.
