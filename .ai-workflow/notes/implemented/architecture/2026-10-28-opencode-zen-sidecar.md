# Agent Note: OpenCode Zen Free Uses an Isolated BoringSSL Loopback Relay Selected by Provider Template

Status: implemented

English | [中文](2026-10-28-opencode-zen-sidecar.zh.md)

## Problem

The AI Gateway could not serve the `OpenCode Zen Free` provider: direct requests sent with its own TLS stack received HTTP 429 from Zen's free tier for the free models even with valid credentials, so clients connected through the gateway never reached the upstream. Zen's endpoint accepts the client TLS profile that BoringSSL presents but rejects the direct stack the gateway used. The root cause was the base URL: the official OpenCode built-in provider API is `https://opencode.ai/inference/openai/v1`, while the gateway persisted the legacy `https://opencode.ai/zen/v1`, which returned HTTP 429 even with genuine `x-opencode-*` headers and an agent request body; the official CLI against the inference base exited 0.

Moving that client into the main application process was not available. The application links `ssh2` with `vendored-openssl`, while wreq brings its own statically linked BoringSSL; both export OpenSSL-family C symbols, so one binary cannot link both without colliding definitions. The transport also had to be selected from durable configuration rather than from a mutable endpoint string, and existing users needed their provider moved without rewriting credentials, mappings or prices.

## Decision

- Transport is a closed template policy. `TransportStrategy` is `direct` (the default) or `opencode_zen_sidecar`, stored as the template's `transport_strategy`; persisted reads tolerate a missing or unknown value as `direct`, and a new save rejects an invalid value. `effective_transport_strategy` resolves only from the provider's bound and resolvable template, so an unbound provider, an unknown or deleted template id, or any other template stays direct and no URL, name or icon is ever consulted.
- The resolved transport is a runtime cache. Each provider carries a `#[serde(skip)]` transport that `normalize_stored_config` publishes on both the read and write paths, and prepared model-pool candidates refresh it through the same resolver; the value is never persisted. Deleting a template still bound by a provider fails with the provider name and leaves the configuration unchanged.
- A built-in `opencode-zen-free` template declares the Zen inference base URL `https://opencode.ai/inference/openai/v1`, the unchanged model-list URL `https://opencode.ai/zen/v1/models` with an identical `source`, the generic sync strategy, the sidecar transport, the OpenCode icon and eight enabled mappings: `zen-free-big-pickle` → `big-pickle`, `zen-free-beam` → `beam-free`, `zen-free-mimo` → `mimo-v2.6-flash-free`, `zen-free-nemotron-vl` → `nemotron-3.5-super-vl-free`, `zen-free-nemotron-lightning` → `nemotron-3.5-lightning-free`, `zen-free-deepseek` → `deepseek-v4.1-flash-free`, `zen-free-glm` → `glm-5.3-flash-free` and `zen-free-flint-40b` → `flint-40b-free`, with their display names and reasoning levels.
- The free template is the only one whose model-list sync filters by upstream pricing. `src-tauri/src/ai_gateway/templates/source.rs` skips every string-only entry and keeps an object entry only when the real upstream nested cost shape proves it free: present and zero `cost.text.input.price` and `cost.text.output.price`, plus zero for any cache read or write price present under `input.cache`. Missing, malformed, non-object or positive-priced entries are excluded. A known upstream id keeps its local alias, display name, enabled flag, reasoning efforts and context window; a new free model derives `zen-free-<upstream id without a trailing -free>` and falls back to the bare upstream id on an alias collision. Every other template keeps its existing sync behavior, and an empty filtered set remains fatal.
- The schema-5 gate binds, on the first read of an older file, only a provider that has no template, whose trimmed name is exactly `OpenCode Zen Free` and whose normalized base URL is exactly `https://opencode.ai/zen/v1`, leaving keys, mappings, prices and every other provider untouched, and it is idempotent. Before the rewrite it makes a one-time best-effort raw-byte copy `ai_gateway.json.bak-pre-schema5` with mode `0600` on Unix, created with `create_new` so an existing backup is never overwritten; a failed copy does not block the migration.
- The configuration schema is now 9. The schema-7 gate remains: when a persisted built-in template state has both its outer `template_id` and its nested `template.id` equal to `opencode-zen-free`, and its `transport_strategy` is missing, null or `direct`, only that field becomes `opencode_zen_sidecar`. The schema-8 gate repairs only the same canonical state's `models_url` when it is missing, null or blank, inserting `https://opencode.ai/zen/v1/models`; a nonblank URL, models, other template fields, sync metadata, providers, keys, mappings and prices stay untouched. The schema-9 gate repoints only the same canonical template snapshot and any provider bound to `opencode-zen-free` whose base URL normalizes to the legacy `https://opencode.ai/zen/v1` to `https://opencode.ai/inference/openai/v1`; custom base URLs, models, metadata, keys, prices, transport, `models_url` and unrelated templates and providers stay untouched. All repairs are idempotent and never touch another template. Gating is cumulative and never skips a step: a schema-9 or newer file is read as-is, a schema-8 file gains only the base-URL repair, a schema-7 file gains the URL and base-URL repairs, a schema-6 file gains the transport, URL and base-URL repairs, and a schema-5 file first drops its obsolete gateway proxy URL and then gains all three. A provider already bound to that template therefore resolves the sidecar transport and the official inference base, and the template becomes syncable, once the repaired snapshot is read.
- The relay is a separate process built from the nested crate `src-tauri/zen-relay`, which has its own workspace and pins `wreq = "=6.0.0-rc.31"` with the `socks` and `stream` features and without `prefix-symbols`. It is a loopback-only hyper server that reads a per-process random token from the first stdin line, reports `READY <port>` or `ERROR <message>`, binds `127.0.0.1` on an ephemeral port, limits request bodies to 64 MiB, accepts only HTTPS `opencode.ai` bases whose path is exactly `/inference/openai` or the legacy `/zen` or a `/...` subpath and rejects other hosts, schemes, paths, queries or fragments, joins paths without duplicating `/v1`, filters hop-by-hop and sidecar headers plus `accept-encoding`, streams responses unchanged, and logs only method, path and status. Its wreq client uses the accepted BoringSSL cipher list and the `X25519:P-256:P-384` curve profile.
- `src-tauri/src/ai_gateway/zen_sidecar.rs` owns the process. It starts lazily on the first sidecar attempt with a ten-second readiness timeout, keeps stdin open for lifetime and shutdown detection, drains stderr, and restarts after an exit. Its identity is the global proxy generation, the explicit proxy URL derived from the snapshot and the read timeout: a new generation creates a new child while admitted ordinary and SSE responses hold leases on the retiring child, which exits after its last response body finishes; an equivalent save or a check-interval-only save keeps the generation and reuses the current child. `stop` is idempotent, both gateway shutdown seams call it, and it terminates every owned current and retiring child. The locator checks `ONESPACE_ZEN_RELAY_BIN`, the executable's sibling, the nested debug and release targets, and `binaries/onespace-zen-relay-<triple>[.exe]`, and a missing binary fails the attempt with the expected paths and never falls back to direct forwarding.
- Sidecar forwarding uses a dedicated no-proxy client with a long read timeout, preserves the upstream path and query, and adds `x-onespace-sidecar-token` and `x-onespace-upstream-base` after client headers are forwarded. Both headers are also excluded from the forwardable client headers, so a client can never override them; the provider credential, body rewrite and other client headers keep their existing behavior.
- Building and bundling are automatic: `src-tauri/scripts/build-zen-relay.mjs` builds dev or release for the environment or host triple and copies the release artifact to the binaries directory, `tauri.conf.json` declares the external binary and prepends the script to the dev and build commands, and the release workflow builds it for macOS `x86_64`/`aarch64` and Windows `x86_64` after ensuring cmake and ninja.

## Alternatives considered

- Link wreq and BoringSSL inside the main application: declined because the vendored OpenSSL already linked through `ssh2` collides with BoringSSL's OpenSSL-family symbols in one binary; a process boundary is the only practical isolation.
- Keep the sidecar always running for the application lifetime: declined because most sessions never use a sidecar provider, and a lazy start keeps the idle process count and attack surface at zero while still paying only once per active session.
- Select the transport from URL, name or icon heuristics: declined because the same policy failure would return for any endpoint that happens to resemble Zen; the template binding is explicit, visible and validated on save.
- Forge a Bun-specific TLS fingerprint: declined as fragile and unnecessary; presenting a real BoringSSL client with the accepted cipher and curve profile is enough for the free tier and does not imitate another client.
- Require users to rebind their provider manually with no migration: declined because the existing provider would keep failing with 429 after the upgrade; the narrow exact-name and exact-URL binding preserves its data and the one-time backup keeps downgrade possible.
- Route every provider through the relay: declined because direct providers work with the existing client and retry behavior, and a universal relay would add a process and credential hop for traffic that does not need it.

## Consequences

- Sidecar lifecycle and security are owned by the gateway runtime: the process is loopback-only, authenticated by a per-process token delivered over stdin, has a bounded readiness wait, restarts on exit or identity change, keeps a retiring child alive through its last response lease, and is terminated together with every retiring child by both shutdown seams, so stopping the gateway or application leaves no relay process behind.
- Failures are explicit. A missing binary, a failed handshake or an unreachable relay fails the attempt with a path-bearing error instead of silently retrying directly, while other model-pool candidates and every direct provider continue normally; upstream statuses such as 429 are relayed unchanged so existing classification and retries still apply.
- Rollback is configuration-level: unbinding the provider or binding a direct template restores the existing direct behavior. Downgrading requires restoring `ai_gateway.json.bak-pre-schema5` first because a build older than schema 5 cannot read the binding, an older build cannot be assumed to preserve or understand schema 9, and the pre-fix relay rejects the `/inference/openai` base; if that copy failed, downgrade is unsupported.
- Production adaptation is a version-gated rollout, not a manual data edit. An installed build that predates the free-only filter must not receive a hand-added `models_url`, because its generic sync and auto-refresh would import every model in the shared upstream list, including paid ones. A pre-fix build, including 0.1.56 on schema 6, must not receive a hand-edited base URL either, because its relay accepts only `/zen` and rejects `/inference/openai`. The supported sequence backs up `~/.config/onespace/ai_gateway.json`, installs and launches a build containing this fix so the first config read migrates schema 6 to 9 and updates the persisted Zen template and bound provider base URL, transport and canonical `models_url`, then opens AI Gateway → Provider Templates → Zen Free → sync model list and confirms exactly the eight free models and a local `GET /v1/models` response of eight `zen-free-*` ids. After upgrading, gateway inference with `zen-free-glm` or `free-model` must be verified and the relay must show the upstream `/inference/openai/v1`; the standalone relay and real OpenCode CLI smoke already succeeded, but the production gateway smoke is still pending, so production success is not claimed. If the new build is not installed, production data stays unchanged.
- A successful model-list fetch, sync and display still does not prove inference. Endpoint and transport determine reachability: the legacy `/zen/v1` base returned 429 even for genuine credentials, while the official `/inference/openai/v1` base through the relay returned a successful stream in the standalone smoke. Hosted free-tier admission and the existing 429 classification and retry behavior are otherwise unchanged.
- Building the desktop application now requires cmake and ninja in addition to the Rust toolchain, and every release target builds and bundles the nested crate. The main application still has no wreq dependency, so its build and its other providers are unchanged.
- Runtime evidence remains bounded: the relay, lifecycle, migration, template and forwarding behavior are covered by unit and behavior tests, including the inference base URL and relay allowlist; a standalone new relay binary plus the real OpenCode CLI completed one request through `/inference/openai/v1` with 11 tools and a 200 `text/event-stream` response. The production gateway smoke remains after upgrade, and the Windows runtime smoke is not executed, leaving only the CI build and the cross-platform sidecar tests as Windows evidence.
- Supersession: [A Single Global Network Proxy Snapshot Drives Generation-Scoped Transport and Relay Leases](2026-10-29-shared-network-proxy-lifecycle.md) partially supersedes this record's relay identity, restart and shutdown statements. The global proxy generation and snapshot-derived explicit proxy URL now drive the child identity, response leases drain retiring children, and an equivalent save reuses the current child. The BoringSSL process boundary, template binding, alternatives, migration backup and known platform gaps remain in force; this record is retained and cross-linked.
