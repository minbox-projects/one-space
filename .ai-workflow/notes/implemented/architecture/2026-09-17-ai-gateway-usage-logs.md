# Agent Note: API Gateway Usage Stats and Request Logs

Status: implemented

English | [中文](2026-09-17-ai-gateway-usage-logs.zh.md)

## Problem

The API Gateway forwarded traffic but kept no record of what it served. There was no way to see per-request tokens, cost, success or failure outcome, or which upstream provider actually handled a local model, and the only persisted state was the encrypted `api_fusion.json` provider, key and terminal-sync ledger. Operators therefore could not answer "what did this gateway cost me and what failed" without external tooling, and there was no price model or retention control for the local relay.

## Decision

Request logs live in an independent, unencrypted SQLite file `api_gateway_usage.db` under `get_app_dir()`, implemented by `UsageLogStore` in `src-tauri/src/api_gateway/usage_log.rs` with the `usage_logs` schema. A record stores the UTC+8 timestamp, local model, actually-forwarded upstream model, provider id and name, result (`success` | `failure` | `cancelled`), HTTP status, input, cache-read, cache-write and output token tiers, total tokens, amount and duration; it stores no request or response bodies, no headers and no credentials. Only requests that pass local auth and enter the `/chat/completions` or `/responses` forwarding flow are recorded, while local auth failures (401), `GET /v1/models` and unknown paths or methods are not. Non-streaming responses are parsed from the buffered body, and streaming responses are read-only accumulated from the SSE `usage` chunk by `SseUsageAccumulator` without changing the bytes forwarded to the caller; missing usage fields become 0, a request without usage still gets a row, and only a storage failure is logged and swallowed so the response is never affected. Retention is configured in a new independent settings section `ai-gateway` (`SettingsTab` in `src/components/SettingsView.tsx`, default 90, range 1–365, stored as `usage_retention_days` with `#[serde(default)]`), and every log append permanently deletes rows older than the retention window.

Cost is computed at record time from the price row scoped to the actually-forwarded provider and upstream model (`match_price_for_provider` and `compute_cost_at_time` in `src-tauri/src/api_gateway/usage_log.rs`; matching is exact and case-sensitive on that provider's own row only, and a global row or another provider's row never matches; four tiers input / cache_read / cache_write / output in USD per million tokens), and the amount is frozen into the row, so later price edits never reprice history. An unpriced model stores `None`, renders as `—` and is excluded from totals; `unpriced_count` drives the "requests have no configured price" hint only for requests that would incur usage-based cost (a success, or a recorded `total_tokens > 0`) and excludes zero-usage failures as zero cost. Price maintenance now lives per mapping row inside the Add/Edit upstream provider dialog (`MappingPriceEditor`) and is saved together with the provider, so the usage-stats tab no longer offers a price entry and the legacy `ModelPriceDialog` is gone ([Gateway Model Prices Move Into Provider Mappings](2026-09-19-gateway-model-prices-in-provider-mappings.md) partially supersedes this record). `GatewayConfig` gained `usage_retention_days` (default 90) and `model_prices`, both `#[serde(default)]`, so an old `api_fusion.json` still deserializes with no migration. The current command surface is `api_gateway_usage_stats`, `api_gateway_request_logs`, `api_gateway_usage_retention_get` and `api_gateway_usage_retention_save`; the standalone `api_gateway_model_prices_get` and `api_gateway_model_prices_save` commands were removed by the 2026-09-19 change. Aggregation, grouping, filtering and pagination run in the backend with a fixed page size of 50 and UTC+8 range resolution (`resolve_range`); `days = null` means all time and `Some(1)` means today. Price and retention saves read the existing config, replace only their own field and write it back, so providers, local keys and `terminal_syncs` are never cleared, and an invalid retention outside 1–365 is rejected with an actionable error and never persisted. The frontend adds two tabs (`usage`, `logs`) inside the existing `api-gateway` page and one settings section (`ai-gateway`); no navigation id was added.

`api_gateway_request_logs` takes the canonical ungrouped value `group_by: "none"`, which is what the frontend sends; `null`, an absent value and the empty string are tolerated as ungrouped aliases for backward compatibility, while `"model"` and `"day"` select grouped rows and any other value is rejected with an actionable error. A response echoes the grouped value in `group_by` and reports `null` for an ungrouped page. An ungrouped page also carries a bounded, in-range `models: string[]` facet of distinct non-empty `local_model` values that respects the resolved range and status filter but neither pagination nor the model filter, so the frontend model selector can offer in-range models that are absent from the current page. A non-streaming response contributes tokens and cost only from its 2xx body, while a streaming attempt that fails after its first forwarded byte is recorded as a status-502 `failure` that keeps its already accumulated usage, so its tokens and frozen amount are counted too; failures without captured usage record all four token tiers at zero. `unpriced_count` with the `—` display applies only to requests that reached an upstream model with no matching price row and would incur usage-based cost (a success, or a recorded `total_tokens > 0`), so zero-usage failures, cancelled and no-upstream failures count as zero cost instead of unpriced.

## Alternatives considered

- Keep usage data inside the encrypted `api_fusion.json` ledger: declined because that file is the credential, provider and terminal-sync store rewritten as a whole, while usage rows are high-volume append-mostly data; an independent SQLite file keeps logging off the credential store and keeps writes and deletions transactional.
- Persist request and response bodies for later recomputation: declined because the data boundary forbids bodies, headers and credentials, and recomputation is unnecessary once the amount is frozen at record time.
- Recompute amounts at query time from the current price table: declined because editing a price would then rewrite history and make past totals unstable, contradicting the record-time freeze.
- Put the price table in the provider forms or the settings page: declined because prices are keyed by upstream model name across providers rather than per provider, and the entry belongs next to the usage analysis it explains.
- Treat an HTTP 200 streamed response as success: declined because at the time of this decision a streaming request whose upstreams are all unavailable also returned HTTP 200 with an SSE error event, so the result is taken from the gateway's final outcome and recorded as `failure` with no amount; that 200-SSE premise no longer holds for a pre-stream failure, which now returns HTTP 502 with a JSON error envelope.
- Let the frontend pull every log and paginate locally: declined because logs can grow unbounded, so aggregation, grouping, filtering and the fixed 50-row pagination stay in the backend with UTC+8 range resolution.
- Keep logs forever without retention: declined because an explicit window with permanent deletion is the requested data boundary, and cleanup runs on every write instead of on a background schedule.

## Consequences

- Logs live in an independent, unencrypted SQLite file `api_gateway_usage.db` under `get_app_dir()`; deleting it clears all log data and leaves the encrypted `api_gateway.json` ledger untouched.
- Amounts are frozen at record time, so later price edits only affect new requests; non-streaming responses contribute usage only from their 2xx bodies, mid-stream streaming failures keep their accumulated usage as status-502 `failure` rows, failures without captured usage record zero tokens, and unpriced models render as `—`, are excluded from totals and are counted in the unpriced-request hint only when the request reached an upstream model with no matching price row and would incur usage-based cost (a success, or a recorded `total_tokens > 0`).
- The request-log contract is stable and mirrored by `MEMORY.md` and `docs/USAGE.md`: `group_by: "none"` is the canonical ungrouped value, `null`, absent and empty are ungrouped aliases, `"model"` and `"day"` group, the response `group_by` is `null` when ungrouped, and the ungrouped page's bounded `models` facet feeds the frontend model filter independently of pagination and the model filter.
- `GatewayConfig` gains `usage_retention_days` (default 90) and `model_prices`, both `#[serde(default)]`; older configs still deserialize without migration, while a rollback version that rewrites the file drops these fields back to their defaults.
- Price and retention saves merge into the existing config, so providers, local keys and `terminal_syncs` survive; an invalid retention outside 1–365 is rejected with an actionable error and never persisted.
- The four current commands `api_gateway_usage_stats`, `api_gateway_request_logs`, `api_gateway_usage_retention_get` and `api_gateway_usage_retention_save` are exported from `lib.rs` and registered in `app_runtime/run_app.rs`, with aggregation, grouping, filtering and the fixed 50-row pagination in the backend; the standalone `api_gateway_model_prices_get` and `api_gateway_model_prices_save` commands were removed by the 2026-09-19 change.
- The frontend exposes the `usage` and `logs` tabs inside the existing `api-gateway` page and the `ai-gateway` settings section; no navigation id, launcher entry or other page changed.
- `docs/USAGE.md`, `MEMORY.md` and `navigation.json` describe this storage, recording, pricing, retention and price-entry behavior, and `navigation.md` was regenerated from the authoritative JSON.
