# Agent Note: Gateway Session Affinity Pins a Session and Model to One Upstream

Status: implemented

English | [中文](2026-09-20-gateway-session-affinity-routing.zh.md)

## Problem

The relay shuffles its candidates on every request (`selection::shuffled_candidates`), so with N eligible upstreams one account is picked with probability 1/N, consecutive requests of one client session land on different accounts, and no account keeps a warm prefix. Provider-side prompt caching only pays off while the same account keeps serving a conversation prefix, so under the pure per-request shuffle that prefix is rewritten on a randomly chosen account instead of being reused. Both terminal clients already send a session identity: OpenCode sends `x-session-affinity` and `X-Session-Id` because the gateway registers itself under the provider key `apigateway`, which is not `opencode`-prefixed, and Codex sends `session-id` on the current release and `session_id` or `conversation_id` on older ones — but no selection rule consumed those headers.

## Decision

Affinity is header-based because a session identity may come only from headers the terminals actually send, and both terminals already send one; it is scoped to one session and model so different sessions keep spreading over the accounts. The gateway derives the session identity from a fixed precedence list of client headers — `x-session-affinity`, `x-opencode-session`, `session-id`, `session_id`, `conversation_id`, `thread-id`, `x-session-id` — and takes the first header present with a non-empty trimmed value. A header whose value is empty or whitespace-only counts as absent and the walk continues, headers outside the list are never consulted, and the inbound map is read already lower-cased. `session-id` deliberately outranks `thread-id`: a Codex session sends its root thread and every subagent request with the same `session-id`, while `thread-id` names a single thread, so a precedence that preferred `thread-id` would split one session's requests across several bindings.

A binding is keyed by the session value together with the trimmed local model name, so two models of one session bind independently and a model that is absent or whitespace-only counts as absent. The first request of a session and model binds to the provider that the existing shuffle already placed first, and it writes that binding at selection time: the binding lookup, the shuffle and the first-request insert happen inside one critical section of the binding store, with the absent case re-checked inside it, so two concurrent requests for the same session and model select the same first provider. Later requests reorder the request's candidate list so that the bound provider is attempted first, leaving the relative order of every other candidate untouched.

A binding never widens the candidate set: it only reorders what the candidate filter already returned, so a provider with a mismatching protocol, a user-disabled or auto-disabled mapping row, or a user-disabled provider is never attempted merely because it is the binding. The binding is settled once per request after its terminal upstream outcome: when the bound provider was not among the eligible candidates of the current request, the binding is replaced immediately by the provider that actually serves it, at a zero miss count and without an attempt or a failure count for the former binding. While the bound provider stays eligible, a request that reaches a terminal upstream outcome on another provider records one miss, and the second consecutive miss migrates the binding to the provider that served the request; a request completed by the bound provider resets the miss count, and a downstream cancellation records nothing. A request with no candidate, no session header or no non-empty trimmed model neither reads nor writes a binding.

A binding that has been idle for more than 30 minutes is treated as absent, and the binding table holds at most 1024 entries, evicting the least recently used one. Bindings live in process memory only: nothing is persisted, a restart starts with none, and the header list, its precedence, the two-miss threshold, the idle expiry and the entry cap are constants — `api_gateway.json` keeps its schema and needs no migration.

The cache benefit is measured after release on the same model as before it: the per-provider Cache read hit rate and the per-provider share of request counts in Usage analysis, compared within the first week after release against the week before. `UsageStatsPanel.tsx` understates the hit rate of OpenAI-family providers because `prompt_tokens` already includes cached tokens while the panel computes `cache_read / (input_tokens + cache_read)`; that bias is stable per upstream and is explicitly not corrected here, so the before-and-after trend on the same upstream is the evidence.

## Alternatives considered

- Derive the session identity by hashing the prompt prefix: declined because a session identity may come only from headers the terminals actually send, and a prefix hash infers identity from request content instead of from what the client declares.
- Inspect the request body for a session identifier: declined for the same reason, and the relay only forwards the body; an identity derived from the body is not a session identity the terminals send.
- Use `x-codex-turn-state`, `x-codex-window-id` or `originator` as a key source: declined because none of them is the session identity the terminals send; a request carrying only those headers behaves exactly like a header-less request and never creates or reuses a binding.
- Add a parent and child session distinction: declined because a subagent must share its session's binding, so `x-parent-session-id` is ignored (it is outside the list) instead of splitting the binding.
- Make the header list, its precedence, the threshold, the expiry or the cap configurable: declined because this change adds no new configuration and no new interface; they stay constants and `api_gateway.json` needs no migration.

## Consequences

- A request carrying one of the known session headers with a non-empty trimmed model attempts its bound provider first while that provider stays eligible; a request carrying none of them, or an empty or whitespace-only value, keeps the current per-request shuffle exactly and neither reads nor writes a binding, so an unknown or renamed header degrades to today's behavior instead of failing.
- Sessions still spread over the accounts: bindings are per session and model, seeded by the existing shuffle, expired when idle and capped. A binding that keeps failing migrates at the second consecutive miss instead of costing one failed attempt on every request, and a binding that stops being eligible is replaced by the serving provider in the same request, with no attempt and no failure count for the former provider.
- The candidate set, the order of the remaining candidates, failure classification, retry order and backoff, cooldown deadlines, auto-disable, `RequestHealth` settlement, the error envelope, the caller-visible response bytes and the usage log rows are unchanged; the only difference is which eligible candidate is attempted first, and a binding never widens the candidate set.
- Bindings are process memory only: nothing reaches disk, `api_gateway.json` and `api_gateway_usage.db` keep their schema, no migration or backfill is needed, and a rollback or a restart starts with no bindings and the per-request shuffle as the only selection rule.
- The delivered rules live in `src-tauri/src/api_gateway/selection.rs` (`SESSION_ID_HEADERS`, `resolve_session_id`, `SessionAffinityStore`, `reorder_bound_first` and the process-global `session_affinity` table) and are applied around the existing candidate filter and shuffle in `src-tauri/src/api_gateway/runtime_http.rs`; the behavior tests in `src-tauri/src/api_gateway/tests.rs` cover the resolver and its boundaries, per-model bindings, concurrent selection, rebinding, migration, reset, idle expiry under a paused clock, the LRU cap, cancellation and the session-header failure paths.
- `MEMORY.md` carries the affinity standard and the session-binding exception of the initial candidate order in the same change; the delivered symbols are module-private (`pub(in crate::api_gateway)`) and no file path changed, so the navigation index needs no entry and `navigation.json` with its generated `navigation.md` stay authoritative and unchanged.
- Supersession: no supersession. [Gateway Per-Model Mapping Disable Is an Explicit Exclusion](2026-09-18-gateway-per-mapping-disable.md) is retained and cross-linked because the affinity reorder only reorders what its exclusion rule already left in the candidate set, and its decision still stands; [Gateway Per-Model Auto-Disable Settles Health on the Mapping Row](2026-09-20-gateway-per-model-auto-disable.md) is retained and cross-linked for the same reason, since the row runtime state it settles narrows that candidate set further and the reorder never widens it; [Gateway Single-Candidate Fast Fail and Standard Error Responses](2026-09-18-gateway-fast-fail-and-standard-errors.md) is retained and cross-linked because the affinity changes only which eligible candidate is attempted first inside its fallback-first schedule, and its scheduling and error-envelope decisions still stand; [Gateway Per-Attempt Request Logging and Stored Error Text](2026-09-20-gateway-per-attempt-logging-and-error-text.md) is unrelated to candidate selection and its log contract is unchanged. The usage-stats, model-price, provider-template, terminal-sync, aggregated-models, local-key and bilingual-note records are unrelated, so none is superseded.
