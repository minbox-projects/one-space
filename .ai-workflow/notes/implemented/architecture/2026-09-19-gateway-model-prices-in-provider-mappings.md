# Agent Note: Gateway Model Prices Move Into Provider Mappings

Status: implemented

English | [中文](2026-09-19-gateway-model-prices-in-provider-mappings.zh.md)

## Problem

Model prices used to live in a single `model_prices` table that already carried an optional `provider_id`, maintained in `ModelPriceDialog` from the Usage & Logs tab. Two providers serving the same upstream model shared a single price, a row without a provider id priced any provider that forwarded that model name, and matching fell back to any provider's row when the forwarded provider had none, so a price configured for one provider could silently price another provider's traffic. The operator asked for prices to belong to exactly one provider plus upstream model, to be edited next to the mapping they price, and to be saved together with the provider, while existing global rows had to keep their meaning for future requests and recorded amounts had to stay frozen.

## Decision

Prices are maintained per mapping row inside the Add/Edit upstream provider dialog. `MappingPriceEditor` renders the four tiers (input / cache_read / cache_write / output, USD per million tokens) and an optional off-peak configuration inside the mapping row's details region, collapsed by default and expanded together with the reasoning efforts by that row's expand arrow (`data-testid="api-gateway-mapping-expand-{index}"`, `aria-expanded` synchronized, accessible name `apiGatewayMappingDetails` — "Mapping details"); a collapsed row renders neither the editor nor the reasoning efforts panel, and the editor renders only when the upstream model is non-blank; rows sharing one upstream model edit one shared draft, all four blank tiers mean the model is unpriced and produce no row, a row with any tier filled is priced with blank tiers counted as 0 (an explicit 0 in every tier is priced at `0.0000`), and off-peak windows keep the existing UTC+8 semantics (optional weekday set with `0` Sunday to `6` Saturday, absent or empty meaning every day, first matching window). Saving the provider submits the provider plus its complete price-row set in one `api_gateway_upsert_provider` call, and the backend replaces exactly that provider's rows in one atomic `write_config`; a save without a price list leaves that provider's rows unchanged, `api_gateway_delete_provider` also removes its rows, and removing a mapping removes its row.

Cost is computed at record time from the forwarded provider's own row only: `match_price_for_provider` requires the provider id and the upstream model name to match exactly and case-sensitively, and the global and any-provider fallbacks are removed, so a row owned by another provider or carrying no provider id never prices a request. Loading a configuration normalizes the price table in memory, idempotently and persisted by the next write: a legacy global row whose model equals a provider's non-blank mapping upstream model or its trimmed `default_model` becomes that provider's scoped row when the provider has no row for that model, every remaining global row is deleted, and rows whose provider no longer exists or whose model is unreachable from its provider (neither a mapping upstream model nor the default model) are dropped, including on manual providers. Recorded amounts stay frozen: migration and price edits only affect new requests, and the usage SQLite schema and history are untouched.

The default model is now a selection over the provider's distinct non-blank mapping upstream models plus an empty choice. When the dialog opens and the loaded `default_model` is covered by no mapping, it is materialized as a visible mapping row marked as auto-added (`local_model` = `upstream_model`, enabled, protocol inherited) that carries the provider's existing scoped price row for that model when one exists; the default selection and the forwarding target stay the same, and saving without removing that row persists both the mapping and its price.

## Alternatives considered

- Keep the price entry in the Usage & Logs tab next to the usage analysis: declined because that view cannot bind a price to the provider that actually forwards the model, the mapping row is the only place where the provider plus upstream model pair is unambiguous, and keeping both surfaces would let the same price be edited in two places.
- Embed prices into the mapping schema itself (for example a `price` object on each `ModelMapping`): declined because duplicate mappings can share one upstream model and would then hold divergent copies, delete and restore would have to maintain per-mapping rows instead of provider-scoped rows, and the existing `model_prices` list already carries rows keyed by provider and upstream model without a schema migration.
- Keep an invisible global fallback for rows no provider claims: declined because a hidden fallback that silently prices another provider's traffic is the defect being removed; unmatched global rows are migrated or deleted instead, and the provider-scoped entry is visible where the price applies.

## Consequences

- Every effective price row carries a provider id, and only the forwarded provider's own exact row prices a request, so one provider's price can no longer price another provider's traffic and a global row can never price anything.
- The provider dialog is the only price entry: the Usage & Logs tab keeps the usage analysis, the `—` rendering and the unpriced hint without any price button, and `ModelPriceDialog`, the `apiGatewayModelPricesGet` / `apiGatewayModelPricesSave` wrappers and the `api_gateway_model_prices_get` / `api_gateway_model_prices_save` commands are removed.
- Migration is read-time and idempotent: each global row becomes one scoped row per reaching provider that has no row for the model, unmatched or unreachable rows are deleted including on manual providers, a scoped row for a provider's default model survives the save that materializes that default as a marked auto-added mapping row because the row carries it, and the normalized table is persisted by the next write.
- Saving is atomic and exact: one `api_gateway_upsert_provider` call replaces exactly that provider's rows, submitted rows bind to the provider id generated for a new provider, duplicate or blank upstream models are dropped, removing a mapping or a provider removes its rows while other providers stay untouched, and a missing price list leaves the rows unchanged.
- Template-bound providers keep their binding and ignored-model lifecycle, but no template flow touches prices: [Provider Templates Drop Built-in Model Catalogs and Prices](2026-09-19-provider-template-manual-model-sync.md) removed the template price data and the sync price propagation, so a sync, a creation and a restore never create or modify a price row, newly created or restored template models start unpriced, and every provider-scoped row is entered by hand in the mapping dialog; deleting a mapping still removes its row.
- Recorded history is frozen: migration and price edits never recompute past amounts, and the usage SQLite schema, recorded fields and retention behavior are unchanged.
- Rollback: reverting the code needs no data migration because the older build still matches provider-scoped rows first, so rows written by the new build keep pricing new requests; global rows already migrated or deleted are not restored automatically, the legacy dialog can recreate unassigned rows if the operator needs them, and usage history and the SQLite schema are untouched.
- Partial supersession: [API Gateway Usage Stats and Request Logs](2026-09-17-ai-gateway-usage-logs.md) is retained and cross-linked; this record replaces only its price-entry and global-matching decisions, while its SQLite logging, record-time price freeze and retention decisions remain in force, and its `unpriced_count` eligibility is partially superseded by [Gateway Unpriced Hint Counts Only Billable Usage](../bug-fix/2026-09-21-gateway-unpriced-billable-usage.md).
- `MEMORY.md`, `docs/USAGE.md` and the `api-gateway` / `api-gateway-backend` entries in `navigation.json` describe the same entry point, matching, migration, atomic save and default-model behavior, and `navigation.md` was regenerated from the authoritative JSON.
