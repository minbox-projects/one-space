# Agent Note: Gateway Migration Is Permanent and Version-Gated

Status: implemented

English | [中文](2026-09-24-version-gated-gateway-migration.zh.md)

## Problem

The gateway carried compatibility that ran on every configuration read: each read normalized the price table, converted singular off-peak windows and cleared legacy provider-level runtime fields, and every usage-log query excluded `cancelled` rows that no gate ever removed; the frontend kept the matching fallbacks, and `migration.rs` was declared a one-release module whose deletion depended on an upgrade window no build could observe. The compatibility was downgrade-only: once a release had written a current-shaped file it could never trigger for that user again, yet every later release kept paying for it, and the "delete in the next release" contract could silently break any installation that skipped that release. Deleting the compatibility outright was not an option either: a configuration that had never been normalized would lose its prices and runtime state, and the `cancelled` rows that all supported queries already ignored were still physically present.

## Decision

The persisted gateway configuration carries `GATEWAY_CONFIG_SCHEMA_VERSION = 2` (`GatewayConfig.schema_version` in `src-tauri/src/ai_gateway/types_config.rs`, `#[serde(default)]`, missing = 0 = legacy), and the usage database carries its own `PRAGMA user_version` gate. `src-tauri/src/ai_gateway/migration.rs` is permanent and version-gated: its former single-release deletion contract is replaced by the version gate, and it remains the only non-test home of the legacy file names, the legacy gateway marker and legacy field names (including the single credential field `api_key`).

- `storage::read_config_file` always runs the pure migration, stamps the current version and best-effort atomically rewrites the encrypted file through `write_config` whenever the stored version is older. A failed rewrite keeps the previous complete bytes and the next read retries the migration; a configuration already at the current version is read with no migration and no write, and a future or unknown version is read as-is without a rewrite.
- `write_config` applies `scope_model_prices` and stamps the version on every write.
- `migrate_legacy_config` performs the raw-JSON migration: it scopes global price rows exactly as the former per-read normalization did, folds a singular `off_peak` into `off_peaks`, clears provider-level runtime keys, and converts a legacy single `api_key` into exactly one enabled `Default`-named pool entry (a blank or missing value yields an empty pool) while removing the old field.
- `migrate_legacy_files` keeps the one-time in-place file renames and `has_legacy_gateway_marker` the legacy terminal-marker predicate.
- `migrate_usage_database` advances `PRAGMA user_version` to 1 and transactionally deletes every `result = 'cancelled'` row once on the first open of an older database; later opens delete nothing.

Each removal is behavior-neutral: the price scoping, off-peak folding and runtime-key clearing happen exactly once, before any request can observe the configuration, and produce the in-memory value the former per-read normalization produced; costing reads `off_peaks` directly because the singular field is folded before it could be read; provider-level runtime fields were already non-filtering legacy, only mapping rows had settled runtime health since the per-model auto-disable change, and the migration drops the old keys from the rewritten file; the legacy single credential is converted to a `Default`-named pool entry exactly once, before any request can observe the configuration, and a blank or missing value yields an empty pool, so the credential a provider serves with is unchanged by the conversion; `UsageResult::Cancelled` and its parser and SQL exclusion are removed together with the rows, and every user-visible query already excluded those rows, so no page, total, facet or group changes; the `"********"` sentinel comparisons in `ai_gateway_upsert_provider` / `ai_gateway_upsert_key` are removed together with the frontend `AI_GATEWAY_KEY_MASK` constant that produced the placeholder, so an all-whitespace value still preserves or generates as before and no supported caller can send it; the whole-configuration `ai_gateway_save_config` command with `save_config_inner` and its `run_app.rs` registration had no frontend caller after its wrapper was removed, and every write goes through the surviving provider, key, retention and template commands; the removed re-exports, the unreachable `effective_default_key` fallback, `AttemptLog::default`, `GatewayKey::default` and the test-only helpers moved behind `#[cfg(test)]` (including `usage_log::is_off_peak`) had no production callers or were unreachable; on the frontend the deleted `UpstreamProviderDetail` component, `resolveMappingPreview` / `GatewayMappingPreview`, the props with no production caller (`onDelete` and `templateSection` on `UpstreamProviderList`, `providers` and `onEditTemplate` on `ProviderTemplatePickerDialog`, `hideTitle` on `ProviderTemplateSection`), the duplicated helpers consolidated into `src/components/AiGateway/gatewayShared.ts` and the 51 unreferenced bilingual keys had no reachable call site, so build, lint and the bilingual parity gate stay green. One deviation from the plan is recorded as delivered: `templateSection` was rendered by `UpstreamProviderList` and covered by a dedicated slot test, but no production caller ever passed it, so removing the prop also removed that test and the frontend suite moved from 1179 to 1178 tests.

## Alternatives considered

- Delete `migration.rs` in the next release as originally planned: declined because the deletion condition cannot be observed by the build; an installation that skips that release would lose its prices and runtime state, while the version gate lets any future release upgrade any older file and becomes a no-op for current files.
- Keep the per-read normalization and compatibility branches and remove only the obviously dead symbols: declined because every read would keep rewriting the in-memory value for a downgrade-only path, and the compatibility surface would grow with each schema change instead of being confined to one versioned migration.
- Delete `cancelled` rows without a database version marker: declined because the deletion must be provably once; the marker records that the cleanup completed, so later opens delete nothing and repeated starts stay idempotent.
- Keep the `"********"` sentinel contract after removing the frontend constant: declined because a blank value already means "no value supplied" on both create and edit, and the sentinel existed only because the frontend echoed the mask; keeping the comparison would preserve a compatibility path with no producer.
- Rewrite the migrated configuration unconditionally on every read: declined because a current-version read must stay side-effect free and a read that cannot rewrite must keep the previous complete bytes; only an older stored version triggers the best-effort write, and a failure is retried by the next read.

## Consequences

- A legacy configuration is migrated and rewritten once at schema version 2 — including the single-credential-to-pool conversion — and a legacy usage database is cleaned once at `user_version = 1`; a current-version installation reads and opens with no migration write and no deletion.
- A failed rewrite or deletion never exposes partial state: the read still returns the migrated in-memory configuration, the on-disk file keeps its previous complete bytes, and the next read retries; deleted `cancelled` rows cannot be restored.
- The migration is idempotent and safe to carry at any future release: it is a no-op for files at the current version, and a future or unknown version is read without a downgrade.
- Downgrades stay best-effort: `off_peaks` remains primary and unknown fields are ignored, but a reverted build no longer sees provider-level runtime fields or `cancelled` rows.
- The migration reads and writes the encrypted `ai_gateway.json` and the usage SQLite file before any request is served; forwarding, retry, settlement, usage statistics, template sync and terminal sync behavior are unchanged.
