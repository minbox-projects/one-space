# Agent Note: API Gateway Smooth Weighted Round Robin Routes Requests and Fallback Candidates

Status: implemented

English | [中文](2026-09-20-api-gateway-weighted-routing.zh.md)

## Problem

Previously, the gateway treated all eligible upstream providers equally, selecting candidates via uniform random shuffling (`selection::shuffled_candidates`). When users configured multiple accounts or providers with asymmetric rate limits, quotas, tier levels, or token balances (e.g. a high-tier paid plan alongside a low-quota free tier), the uniform shuffle routed traffic evenly (1/N probability), leading to premature quota exhaustion on smaller providers while larger capacities remained underutilized. Furthermore, when a request carried session affinity headers for a new conversation, the initial upstream binding was seeded by this uniform random shuffle, causing long-lived sessions to distribute evenly across accounts rather than respecting user-configured capacity differences. In the frontend, providers lacked any weight setting in `ProviderDetailDialog` and had no visual indicator of capacity allocation on provider cards.

## Decision

Each upstream provider configuration (`GatewayUpstreamProvider`) supports an integer `weight: u32`, with a default of 1 and an allowed range between 1 and 100 (`MIN_PROVIDER_WEIGHT` to `MAX_PROVIDER_WEIGHT`). The field uses `#[serde(default = "default_provider_weight")]` to ensure existing `api_gateway.json` configurations deserialize with a default weight of 1 without requiring manual migration. Inbound config persistence via `api_gateway_save_config` and `api_gateway_upsert_provider` strictly validates the weight range, rejecting values less than 1 or greater than 100 with an actionable error and refusing to write to disk. In the frontend, `ProviderDetailDialog` provides a dedicated numeric input (with a range helper text "1–100") validating positive integer inputs, and `UpstreamProviderList` displays a prominent `Weight: X` (or `权重: X` in Chinese) badge on each provider card.

Candidate scheduling adopts the Smooth Weighted Round Robin (SWRR) algorithm implemented in `selection::weighted_candidates`, replacing the legacy uniform random shuffling. A process-global state map (`WEIGHTED_SCHEDULER`) tracks the dynamic current weight of each provider. For each candidate resolution: (1) each candidate's current weight is incremented by its effective weight (`weight.max(1)`); (2) the candidate with the highest current weight is selected as the primary upstream, using provider ID lexicographical comparison (ascending order) as a deterministic tie-breaker; (3) the selected candidate's current weight is reduced by the total weight of all participating candidates; (4) the remaining candidates are sorted in descending order of their updated current weights (with provider ID ascending as tie-breaker) to construct a deterministic fallback sequence. If the candidate list has zero or one candidate, it is returned immediately without scheduler mutation. Disabled or auto-disabled providers and models are pre-filtered by candidate resolution and never participate in weight accumulation or scheduling.

Weighted routing integrates seamlessly with session affinity (`session_affinity`). Stateless requests without session headers are routed and ordered strictly by `weighted_candidates`. When a request introduces a new session without an existing binding, the initial upstream candidate is resolved via `weighted_candidates` within the affinity critical section and stored as the session's pinned provider, ensuring long-lived sessions distribute across provider accounts in exact proportion to their configured weights over time. When a request matches an existing active session binding and the bound provider remains eligible, that bound provider is placed first to preserve prefix cache continuity, while all remaining eligible candidates maintain the deterministic weighted fallback sequence produced by `weighted_candidates`. The existing session affinity lifetime, LRU cache cap, consecutive miss migration rules, and failover behavior remain fully preserved.

## Alternatives considered

- Random weighted selection (roulette wheel selection): declined because pseudo-random weighted sampling produces clustering and uneven bursts over small request windows, whereas Smooth Weighted Round Robin provides mathematically deterministic, smooth interleaving of requests across upstreams.
- Pure stateless round-robin without weights: declined because providers have asymmetric rate limits and quota tiers, and an unweighted rotation cannot reflect capacity differences between accounts.
- Random fallback ordering for remaining candidates: declined because when the primary candidate fails, fallback retries should prioritize the upstream with the next highest dynamic capacity rather than a randomly selected one.
- Separate session routing pools decoupled from weights: declined because session affinity should naturally honor account capacity proportions upon initial assignment rather than requiring redundant pool configuration.
- Floating-point weights or unbounded integers: declined because an integer range of 1 to 100 is intuitive for operators, avoids floating-point precision hazards in weight accumulation, and covers typical multi-account ratio requirements.

## Consequences

- Upstream provider configurations support `weight: u32` (range 1–100, default 1, `MIN_PROVIDER_WEIGHT` to `MAX_PROVIDER_WEIGHT`), deserializing seamlessly from legacy configs without schema migrations; values outside 1–100 are rejected by `api_gateway_save_config` and `api_gateway_upsert_provider`.
- The gateway replaces uniform random shuffling with Smooth Weighted Round Robin (`selection::weighted_candidates`), picking the candidate with the highest current dynamic weight and ordering remaining candidates by descending dynamic weight for fallback retry; zero or single candidate requests pass through without scheduler overhead.
- Session affinity integrates with SWRR: stateless requests use SWRR ordering directly; new conversations have their initial upstream bound according to SWRR, spreading multi-session workloads proportionally across accounts; existing active bindings keep the bound provider first while remaining candidates follow weighted fallback.
- Frontend `ProviderDetailDialog` provides a validated weight input field (1–100, default 1), and `UpstreamProviderList` renders a `Weight: X` / `权重: X` badge on each provider card, with full bilingual i18n support.
- Partial supersession: [Gateway Session Affinity Pins a Session and Model to One Upstream](2026-09-20-gateway-session-affinity-routing.md) is retained and cross-linked; this record replaces only its reliance on uniform random shuffling (`selection::shuffled_candidates`) for initial candidate ordering and seeding new session bindings, while its header precedence, 30-minute idle expiry, 1024-entry LRU cap, and two-miss migration rules remain fully active.
- `MEMORY.md` documents the provider weight configuration attribute, the SWRR candidate scheduling and fallback sequencing algorithm, and the session affinity synergy in the same change; navigation index and test suites are verified clean.
