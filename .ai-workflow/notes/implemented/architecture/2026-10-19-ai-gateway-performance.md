# Agent Note: AI Gateway Avoids Redundant Configuration, History, Database, Stream Framing and Management Fetch Work

Status: implemented

English | [中文](2026-10-19-ai-gateway-performance.zh.md)

## Problem

A warm gateway read avoided decryption through the file-identity cache, but each read still returned an owned `GatewayConfig` deep clone. Request handling, listener status/start/stop, model discovery, autostart and the per-attempt key-mark reread all paid that copy, so local work grew with the complete stored provider, mapping, key, price and pool set even though those consumers only read. Model-pool planning had a second multiplier: it cloned a complete provider to build a one-mapping routing view for every stored candidate, including disabled providers and disabled mappings that could never serve or be probed. Same-turn continuation parsing copied the caller history array into a `Value`, and recording a delivered hold cloned that history again, so a large conversation was copied twice before its existing prefix, tool-identity and byte-budget checks ran. Streaming observation also continued work it no longer needed: the timing observer framed every complete SSE event for the whole upstream stream even though only the first meaningful event can set the first-output instant. Once that instant was known, later events in the same received read and every later chunk were still buffered, scanned for a boundary, drained and parsed, and a final unterminated event could remain buffered until finish even though the observation window was already closed. The usage dashboard repeated the same pattern at the database layer: every read opened, initialized and migrated the SQLite file and re-prepared the same statements, usage statistics scanned the provider set a second time and filtered it per model, and provider history opened and initialized its own handle for the same read. Quota and Go-usage refreshes duplicated work in the same way: concurrent lookups for the same account each started their own network fetch even when the first was still in flight, so a burst of card refreshes multiplied upstream requests. The built-in provider template snapshot was also reparsed on every template lookup even though its embedded bytes cannot change at runtime. The management dashboard repeated similar redundant reads at the page layer. Every load fetched today's statistics and a grouped today log only to sum failure counts that the statistics already expose; the five-second freshness poll and the focus catch-up repeated those reads even when an equivalent request was in flight; a burst of configuration events started one scoped reload per event; and a configuration mutation or older reply could be overwritten by a response that started earlier. The first mount also constructed every heavy tab and every usage subview even when never visited, while inactive panels kept rebuilding their rows and number formatters on each render.

## Decision

`storage` keeps the process read cache keyed by path, byte length and modification time but stores an `Arc<GatewayConfig>`. `read_config_shared()` returns the shared immutable value for read-only hot consumers: the request boundary, listener start/stop/status, autostart and the per-attempt key-mark refresh. `read_config()` remains the owned API for callers that need ownership and clones only when it must hand out an owned value; `modify_config()` takes an owned copy under the existing write lock so it can mutate, writes atomically, and publishes the normalized result as a new cached `Arc` only after a successful write. A direct on-disk rewrite that changes file identity is still observed by the next read; no TTL, result cache, content hash or serialization field is added. The only copy counters are test-only `cfg(test)` seams.

Model-pool planning now builds the one-mapping routing clone only for a candidate whose provider and mapping are enabled. An auto-disabled mapping is still prepared because it can be the eligible half-open probe; disabled providers and disabled mappings stay borrowed and are never prepared. The healthy candidate list holds references to the resolved candidates, and weighted ordering clones only the prepared providers it actually returns, plus the single probe it appends. Candidate set, eligibility, weights, independent SWRR accounting, fallback order, reasoning filtering, cooldown and probe placement are unchanged.

`CallerHistory` stores its history as `Arc<Value>` and a `HoldEntry` shares that value instead of cloning it. Parsing allocates the array once inside the `Arc`; recording a delivered hold increments the reference count. Prefix comparison, instruction/tool-context equality, tool-call identity, admission-token ordering, entry count, per-entry and total byte budgets, expiry and eviction are unchanged.

`OutputTimingObserver` stops observing once the first meaningful output is known. `feed_at` returns without buffering or framing when `first_output_at` is already set; in the read that establishes the observation it stops framing at that event, discards the remaining buffered events and clears the buffer. `finish_at` still records the whole-attempt end instant on its first call, and before any output is known it still recognizes a final valid event that arrived without a terminating blank line. A buffer that never terminates remains bounded by the existing `MAX_BUFFER_BYTES`. The first-token instant, the whole-attempt TPS window, the meaningful-output rules, raw-upstream observation and every forwarded byte are unchanged. Usage collection and pool-continuation observation remain independent and keep their own tolerances; no shared SSE framing helper is introduced because the observer is the only consumer of this stop-after-first-output rule.

`usage_store` keeps one query connection per database path, separate from the existing write connection. Each path and role has its own mutex; the global entry-map lock only covers the short lookup and is released before SQL or schema initialization, so unrelated paths never serialize. A handle is reused only while the actual file identity (device and inode) still matches, so a replaced, restored or deleted database is reopened and initialized against the file that is present. Query connections use `prepare_cached` with a capacity of 256; this reuses statements, not results, so newly committed rows stay visible. `UsageLogStore::query_connection`, `with_query_connection`, `QueryConnection` and the test-only `QueryWorkStats` counters are internal to `ai_gateway`, not new public commands or fields. `usage_stats` derives model aggregates and provider rows from one grouped scan plus a hash lookup instead of a second full provider scan and per-model filtering. `provider_usage_history` reads metadata and summaries through the same query connection inside one read transaction. Detail rows and eligible provider/day contributions still commit in one request transaction, retention still runs immediately after each successful append, and no request batching was added. No index was added; configuration schema 3, usage database `user_version` 2, existing tables, columns, stored values and DTO/command serialization are unchanged, as are journal mode, durability and the busy timeout.

`quota` and `go_usage` keep an in-flight map beside the existing five-minute snapshot cache. A flight is keyed by the exact source identity: provider id, pinned source key value, provider base URL and effective quota policy name. A cold miss whose identity already has a flight joins it, and a forced refresh still bypasses the completed snapshot cache but joins the matching in-flight fetch instead of starting a second network request. The owner publishes its settled result over a `watch` channel that keeps its own receiver alive, so a follower subscribing after settlement still receives that result. Settlement removes the entry only while it still points at the same owner. A failed fetch or parse is published to current joiners but never stored in the snapshot cache, so a later lookup retries; dropping an owner before completion settles its flight with an error and removes only its own entry, leaving a replacement untouched. Pinned-key selection, the effective-policy guard before any key or base-URL read, fixed endpoints, the existing 15-second timeout and no-redirect clients, 300,000 ms freshness, provider-scoped key/base-URL invalidation, the force bypass of a completed cache and read-only behavior are unchanged. No DTO, command signature, serialized field or persisted state is added.

`templates::builtin_templates` parses the compile-time embedded snapshot once per process through `OnceLock` and returns a clone of the validated list. A persisted template snapshot still wins in `effective_template`, and an unknown or deleted template id still fails. `commands`, `auto_refresh` and `daily_reset` needed no product change: their measured management paths showed no repeated read worth editing, and template batch order, manual/automatic single-flight, terminal-write boundaries, daily-reset scanning and lifecycle behavior are unchanged. No general single-flight framework or scheduler redesign is introduced.

`aiGatewayUsageStats(range, options?)` and `aiGatewayRequestLogs(query, options?)` join one in-flight read keyed by the complete parameter set. The entry is removed as soon as the exact source promise settles, including on failure, so a later read retries and no result is cached; `{ fresh: true }` starts an independent read for manual refresh instead of joining. The option type is internal, and query payloads, DTOs and command serialization are unchanged.

`AiGateway/index.tsx` keeps configuration, today, status and pool generations; a hidden page, a newer configuration read or a newer request invalidates earlier replies before they can commit. A hidden page issues no page read, and configuration-event bursts run at most one current scoped read plus one follow-up, with hidden events only recording pending work. A hidden-to-visible transition performs one coherent page read and consumes the interval's single catch-up. Today's failure count is derived as `max(0, request_count - successful_request_count)` from the same statistics snapshot, so the grouped log read is gone; a plain, ungrouped today log read supplies only the fallback count when statistics are unavailable. Configuration mutations supersede earlier reads, and runtime updates keep the existing merge and draft behavior.

The model list, model pools, terminal integration and all three usage subviews mount on first visit and stay mounted afterwards, hidden but state-preserving; providers remain the initial mounted tab. Visited panels are memoized and skip row, candidate and count derivation while inactive, with stable callbacks and tab counts derived from configuration through memoization. Locale-aware `Intl.NumberFormat` instances are cached per resolved locale in the statistics, logs, history and quota blocks. No DTO, schema, i18n, or runtime-status/visibility API changes are made.

## Alternatives considered

- Add a TTL or result cache, or keep a separate configuration snapshot per route: declined because an immutable `Arc` handed from the existing identity-checked cache preserves freshness without a staleness window or another invalidation surface.
- Hash configuration bytes to validate the cache: declined because path, byte length and modification time already invalidate every real change, including a direct on-disk rewrite, without hashing secrets or adding cryptographic work.
- Keep preparing a complete provider clone for every stored candidate: declined because disabled providers and disabled mappings cannot be selected or probed, so their copy work must not scale with the stored set.
- Clone the caller history again when recording a delivered hold: declined because the parsed history is immutable; prefix and byte-budget checks can read the same shared value.
- Move shared state into serializable transport types: declined because this sharing is process-internal; public commands, DTOs, serialized fields and schema stay unchanged.
- Extract a shared SSE framing helper for the observer and the converters: declined because only the observer needs the stop-after-first-output rule, while the converters and usage observers retain different tolerance and completion semantics; a shared helper would either merge those rules or add an abstraction with no second user.
- Cache query results or add a TTL for usage reads: declined because the requirement is fresh committed data from the current file, and a result cache would add staleness without reducing the dominant open, initialization and preparation work.
- Use one pooled connection for reads and writes or hold the entry-map lock across SQL: declined because readers would wait on writers and unrelated database paths would serialize during schema work; separate per-path entries keep both boundaries independent.
- Add an index without execution-plan evidence: declined because the measured paths already group and filter on existing columns, and the change introduces no unproven index or migration.
- Serialize quota or Go lookups globally, or add a result TTL for in-flight requests: declined because unrelated sources would queue and the existing snapshot cache already owns freshness; per-identity flights join only the same source.
- Let a forced refresh start a second fetch while a matching fetch is in flight: declined because it rereads the same account without producing newer data and multiplies upstream load during refresh bursts.
- Serve a forced refresh from the completed snapshot cache: declined because force is the explicit bypass of a completed snapshot; only an in-flight join is shared.
- Reparse the built-in template snapshot per lookup or memoize the effective template including persisted state: declined because the embedded bytes are immutable, while persisted syncs must stay authoritative and observable without a stale memo.
- Cache settled dashboard reads or add a TTL: declined because the visible poll and manual refresh must observe committed rows; in-flight sharing removes duplicate work without introducing staleness.
- Coalesce by command name or serialize every page read: declined because ranges, filters, grouping and pages are distinct reads, and unrelated views would wait on each other.
- Keep the grouped log read to compute today's failure count: declined because the statistics totals already contain request and success counts; the ungrouped log read remains only as an unavailable-statistics fallback.
- Keep every tab eagerly mounted or unmount a tab on leave: declined because eager mounting builds unvisited views while unmounting discards filters, drafts and focus; first-visit mounting keeps both.
- Gate the UI change on jsdom elapsed time: declined because deterministic duplicate-work counts test the read and render work directly, while jsdom timing is only a proxy.

## Consequences

- Warm hot reads share the cached configuration: eight repeated model-discovery reads after warm-up observed zero owned configuration copies, where the previous implementation observed eight.
- The next read observes a direct configuration rewrite with changed file identity, and the next attempt observes a key-state publication made while an earlier attempt was in flight; neither a request-start snapshot nor the shared cache freezes key marks.
- Planning a pool whose stored candidate count grows from two to twelve kept the provider-copy count flat, where the previous implementation copied three and thirteen respectively. Only the candidates that can actually serve or probe are prepared, and the delivered order and probe remain equivalent.
- Parsing and recording one delivered continuation copies the history at most once, where the previous implementation copied it twice; the existing continuation limits and decisions are unchanged.
- Streaming observation now ends its framing work at the first meaningful event: the event that establishes the observation is counted, while a later event in the same read and all later fragments are not framed. The first-output instant and whole-attempt TPS keep their definitions, and a final unterminated valid event observed before any output is still recognized at finish.
- A warm query path opens, initializes and migrates the actual database once per file identity, and repeated identical reads reuse prepared statements; a deleted or replaced file is reopened and initialized instead of serving rows from the old handle. Newly committed rows remain visible because no result is cached.
- Usage statistics now runs one grouped scan for both model aggregates and provider rows, with the provider rows assembled by local-model hash lookup; provider history reads metadata and summaries in one read transaction on the same query connection.
