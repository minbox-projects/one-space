# Agent Note: Gateway Key Pool Rotation Is Ordered, Probe-Limited and Manual-Only for Auth

Status: implemented

English | [中文](2026-09-24-gateway-key-pool-rotation.zh.md)

## Problem

An upstream provider could hold only one credential: a 401/403 disabled the mapping row immediately and an exhausted or revoked key left the operator editing the provider by hand, while providers that issue several keys (per project, per account or per quota cycle) had no way to keep them ordered and in service. A multi-key pool also has to stay predictable while it fails: an exhausted or rejected key must not be retried indefinitely, recovery must not spend the bounded retry budget or distort mapping-row health, and an operator must be able to see which key is out of service and bring it back deliberately. The change therefore had to decide how a pool serves traffic, when a marked key may return by itself, and which failures stay manual.

## Decision

An upstream provider persists an ordered key pool (`GatewayUpstreamProvider.keys: Vec<UpstreamKey>`, schema version 2) where list order is the user-visible priority. Each entry carries a stable id, a required non-blank name, its value, the user's `enabled` flag and the runtime mark fields (`auto_marked`, `failure_kind` of `authentication` or `quota`, `marked_at`, `reason`), and every field is always serialized. Whenever the gateway prepares one attempt, it selects the first enabled and unmarked key in list order, so traffic sticks to the highest-priority usable key instead of spreading across the pool or reordering itself after a failure.

Rotation is scoped to the two key-specific failure classes. A 401/403 marks the attempted key as `authentication`, a quota-classified 429 marks it as `quota`, and the same request immediately continues on the next usable key without a backoff wait, without consuming the per-request retry budget and without registering mapping-row health; a streaming request rotates only before the first byte is written to the client. Transient 429, network, 5xx, 404 and other 4xx failures never mark a key and never rotate. Marks persist in the encrypted configuration, so a restart never retries an auth-failed key and a quota cooldown survives.

Recovery is cooldown-based or explicit. Only when no enabled unmarked key remains does a request probe at most one eligible key after `KEY_PROBE_COOLDOWN_SECS = 60`, choosing the oldest `marked_at` first and breaking ties by list order; a successful probe clears the mark and serves with that key, and a failed probe re-arms the cooldown. Auth-marked keys are never probed: they recover only through `ai_gateway_reenable_provider_key(provider_id, key_id)` or by editing the value, both of which clear the runtime mark without changing the user's `enabled` flag. When a pool has no usable key and no eligible probe, the provider is treated as unavailable: selection skips it without touching its mapping rows or counters and the request continues through the existing fallback or the standard `all_providers_unavailable` path. An empty key list is allowed and leaves the provider unserviceable on the same terms: it has nothing to select or probe, so it is skipped and never attempted with an empty credential, and no error loop can occur.

The provider upsert preserves runtime state by key id, keeps the stored value for a blank edit, clears runtime state when the value changes and preserves it on rename, reorder, enable or disable; blank names and blank new values are rejected, while an empty list is accepted. Error sanitization covers every non-blank value of the pool.

## Alternatives considered

- Spread traffic round-robin or least-recently-used across the pool: declined because list order is the user's priority; a request must stay on the highest-priority working key, and failure history must not silently rewrite the order.
- Promote a lower-priority key to the front when a higher-priority one is marked: declined because it would make the pool's behavior depend on failure history and hide the user-visible priority; sticky order relies on manual re-enable and the quota probe instead.
- Probe a marked key while an unmarked usable key still exists: declined because a probe is a recovery fallback, not a health check; probing during normal service would spend requests on a key that must not carry traffic and would blur the priority contract.
- Probe auth-marked keys like quota-marked ones: declined because a rejected credential cannot recover without operator action; probing it would add latency and log noise and would repeat a known-invalid credential against the upstream.
- Keep the mapping-row 401/403 immediate disable and the quota-429 mapping-health count: declined because the failure belongs to the credential, not the model; key-scoped settlement keeps mapping health meaning model availability and lets the same request continue on a valid key.
- Test auth keys in the background and re-enable them automatically: declined because it would put unrequested traffic on upstream accounts and there is no basis to assume a revoked credential became valid.

## Consequences

- Rotation is bounded: one request tries at most the usable keys plus one probe, pays no backoff for a key-scoped failure, never consumes the retry budget and never contaminates mapping health, usage statistics or terminal sync.
- Auth and quota marks persist and survive restart; an auth-marked key stays out until the user re-enables it or edits its value, and a quota-marked key returns after its 60-second cooldown or through the manual re-enable. The upsert preserves runtime state for an unchanged id and starts a new or revalued key healthy.
- The provider card summarizes key names and states, and the dialog editor adds, renames, revalues, deletes, reorders, enables, disables and manually re-enables keys, with blank edits keeping the stored value and value edits clearing runtime state.
- Error sanitization covers every non-blank pool key value, and the whole pool's values stay out of logs, errors and terminal configuration.
- Verification: behavior tests cover ordered selection, 401/403 and quota rotation with untouched mapping health, transient non-rotation, cooldown boundaries and probe selection, provider skip (including an empty pool, which is unserviceable and never attempted without an error loop), upsert preservation and whole-pool redaction; the frontend covers the editor, the card summary and bilingual copy.
