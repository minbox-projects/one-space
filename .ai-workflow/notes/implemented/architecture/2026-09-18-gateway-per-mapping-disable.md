# Agent Note: Gateway Per-Model Mapping Disable Is an Explicit Exclusion

Status: implemented

English | [中文](2026-09-18-gateway-per-mapping-disable.zh.md)

## Problem

Upstream providers could previously be turned on or off only as a whole, so an operator who wanted the gateway to stop serving one local model had to delete that mapping row or disable the entire provider. Deleting the row discards the remote model name, the row protocol and the display name, and an unmapped local model then falls back to the provider's `default_model`, which silently reroutes it instead of refusing it. Disabling the provider takes every other model of that provider offline, and re-enabling it would have to guess the mapping states it had. Neither expresses "this provider explicitly does not offer this one model while it keeps serving the others", and a state inferred from row deletion cannot be carried across a provider disable/re-enable cycle.

## Decision

`ModelMapping` gains a persisted boolean `enabled` with `#[serde(default = "default_true")]`: an absent field means enabled, the value is always serialized so the user's per-row intent survives a config round trip, and a legacy `api_fusion.json` needs no migration. `selection::resolve_model_for_protocol` skips disabled rows while matching, so a disabled row never serves, never produces a `ProtocolMismatch`, and its `upstream_model` is never forwarded. When the requested local model matches only disabled rows for a provider, resolution returns `NoMatch` before the `default_model` fallback, so that provider is not a candidate and is never contacted; a per-model disable is an explicit exclusion rather than an absence. A local model matched by an enabled row under another protocol keeps the existing `ProtocolMismatch` no-fallback rule, and a local model that matches no mapping at all keeps the existing `default_model` fallback when the provider protocol matches. `storage::normalize_config` still keeps non-empty disabled rows, so a disabled mapping survives a save and reload instead of being pruned.

The same enabled predicate is applied everywhere a mapping is exposed: `runtime_http::local_model_names` for `GET /v1/models`, `aggregateModels` and the `Model list` tab (`ModelListPanel.tsx`, which the `Aggregated models` metric card selects on click) in the frontend, and `build_gateway_provider` for terminal sync. A provider contributes only while `enabled`, and a row only while `enabled && !auto_disabled`: no provider-level runtime field exists in the type, and a row's own automatic disabling is settled by the mapping runtime state described in [Gateway Per-Model Auto-Disable Settles Health on the Mapping Row](2026-09-20-gateway-per-model-auto-disable.md); the version-gated migration clears the legacy provider-level keys once ([Gateway Migration Is Permanent and Version-Gated](2026-09-24-version-gated-gateway-migration.md)). For `opencode`, only enabled, not auto-disabled mappings are written to `tool_config.models`; for `codex`, `model` is the first non-empty enabled, not auto-disabled mapping `local_model` and falls back to the first non-empty `default_model` only when no such mapping exists.

The mapping-level `enabled` is independent of the provider-level `enabled` and of the row's runtime state. `selection::set_user_enabled` stays provider-only and `selection::manual_reenable` clears only row runtime state — every auto-disabled row's runtime state — so disabling or re-enabling a provider, or clearing an auto-disabled state, never changes any mapping's `enabled` intent; a mapping the user disabled is restored only by an explicit action on that mapping. In the frontend, `ProviderDetailDialog` gives every mapping row an enable switch that reflects and submits the stored value, and marks a user-disabled row with `data-disabled="true"` and a muted style and an auto-disabled row with `data-auto-disabled="true"`.

## Alternatives considered

- Delete the mapping row instead of adding an enable flag: declined because deletion discards the remote model, protocol and display name, and an unmapped local model then falls back to `default_model`, which reroutes it instead of refusing it.
- Disable the whole provider: declined because it takes every other model of that provider offline and cannot express a single unavailable model.
- Treat a disabled row as unmapped and let it fall back to `default_model`: declined because the point of an explicit exclusion is to refuse the local model on that provider, and a fallback would route it to the default remote model and hide the user's intent.
- Derive availability from upstream health and auto-disable individual mappings: declined at the time because a mapping's `enabled` is user intent, while automatic availability was expressed only by the provider-level `auto_disabled`. [Gateway Template Model Retirement](2026-09-20-gateway-template-model-retirement.md) later made one automatic per-mapping disable part of the template-sync contract — a sync disables the derived mapping of a model the previous template removed, writing only `false` — and [Gateway Per-Model Auto-Disable Settles Health on the Mapping Row](2026-09-20-gateway-per-model-auto-disable.md) makes upstream health the other automatic per-row disable, so this alternative no longer holds; a template sync still never enables a mapping.
- Let provider disable/re-enable reset or restore mapping states: declined because the user's per-row intent must survive the provider switch, and mixing the two levels would let a provider re-enable silently change routing.
- Store per-mapping state outside the mapping row: declined because it would need a parallel store and a second source of truth; an optional field on the existing row keeps one source of truth.

## Consequences

- A disabled mapping is excluded from candidate selection, from `GET /v1/models`, from the aggregated model view and from the terminal-sync model lists; its `upstream_model` can no longer be forwarded, and a request matching only a disabled mapping on a provider returns no candidate (`all_providers_unavailable`) instead of falling back to that provider's `default_model`.
- A request for a local model that matches no mapping still uses the provider `default_model` when the provider protocol matches, so the existing fallback is narrowed to requests that genuinely match no row.
- Older `ai_gateway.json` files deserialize with every mapping enabled and are upgraded once by the version-gated migration ([Gateway Migration Is Permanent and Version-Gated](2026-09-24-version-gated-gateway-migration.md)); the new build always serializes `enabled`, and an older build ignores the unknown field and treats every row as enabled, so rollout in either order is safe.
- Provider disable/re-enable and manual clearing of `auto_disabled` keep every mapping's state, so a user-disabled row stays disabled until the user toggles that row; the provider and mapping levels remain independent.
- `MEMORY.md` and `navigation.json` were updated in the same change for the mapping-level `enabled` semantics and the per-row toggle, and `navigation.md` was regenerated from the authoritative JSON.
- Supersession: partial supersession.
