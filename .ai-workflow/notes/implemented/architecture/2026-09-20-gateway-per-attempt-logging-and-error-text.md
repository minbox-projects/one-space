# Agent Note: Gateway Per-Attempt Request Logging and Stored Error Text

Status: implemented

English | [中文](2026-09-20-gateway-per-attempt-logging-and-error-text.zh.md)

## Problem

The request log recorded exactly one row per inbound request, taken from the gateway's final outcome, so a request that recovered after one or more provider failures left no record of which provider failed, what it returned, or which model it served. The only failure text visible to an operator was the caller-visible `all_providers_unavailable` envelope, which aggregates provider names and status-level reasons; it carries no per-provider `error.message`, and it is a response rather than a stored record. Persisting the raw upstream bodies instead would have crossed the log database's no-bodies, no-headers and no-credentials boundary.

## Decision

Every inbound request that completes as a business outcome writes one row per completed upstream attempt plus exactly one terminal row for the request. Each attempt row is bound to that attempt's provider and upstream model, and an attempt is completed once the gateway has fully determined its outcome: a non-streaming body that has been read, a non-2xx response, a response rejected for a missing or malformed SSE stream, an empty stream, a call-setup or stream failure, or a normally ended stream. Completed attempts are buffered until the inbound request outcome is known; when a later candidate succeeds or the request otherwise completes normally, the buffer preserves the per-provider failure attribution. The cancellation-specific persistence rule originally recorded here is partially superseded by [Gateway Cancelled Requests Are Not Logs](../simplification/2026-09-21-gateway-cancelled-requests-are-not-logs.md): a downstream transport cancellation or an undeliverable response discards the whole buffered set, including completed attempts.

Exactly one row per normally completed request is terminal: the successful attempt, the `ReturnToClient` attempt, the mid-stream failure attempt, the chronologically last completed attempt when every candidate is exhausted, the normal probe attempt of a zero-candidate request that had an eligible half-open probe, or the existing synthetic 502 row when no candidate can serve the request and no eligible probe exists. The exhausted non-streaming terminal row records the last observed upstream status (0 for a network failure) instead of the caller's transport 502, matching the rule the streaming path already followed; the no-candidate row keeps 502 and no caller-visible byte changes. Usage statistics (totals, time buckets, per-model and per-provider breakdowns, `unpriced_count`) aggregate terminal rows only; the per-provider breakdown additionally excludes `provider_id=''`, while a no-candidate failure still counts toward totals/models. A zero-candidate request that attempted an eligible half-open probe instead writes the probe's normal named attempt row plus its terminal row, attributed to the probed provider like any other named attempt. The ungrouped list, its `total`, its status and model filters and its in-range `local_model` facet consider all visible success/failure rows, so completed attempt rows for normally completed requests stay visible. Historical `cancelled` rows are deleted once when an older usage database first opens and the compatibility representation is removed, both under the superseding cancellation decision and the version-gated database cleanup ([Gateway Migration Is Permanent and Version-Gated](2026-09-24-version-gated-gateway-migration.md)).

A failure that reached an upstream stores readable error text in the new nullable `error_message` column: the standard JSON envelope's `error.message` when the body carries a non-empty one, otherwise a readable summary of the body produced by lossy UTF-8 decoding, HTML markup removal, whitespace collapsing and trimming. A transport or stream failure stores its description, an attempt that never reached an upstream stores `null`, and text that is empty after sanitization stores `null`. Before the insert, every non-blank key value of the provider's ordered upstream key pool is replaced verbatim with `[redacted]`, `Bearer` and `sk-` credential shapes are masked, and the text is bounded to 4096 characters truncated on a Unicode scalar boundary with `…` appended only when truncation occurred; request headers, request bodies and complete raw response bodies are never stored.

## Alternatives considered

- Keep one row per request and diagnose failures from the caller-visible `all_providers_unavailable` text: declined because that envelope aggregates provider names and status-level reasons, carries no per-provider message, and leaves a failure that another candidate recovered completely unrecorded.
- Add a request identifier and a per-request grouped view instead of per-attempt rows: declined because the flat request log is the surface an operator already reads, and an identifier plus a new grouping mode would add schema and interface surface without attributing failures to providers in the list.
- Count the attempt rows in statistics: declined because totals, buckets and breakdowns would inflate for multi-attempt requests and stop being comparable with historical data, so every aggregate and grouped view counts terminal rows only.
- Persist the complete raw upstream body or the whole error envelope: declined because the log database's boundary forbids request bodies, headers and credentials; only extracted, sanitized and bounded text may be stored.
- Backfill pre-upgrade rows with a message or a non-terminal state: declined because pre-upgrade rows carry no error text, and defaulting them to terminal with no message preserves their statistical meaning without rewriting history.
- Keep the caller-visible transport 502 as the exhausted non-streaming terminal status: declined because the log should record what the upstream actually returned, and the streaming path already recorded the last observed upstream status; the caller-visible response is unchanged by the log status either way.
- Redact and bound the text at read time instead of write time: declined because the stored row is the privacy boundary — every reader, query and future export must be safe on its own — so sanitization happens before the insert.

## Consequences

- The `usage_logs` table gains a nullable `error_message` column and a non-null `terminal` column that defaults to terminal, added by the `PRAGMA table_info`-driven idempotent migration in `src-tauri/src/api_gateway/usage_log.rs`; a pre-upgrade database keeps every row, reads it as terminal with no message, and reopening changes nothing further, so statistics over historical rows match their pre-migration numbers.
- One row per completed upstream attempt plus exactly one terminal row per normally completed request; the attempt buffer is owned by the connection handler and only borrowed by the forwarding future. A success, failure, recovered multi-attempt request or no-candidate request keeps this behavior, with the probe exception that a zero-candidate request with an eligible half-open probe writes the probe's normal attempt row plus its terminal row instead of the synthetic no-candidate row, while the superseding cancellation decision discards the entire buffer when the downstream transport closes or the response cannot be delivered.
- Usage statistics (totals, buckets, per-model and per-provider breakdowns, `unpriced_count`) count terminal rows only, with the per-provider breakdown additionally excluding `provider_id=''`; a no-candidate failure still counts toward totals/models. Request-log pages, totals, page counts, model facets, model/day groups and timestamps never include `cancelled` rows — the legacy rows are deleted once when an older database first opens — while completed attempt rows for normally completed success/failure requests remain visible; the exhausted non-streaming terminal row records the last observed upstream status (0 for a network failure) and the synthetic no-candidate row — written only when no eligible half-open probe exists — keeps 502, with no caller-visible response byte changed.
- `error_message` holds the standard `error.message` when the body is a valid JSON error envelope and otherwise a readable summary; transport and stream failures hold their description, no-upstream and empty-after-sanitization failures hold `null`, every non-blank upstream pool key value becomes `[redacted]`, `Bearer` and `sk-` credential shapes are masked, and the text is capped at 4096 characters on a Unicode scalar boundary with `…` appended only on truncation; no headers, request bodies or complete raw bodies are stored. Whole-pool scope comes from the key-pool decision recorded by [Gateway Key Pool Rotation Is Ordered, Probe-Limited and Manual-Only for Auth](2026-09-24-gateway-key-pool-rotation.md).
- `UsageLogStore::append_batch` writes a request's rows through one connection plus the retention cleanup, `append` remains the single-row path, and a migration or log-write failure stays a swallowed `log::warn!` that a later open retries rather than affecting the response.
- The request-log record exposes optional `error_message` and `terminal` fields with serde defaults; the ungrouped list shows a visible failure row's stored message as a single truncated reason line whose hover and keyboard-focus tooltip reveals the complete message with HTTP status context, keeps the generic status-code reason when no message exists, shows nothing for success rows, and marks non-terminal rows with a lightweight attempt label, in Chinese and English alike. No `cancelled` representation remains in the record type, and the legacy rows are deleted once when an older database first opens, under the superseding cancellation decision.
- Partial supersession: [API Gateway Usage Stats and Request Logs](2026-09-17-ai-gateway-usage-logs.md) is retained and cross-linked by this record, which replaces only its one-row-per-request recording granularity and its absence of stored error text; the SQLite logging, record-time price freeze, retention, `group_by` contract and model-facet decisions still stand, while its `unpriced_count` eligibility is partially superseded by [Gateway Unpriced Hint Counts Only Billable Usage](../bug-fix/2026-09-21-gateway-unpriced-billable-usage.md).
- Partial supersession: [Gateway Single-Candidate Fast Fail and Standard Error Responses](2026-09-18-gateway-fast-fail-and-standard-errors.md) is retained and cross-linked by this record, which replaces only the statement that the request-log failure-status semantics stayed unchanged — the exhausted non-streaming terminal row now records the last observed upstream status like the streaming path — while its no-candidate 502 rule, fallback-first scheduling and standard error-envelope decisions still stand.
- Partial supersession: [Gateway Cancelled Requests Are Not Logs](../simplification/2026-09-21-gateway-cancelled-requests-are-not-logs.md) replaces only this record's cancellation behavior: completed attempts are no longer retained and no synthetic terminal row is written when the downstream transport closes or a response cannot be delivered; historical `cancelled` rows are deleted once when an older database first opens and the compatibility representation is removed ([Gateway Migration Is Permanent and Version-Gated](2026-09-24-version-gated-gateway-migration.md)). Per-attempt logging for normally completed success, failure, recovered and no-candidate requests, stored error text, migration defaults and privacy boundaries still stand.
- Partial supersession: [Gateway Auto-Disable Recovery Uses a Cooldown Half-Open Probe, a Post-Resume Transport Grace and a Transition Broadcast](2026-09-23-gateway-auto-disable-recovery.md) replaces only this record's statement that a request which cannot be served by any candidate always writes the synthetic no-candidate row; a zero-candidate request with an eligible half-open probe writes a normal probe attempt row plus its terminal row instead. Per-attempt granularity, terminal-row-only statistics, stored error text, migration defaults and privacy boundaries still stand.
- `MEMORY.md` describes this granularity, the terminal-only statistics rule, the terminal-row status rule, the migrated columns and the error-text privacy boundary in the same change; the request-log record gained optional `error_message` and `terminal` fields, and the navigation index was synced for the delivered backend log behavior with `navigation.md` regenerated from it, while no new index symbol name or file path was added.
