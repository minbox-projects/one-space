# Agent Note: Provider Templates Own Closed Strategies and Bind Providers by Template Id

Status: implemented

English | [中文](2026-10-10-provider-template-bound-strategies.zh.md)

## Problem

The AI Gateway selected provider-specific integration behavior from mutable endpoint strings: a CommandCode-looking `base_url` gained the CommandCode quota card and a Go-looking URL gained the Go usage block, independent of how the provider was actually configured. That coupling could not express per-template behavior, granted special integration to any provider whose URL happened to match, and offered no way to distinguish an unbound provider from a bound one. The built-in catalog was also centered on an OpenCode Zen template whose model list carried no per-model protocol, so the value the sync could route was undefined. Existing Zen providers additionally needed a one-time, data-preserving transition to OpenCode Go that would never rewrite a provider merely because its URL resembled Zen.

## Decision

- Template strategy fields: `ProviderTemplate` carries the closed policy fields `sync_strategy` (`generic` | `opencode_go`), `quota_strategy` (`none` | `commandcode` | `opencode_go`) and `error_strategy` (`generic`), typed by `SyncStrategy`, `QuotaStrategy` and `ErrorStrategy` in `types_config.rs` and each `#[serde(default)]`. `parse_template_snapshot` reads them tolerantly: a missing or unknown stored value resolves to `generic`, `none` or `generic`, while a newly saved invalid value is rejected without changing the configuration.
- Built-in catalog: `provider_templates.json` ships exactly `commandcode` (empty `models`, model-list URL `https://api.commandcode.ai/provider/v1/models`, `sync_strategy = generic`, `quota_strategy = commandcode`) and `opencode-go` (base URL `https://opencode.ai/zen/go/v1`, model-list URL `https://opencode.ai/zen/go/v1/models`, `sync_strategy = opencode_go`, `quota_strategy = opencode_go`). No `opencode-zen` built-in remains.
- Go declaration baseline: the OpenCode Go template declares exactly 20 Chat Completions model ids and six Responses model ids. `parse_model_list_source` is declaration-aware for a `SyncStrategy::OpencodeGo` template: after parsing the source it keeps only ids the effective template declares as Chat Completions or Responses, or ids the source itself declares with a supported endpoint, and rewrites a declared id's protocol to the declaration; a source-declared `/messages` or `/v1/messages` id is now recognized as Anthropic Messages, while an undeclared or metadata-less id is never added and never guessed as Chat. A `generic` template keeps the existing protocol-inheritance parsing.
- Binding and effective-policy resolution: `ai_gateway_upsert_provider` already carries `template_id: Option<String>`, so no new binding command exists. A submitted unknown or deleted id is rejected before anything is staged, `None` unbinds, and the value resolves through `effective_template` (persisted template state first, then the built-in snapshot, with an error for an unknown or deleted id), `effective_provider_template` (returns `None` for an unbound or broken binding) and `effective_quota_strategy` (defaults to `none`). Resolution reads only `template_id`; URL, name and icon are never consulted.
- Policy-based monitor dispatch: `resolve_quota_request` accepts only a provider whose effective quota strategy is `commandcode` and `resolve_go_usage_request` only `opencode_go`; each rejects a mismatch before it reads a key or the base URL, so no upstream fetch can happen. The fixed endpoints, pinned source key, five-minute per-provider caches, forced refresh, source-key and base-URL invalidation and the read-only boundary are unchanged, and a policy or binding change cannot reuse an incompatible cached snapshot because the strategy guard rejects the request before the cache is read.
- Schema 3 migration: `GATEWAY_CONFIG_SCHEMA_VERSION` advances to 3. The version-gated `migrate_legacy_config` first runs an idempotent raw-JSON `opencode-zen` → `opencode-go` transform driven only by a persisted `template_id`: template ids and bound providers move to `opencode-go` and the Go base URL, the persisted template snapshot and `source` become the Go baseline, `synced_at` is cleared, provider account and user-maintained data (name, keys, enabled state, weight, tags, icon, price rows, explicit protocols) is preserved, legacy mappings not declared as Go Chat/Responses are set disabled and appended once to `ignored_models`, an unsupported `default_model` is cleared, and a supported Responses mapping that inherited the old provider default gains an explicit Responses protocol. A provider whose URL merely resembles Zen is never migrated, an existing Go template state drops the stale Zen duplicate deterministically, a failed rewrite keeps the old complete bytes for the next read to retry, and a future version is read without downgrade.

## Alternatives considered

- Keep the URL/name heuristic for quota and Go dispatch: declined because it grants special integration to any provider whose endpoint string happens to match, cannot distinguish an unbound provider from a bound one and breaks when an endpoint moves; an explicit template policy is stable and visible.
- Add per-provider strategy overrides or a new binding command: declined because the template or the generic fallback is the single strategy source and the existing provider upsert already carries the binding field.
- Ship a curated OpenCode Go catalog with prices and reasoning efforts: declined for the same reason the earlier template catalog was removed — prices and reasoning efforts are account-specific and maintained on the mapping row; the Go template ships only the protocol declarations that decide which synchronizable ids are routable.
- Infer a protocol for undeclared ids or reuse the Zen `/zen/v1/models` endpoint: declined because the Go model list carries no per-model protocol and the Zen endpoint is a different product surface; only explicit Chat/Responses declarations are authoritative.
- Migrate every provider whose URL resembles Zen: declined because URL resemblance is not a binding; only a persisted `opencode-zen` `template_id` triggers migration, so user-configured providers are never silently rewritten.
- Drop a failing migration rewrite instead of retaining the old bytes: declined because a failed rewrite must not expose partial state; the migration keeps the previous complete bytes and the next read retries.

## Consequences

- Provider integration resolves from `template_id` alone: a bound provider follows its template policy, an unbound or broken binding uses the generic fallback (`generic`/`none`/`generic`), and no provider gains CommandCode quota or OpenCode Go usage from its URL. A broken binding routes generically, the UI shows the missing target and a direct monitor command rejects the mismatch before fetching.
- The built-in catalog is exactly CommandCode and OpenCode Go; the Go template's 20 Chat and six Responses declarations decide the routable Go model set while a generic template keeps the existing protocol-inheritance sync, and a source-declared `/messages` id is now admitted as an Anthropic Messages mapping rather than remaining non-routable.
- Quota and Go usage stay read-only, five-minute cached per provider, force-refreshable and invalidated by a changed source key or base URL; a policy or binding change cannot reuse an incompatible snapshot, and a monitor query never mutates provider health, configuration, usage logs or terminal sync.
- The schema-3 migration preserves provider account and user-maintained data while quarantining unsupported legacy mappings as disabled `ignored_models`, clears an unsupported default, and is idempotent; a second read is byte-stable, a failed rewrite keeps the old bytes for retry, and a future version is read without downgrade.
- Rollback: reverting the product code does not reverse a persisted schema-3 identity migration. To run an older build that still needs the OpenCode Zen identity, restore the pre-migration encrypted `ai_gateway.json` backup for the same profile and verify the old template id, base URL, mappings and prices; a binary revert alone leaves the persisted `opencode-go` identity in place.
- Supersession: partial supersession of six records. This record replaces the URL-based quota dispatch of [CommandCode Provider Cards Show Account Quota](../feature/2026-09-23-commandcode-provider-quota.md) and [OpenCode Go Provider Cards Show Usage](../feature/2026-09-24-opencode-go-provider-usage.md) and the URL-based bulk-refresh eligibility of [Upstream Provider List Bulk-Refreshes Quota for the Current Filter Results](../feature/2026-09-28-provider-quota-bulk-refresh.md); it replaces the built-in `opencode-zen` catalog and adds the closed policy fields, binding validation and effective-policy resolution to [API Gateway Provider Templates and Incremental Model Sync](2026-09-18-api-gateway-provider-templates.md) and [Provider Templates Drop Built-in Model Catalogs and Prices](2026-09-19-provider-template-manual-model-sync.md); and it advances [Gateway Migration Is Permanent and Version-Gated](2026-09-24-version-gated-gateway-migration.md) from schema 2 to schema 3 with the Zen-to-Go transform. Each source record keeps its endpoint, cache, read-only boundary, naming and structure decisions, and the declaration-aware Go sync replaces the empty-catalog assumption only for the Go template.
- Supersession update: [Native Anthropic Messages Entry, Protocol Recognition and OpenAI Entry Conversion](2026-10-11-ai-gateway-anthropic-messages.md) partially supersedes this record's Go declaration baseline and endpoint-recognition boundary: a source-declared Messages endpoint now enters the compatible set as Anthropic Messages and its Anthropic Messages mapping is servable through the existing OpenAI entries by conversion, while the closed strategy fields, binding validation, effective-policy resolution and schema-3 migration decisions remain in force.
