# Agent Note: Native Anthropic Messages Entry, Protocol Recognition and OpenAI Entry Conversion

Status: implemented

English | [中文](2026-10-11-ai-gateway-anthropic-messages.zh.md)

## Problem

The AI Gateway relayed only the OpenAI-compatible `/v1/chat/completions` and `/v1/responses` entries. A provider's persisted `protocol` knew only `chat_completions` and `responses`, the model-list source parser dropped any entry whose declared `supported_endpoints` named neither Chat Completions nor Responses, and the loopback server answered `/v1/messages` as an unknown path. A Messages-only upstream could therefore be neither configured nor called natively, and Claude Code, which speaks the native Messages protocol, had no entry through the gateway. Once such an upstream was configurable, the existing OpenAI entries still could not reach it: candidate resolution excluded an Anthropic mapping from Chat and Responses requests and no request, response or stream conversion existed, so a caller speaking Chat Completions or Responses could not use a model the gateway could serve only over Messages. Terminal sync and the configure/sync commands supported only `opencode` and `codex`, deliberately leaving `claude` records untouched, and there was nowhere to persist the operator's four model choices (the default model plus the haiku/sonnet/opus family aliases). The Claude tool's native Anthropic base URL is the bare loopback origin, not the OpenAI tools' `/v1` base URL, so reusing the existing base URL would append a second `/v1`. The existing provider upsert replaces the whole record, so a later sync that omitted choices would silently clear them, and a fixed profile code or an unmarked user record could collide with or overwrite the user's own Claude configuration.

## Decision

- Persisted protocol: `UpstreamProtocol::AnthropicMessages` is added in `src-tauri/src/ai_gateway/types_config.rs` and serialized as `anthropic_messages`; it is accepted at the provider default, at each mapping row, and at the template default and each template model, and `endpoint_path()` returns `/messages`. The exhaustive protocol matches in `src-tauri/src/ai_gateway/migration.rs` handle the new variant as compatibility plumbing; the configuration schema stays 3 and no migration is introduced.
- Source recognition: `src-tauri/src/ai_gateway/templates.rs` recognizes `/messages` and `/v1/messages` in a declared `supported_endpoints` under the Chat Completions > Responses > Messages preference; an entry declaring none of the three is dropped, and an entry without endpoint information keeps no protocol and inherits the template. Generic inheritance and the Go declaration-aware path are preserved, a source-declared Messages endpoint now enters the compatible set, and disabled/ignored state and atomic synchronization are unchanged.
- Route modules: `src-tauri/src/ai_gateway/anthropic.rs` provides the native helpers `is_messages_path`, `DEFAULT_ANTHROPIC_VERSION` (`2023-06-01`), the Anthropic `error_payload` and the `stream_error_event` fragment, plus the conversion entry points `is_conversion_path`, `convert_request`, `convert_response` and `validate_conversion_request`; `src-tauri/src/ai_gateway/anthropic_sse.rs` provides the read-only `AnthropicSseObserver` and the `AnthropicSseConverter`.
- Native entry: `src-tauri/src/ai_gateway/runtime_http.rs` serves `POST /v1/messages` including query strings such as `?beta=true` (`/messages` is tolerated), authenticates locally with an `Authorization: Bearer` or `x-api-key` local key, answers gateway-generated errors with the Anthropic error envelope/event, substitutes only the mapped model, sends the selected upstream pool key as `x-api-key`, passes `anthropic-beta` and `anthropic-version` through, and supplies `anthropic-version: 2023-06-01` only when the caller omits it.
- Request conversion: an enabled `anthropic_messages` mapping (or Anthropic default) now serves Chat and Responses callers. `convert_request` translates `system`/`developer` messages and Responses `instructions` into the Messages `system` field, text and URL/base64 `image_url`/`input_image` content into text/image blocks, `user`/`assistant` turns, client function-tool schemas into `tools` with `input_schema`, assistant `tool_calls` and Responses `function_call` into `tool_use`, and `tool`/`function_call_output` results into `tool_result`, preserving tool ids and multi-turn continuity. `tool_choice` maps `auto`/`required`/`none`/`function` to the Messages equivalents, `parallel_tool_calls: false` adds `disable_parallel_tool_use`, `temperature`/`top_p` pass through, and Chat `stop` becomes `stop_sequences`. For Chat, `max_completion_tokens` precedes `max_tokens`; Responses uses `max_output_tokens`; an omitted cap defaults to 4096; an explicit zero or positive integer is preserved, and a negative, fractional or string cap is rejected with a field-specific 400 before any Anthropic attempt. Native requests never receive this conversion default.
- Unsupported conversion: `previous_response_id`, an unresolved item reference, `background: true`, `store: true`, `n > 1`, a non-null `response_format` (JSON/schema output) and a nonempty untranslatable reasoning option are rejected field-specifically with a 400 before an Anthropic HTTP or key-health attempt, and `runtime_http.rs` runs this validation before the attempt when any candidate resolves to `anthropic_messages`. A same-protocol OpenAI request that carries those fields keeps its existing passthrough behavior and is never rejected by the converter.
- Response conversion: `convert_response` turns an Anthropic JSON body into the caller format, identifying the local model: text blocks become Chat message content and Responses `output_text`, `tool_use` blocks become Chat `tool_calls` and Responses `function_call` items with string-form arguments, and completion reasons and usage are translated; an upstream 2xx body that cannot be converted becomes a caller-format 502 `conversion_error` instead of raw Anthropic bytes.
- Streaming conversion: `AnthropicSseConverter` incrementally converts fragmented Anthropic SSE into caller events with stable text and tool identities and ordered argument deltas: `message_start` captures the message id and merges usage without emitting a delta, `content_block_start`/`input_json_delta` emit Chat tool-call chunks or Responses `response.output_item.added`/`response.function_call_arguments.delta`, text deltas emit Chat content or Responses `response.output_text.delta`, and `message_stop` emits one Chat `[DONE]` or a Responses `response.completed`. Native-only events such as pings fabricate no content. `AnthropicSseObserver` reads the forwarded native bytes only, merging `message_start.message.usage` with cumulative `message_delta.usage` field-wise (a present value replaces, an omitted value is retained); a native or converted stream succeeds only after `message_stop`, and an in-band `error` event is never a success.
- Failure and lifecycle: a post-first-byte error, EOF or missing `message_stop` ends the converted stream with a caller-format error and no successful completion marker or replay, while a native stream keeps its native error format; usage captured before the failure is preserved in the failed attempt. The existing first-client-byte retry boundary, downstream cancellation (which discards the buffered rows and does not settle upstream health), idle-read timeout, key rotation, probing and health settlement are unchanged.
- Conversion-aware resolution and accounting: `src-tauri/src/ai_gateway/selection.rs` resolves a candidate when its effective protocol equals the inbound protocol, or when it is `anthropic_messages` and the inbound protocol is Chat Completions or Responses. Native Messages therefore never selects a Chat or Responses upstream, Chat-only and Responses-only upstreams stay mutually exclusive without an Anthropic adapter, and disabled rows, auto-disabled rows, defaults, weighted scheduling, session affinity and key/retry policy keep their existing behavior. Usage is taken from the actual upstream before conversion: the field-wise Anthropic merge normalizes to the existing four tiers, so a converted Chat response reports an inclusive input (ordinary plus cache read plus cache write, matching the OpenAI shape) while the persisted ordinary upstream input stays distinct.
- Claude target and DTO: `claude` joins the existing `ai_gateway_configure_terminal` and `ai_gateway_sync_terminal` commands, which gain the optional `claude_models: Option<ClaudeModelSelection>` argument. `ClaudeModelSelection` (`src-tauri/src/ai_gateway/types_config.rs`) carries the four explicit local mapping ids `{ default_model, haiku, sonnet, opus }`, each a local id (never a vendor name guessed from a model), and the same id may fill several slots. The same struct is serialized on the model-only `TerminalTarget.claude_models` snapshot and never carries a credential value.
- Validation and atomicity: `validate_claude_selection` in `src-tauri/src/ai_gateway/commands.rs` requires all four choices to be non-blank, enabled and servable as a native Anthropic Messages local mapping (an Anthropic mapping row or provider default resolved through the same authoritative `selection::resolve_model_for_protocol` the request path uses). A missing initial selection, an invalid choice or no usable local key is rejected before any Claude provider, ledger or projection write, and every payload of the batch is built before the first upsert, so a rejection leaves no partially upserted batch behind.
- Persistence and ownership: the four choices persist only in the gateway-owned canonical Claude service provider's top-level `model` and `claude_model_mappings` (the `haiku`/`sonnet`/`opus` rows' `upstream_model`), and a later sync reads the complete saved selection back from that owned record and resends it whole, so the existing replace-style upsert cannot clear omitted choices. The pipeline reuses only the same-tool, same-profile marked gateway record; `code` is derived from the new provider UUID on first creation and reused verbatim afterwards, so a fixed-name collision or the user's own unmarked provider is never claimed or overwritten, and the opposite profile's records are unaffected.
- Origin, variables and reuse: `src-tauri/src/ai_gateway/storage.rs` adds `local_origin(port)`, the bare loopback origin `http://127.0.0.1:<port>` without `/v1`. The Claude provider uses that origin as its `base_url` and writes `claude_api_format = "anthropic_messages"`, `claude_connection_mode = "native_anthropic"` and `claude_auth_env_key = "ANTHROPIC_API_KEY"`, reusing the existing upsert, per-profile activation and Claude projection. A manual sync activates and projects Claude on success; because upsert, activation and projection are not one transaction, a later projection failure is surfaced rather than reported as a successful application.
- Target, pending and fan-out: `TerminalTarget` gains the optional model-only `claude_models` snapshot (no credentials); a Claude target's `pending_sync` compares the ledger's key id and the bare origin and treats an unreadable or incomplete selection as drifted, so a current address, key and selection is not pending. A previously synchronized Claude record participates in the existing best-effort post-template refresh fan-out (`previously_synced_terminal_tools` order `opencode`, `codex`, `claude`); an invalid or missing selection skips that automatic Claude write without prompting, replacing or clearing the saved choices, and the template sync result still stands.
- OpenCode adapter precedence: OpenCode keeps its existing Chat adapter whenever any enabled gateway can serve the local model over Chat Completions or Anthropic Messages, including a source that is both Responses- and Anthropic-servable; only a genuinely Responses-only local model receives the `@ai-sdk/openai` npm override. Codex configuration, identity and manual activation are unchanged.

## Alternatives considered

- Keep an OpenAI-only protocol enum and give the Messages entry its own separate configuration: declined because the provider default and the mapping row already express the effective protocol, and a parallel configuration surface would duplicate template binding, key pools and selection.
- Build the native entry and the OpenAI-entry conversion as one undifferentiated step: declined because the native entry and protocol recognition are independently verifiable and the conversion depends on their selection and runtime plumbing already being in place.
- Convert Chat Completions directly to Responses or the reverse, synthesize multiple generated choices, add server-side Responses conversation/retrieval/background storage, or guess structured-output and reasoning-parameter equivalents: declined because these are not the caller's requested protocol and would invent semantics the upstream may not support; unsupported critical fields are rejected field-specifically instead.
- Repair or silently reinterpret unsupported conversion input instead of rejecting it: declined because sending a malformed or downgraded request would misrepresent the caller's intent; a field-specific 400 before any attempt is explicit and safe.
- Make the conversion output cap unbounded or inherit an arbitrary upstream default: declined because an omitted cap needs a deterministic, documented bound; the fixed 4096 default is applied only to converted requests.
- Rewrite or normalize native stream bytes, or inject an OpenAI terminator into a native stream: declined because native callers and this gateway are byte-faithful relays, and injecting `[DONE]` or rewriting events would corrupt the Messages protocol.
- Give Claude a separate synchronization path with its own storage instead of extending the existing configure/sync commands and canonical provider: declined because it would duplicate upsert, activation, projection and marker ownership, while the existing commands already express a per-tool target.
- Store the four choices only on the terminal target or a new side ledger instead of the owned canonical Claude provider: declined because the canonical provider is the single source the existing projectors already read, and a parallel store would desynchronize from the projected `ANTHROPIC_MODEL` and family variables.
- Derive a fixed Claude profile code or reuse any same-tool record: declined because a fixed code collides across installs and an unmarked record is the user's own configuration; a UUID-derived code reused only on the owned marked record keeps re-sync idempotent without claiming user data.
- Append `/v1` to the OpenAI base URL for Claude instead of using the bare origin: declined because Claude's native Anthropic base URL is the origin and the gateway already tolerates a missing `/v1`; a second `/v1` would produce a duplicate version segment.
- Silently clear or substitute a Claude choice when a model becomes unavailable: declined because erasing the operator's explicit choice is destructive; an automatic refresh skips the Claude write and a manual sync requests a replacement.
- Require the four choices to be distinct ids: declined because the operator may deliberately point several family aliases at one model; only blank, disabled or unservable ids are rejected.

## Consequences

- A provider default or mapping row can persist `anthropic_messages` and serve it both through the native `POST /v1/messages` entry and, via conversion, through the existing `/v1/chat/completions` and `/v1/responses` entries with the caller's requested model identity; a native Messages request still selects only an Anthropic upstream.
- Request, JSON response and SSE conversion cover system/developer/instructions, text and URL/base64 images, function-tool schema, calls and results, tool choice, parallel controls, sampling/stop options and output caps, with ordered incremental caller events; caps obey the specified precedence (Chat `max_completion_tokens` over `max_tokens`, Responses `max_output_tokens`, default 4096) and invalid caps plus unsupported critical semantics fail field-specifically before any Anthropic attempt.
- Streaming stays incremental with stable identities and ordering: Chat ends once with `[DONE]`, Responses carries its own tool and completion events, ping-only input fabricates no content, and a post-byte error, EOF or missing `message_stop` produces a caller-format failure with no successful marker or replay while preserving captured usage.
- Conversion-aware resolution preserves every runtime boundary: attempts and probes carry the actual effective upstream protocol, weighted scheduling stays ingress-scoped, exclusions, default blocking and key/retry policy hold, native Messages never selects an OpenAI upstream, and Chat-only and Responses-only upstreams remain mutually exclusive.
- Accounting stays actual: the field-wise `message_start`/`message_delta` merge normalizes to the existing four tiers, and a converted Chat response's inclusive input can differ from the persisted ordinary upstream input while attempts, pricing and provider identity stay the upstream's.
- Compatibility and boundary: the configuration schema stays 3 with no new migration, a same-protocol OpenAI payload keeps its existing behavior apart from the existing model rewriting, and no Chat-to-Responses conversion, multiple choices, server-side Responses storage, structured-output/reasoning inference or curated model/price list is added. This change delivers Step 3's Claude terminal synchronization (target, DTO, commands, validation, persistence, ownership, origin and fan-out); the four UI selectors and the Claude selection dialog (Step 4) and any curated model/price list are not delivered.
- Claude terminal sync: a first manual sync with four valid choices persists them in the owned canonical provider and activates/projects Claude; later syncs reuse them, an invalid automatic refresh skips the Claude write without replacement, and a manual sync can request a replacement, while the user's unmarked provider or the opposite profile is never overwritten.
- `MEMORY.md`, the authoritative `ai-gateway-backend` navigation entry and the regenerated `navigation.md` describe the new modules, symbols, tests and behavior in the same change.
- Partial supersession: [API Gateway Provider Templates and Incremental Model Sync](2026-09-18-api-gateway-provider-templates.md) keeps its incremental merge, ignored-model lifecycle and naming decisions while its endpoint filtering and recognition gain Messages and its recognized Messages mappings are now servable through the existing OpenAI entries by conversion; [Provider Templates Own Closed Strategies and Bind Providers by Template Id](2026-10-10-provider-template-bound-strategies.md) keeps its closed strategy fields, binding validation and effective-policy resolution while its Go declaration baseline admits a source-declared Messages id that conversion can now serve through the OpenAI entries; [API Gateway Cache Hit Rate Normalizes Provider Usage Semantics](../bug-fix/2026-09-21-api-gateway-cache-hit-accounting.md) keeps its four-tier normalization, storage migration, eligibility predicate and coverage contract while native and converted Messages usage is observed by a separate field-wise merge and a converted caller's inclusive input stays distinct from the persisted ordinary tier; [OpenCode Responses-Only Models Carry the @ai-sdk/openai npm Override](../bug-fix/2026-09-28-opencode-responses-npm.md) keeps its per-model npm override, its all-enabled-gateways evaluation and its rollback decision while its "the gateway does no request-body conversion" boundary and its per-model servability now account for Chat/Responses-to-Messages conversion and for Anthropic Messages as a chat-servable source, so the override is reserved for a genuinely Responses-only model; [API Fusion Terminal Sync Writes an Independent Gateway Provider](../feature/2026-09-17-api-fusion-terminal-independent-provider.md) keeps its independent-provider, ledger-reuse and marker-ownership decisions while `claude` becomes a third supported terminal target with its own model choices, bare origin and activation/projection, narrowing its earlier statement that `claude` records are untouched.
