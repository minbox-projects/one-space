# Agent Note: Gateway Key Health Rotates Bare 429s, Recovers Quota Marks after a TTL, Retries a Single Candidate and Pins the Query Source Key

Status: implemented

English | [中文](2026-09-25-gateway-key-health-lifecycle.zh.md)

## Problem

The ordered key pool marked only 401/403 keys as `authentication` and quota-classified 429 keys as `quota`, and every other failure either failed over to another provider or ended the attempt. A plain rate-limit 429 that the quota-message classifier does not classify as quota exhaustion was therefore treated like any transient failure: the request did not use the provider's next usable key even though the attempted key might recover immediately. A quota-marked key stayed out of service until the all-marked 60-second probe or an operator action, although upstream quota windows reset on their own. A request with exactly one serviceable candidate failed immediately on a transient 500 or network error without any retry on that provider. And the read-only quota and usage queries pinned the first enabled key even when the gateway had runtime-marked it, so a card could query the account with a key that was already out of service.

## Decision

An attempt result now distinguishes a persistent key-scoped failure from a bare rate-limit 429. `key_failure_kind` still classifies 401/403 as `authentication` and a quota-exhausted 429 as `quota`, and those marks persist exactly as before; a 429 that the quota-message classifier does not classify sets `bare_rotation` and persists nothing. `select_usable_key(provider, now, attempted)` returns the first enabled key, in list order, that the current pass has not attempted and that is either unmarked or carries a TTL-expired quota mark, and each pass tracks its `attempted_keys` set, so bare-429 rotation tries each usable key at most once. A bare 429 never marks the key, never registers mapping health and never consumes the retry budget for the rotation itself: the request continues on the next unattempted usable key, and when the pass runs out of usable keys the remembered failure enters the existing bounded retry schedule with its full budget intact — one initial attempt plus up to `MAX_RETRIES_PER_PROVIDER` (5) retries per provider, each retry a fresh pass that restarts from the first usable key with a cleared attempted set. Streaming rotates only before the first forwarded byte, and a post-first-byte failure keeps the truncation path. Network errors, 5xx, 404 and other 4xx failures still mark nothing and rotate nothing.

`types_config::KEY_QUOTA_MARK_TTL_SECS = 1800` gives a quota-marked key a lazy recovery path. `selection::quota_mark_expired(key, now)` is true only for a quota mark (`auto_marked` with `failure_kind == Quota`) that has a `marked_at` and whose age is at least the TTL — inclusive at exactly 1800 seconds and exclusive below it. Normal list-order selection may pick such a key; selecting it clears its runtime state in memory and persists the clear through the serialized configuration write, so it serves by list priority. If it is still exhausted, the attempt re-marks it as quota and the same request continues on the next usable key. Auth marks and quota marks without a marking time never expire through this TTL, and the existing all-marked 60-second single-probe rule (`KEY_PROBE_COOLDOWN_SECS = 60`) is unchanged for marks that are not TTL-expired.

The candidate-count gate is removed from both attempt paths. A retryable pre-first-byte failure — an upstream 500, a network error or another retryable class — queues for the bounded retry schedule even when the request has exactly one serviceable candidate, subject to the existing per-provider retry cap, exponential backoff with jitter, `Retry-After` priority and the 120-second wait budget; `attempt_non_streaming` and `attempt_streaming` both enqueue while `candidate.attempts <= MAX_RETRIES_PER_PROVIDER`. A streaming failure after the first forwarded byte keeps the existing truncation path with no retry, and non-retryable classes keep their existing skip or return-to-client behavior. Multi-candidate scheduling — the fallback-first pass, earliest-deadline serial retries and the same cap, backoff, `Retry-After` priority and budget — is unchanged.

`selection::pinned_key_value` now resolves the read-only query source as the first enabled unmarked key in list order, then the first enabled key when every enabled key is marked, then the first stored key when no key is enabled. An empty pool still yields no pinned key, and both `resolve_quota_request` and `resolve_go_usage_request` keep the existing no-key error. CommandCode quota and OpenCode Go usage use this rule, and their existing invalidation on a source-value or base-URL change is unchanged.

## Alternatives considered

- Persist a key mark or a cooldown for a bare 429: declined because a bare rate-limit 429 is often transient or per-request, and persisting it would take the key out of service, add key state to the provider dialog and defeat the pool's list priority; the pass-scoped attempted set already bounds the rotation.
- Retry the same key on a bare 429 instead of rotating to the next usable key: declined because the request should continue on the next usable key promptly; repeatedly contacting one rate-limited key would delay the healthy key the pool exists to provide.
- Charge the rotation against the per-provider retry budget: declined because a rotation is not a retry; the budget must stay intact so the provider can still receive its full bounded retry schedule after a fully rate-limited pass.
- Let a pass keep rotating without bound or allow a key to be retried inside the same pass: declined because a provider could then loop indefinitely; each pass attempts each usable key at most once and hands the failure to the bounded retry schedule.
- Apply the TTL to auth marks or to quota marks without a marking time: declined because a rejected credential cannot recover by time and needs the operator, while a missing marking time gives no evidence of elapsed TTL; both stay permanently marked.
- Recover TTL-expired keys through the half-open probe instead of normal selection: declined because the probe is the last-resort single-flight recovery when no usable key remains; TTL recovery is deterministic freshness and belongs to normal list-order selection, with clear-on-selection and re-mark when still exhausted.
- Choose no TTL or a background probe for quota recovery: declined because quota windows reset without operator action while background probing is a non-goal, so recovery must stay request-driven; a fixed 30-minute TTL bounds the cost to at most one wasted call per still-exhausted key per period and leaves the all-marked 60-second probe untouched.
- Keep the single-candidate fast fail: declined because a transient 500 or network error then surfaces immediately with no retry on the only provider; the existing cap, exponential backoff and 120-second budget already bound the extra attempts, so the earlier rationale no longer outweighs a transient recovery.
- Pin the query source key to the serving key or to the first stored key: declined because following the serving key couples an informational query to traffic, and the first stored key may be disabled or runtime-marked; the ladder prefers the first usable key and only falls back when none is usable.

## Consequences

- Bare-429 rotation is bounded: one pass attempts each usable key at most once, the rotation itself persists no mark, registers no mapping health and consumes no retry budget, and an exhausted pass hands the provider to the existing bounded retry schedule with its full budget; streaming keeps the first-byte boundary and every other failure class keeps its previous behavior.
- A quota-marked key returns by list priority once its mark is at least `KEY_QUOTA_MARK_TTL_SECS = 1800` seconds old (inclusive at the boundary); selection clears its runtime state and persists that clear through the serialized configuration write, a still-exhausted attempt re-marks it and continues on the next key, and auth marks, marks without a marking time and the all-marked 60-second probe are unchanged.
- A single serviceable candidate receives the same bounded retry schedule as a multi-candidate request in both the non-streaming and streaming paths; the multi-candidate fallback-first schedule, `Retry-After` priority, per-provider cap and 120-second budget are unchanged, and a post-first-byte streaming failure still truncates without retrying.
- The quota and usage queries use the first enabled unmarked key, then the first enabled key, then the first stored key; an empty pool keeps the existing no-key error, the queries remain read-only, and the existing cache invalidation on a source-value or base-URL change is unchanged.
