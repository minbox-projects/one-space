# Agent Note: Gateway Template Model Retirement Disables Derived Mappings

Status: implemented

English | [中文](2026-09-20-gateway-template-model-retirement.zh.md)

## Problem

Template syncs could add models but could not retire them. A sync replaced the template's model list wholesale from its `models_url`, yet every derived provider kept the mapping for a model the endpoint had dropped, and that mapping stayed enabled and kept serving until the operator found the removed model in the provider dialog and disabled or deleted it by hand. The sync result and the forwarding state it left behind therefore disagreed, and the provider cards gave no sign of which mappings came from a template or that a mapping's model had left its template.

## Decision

A template sync now disables, without deleting, the derived mapping of every model the previous template carried and the fetched list no longer contains. In `propagate_to_derived` (`src-tauri/src/api_gateway/templates.rs`) the sync computes the retirement set as the `previous.models` entries whose `upstream_model` is absent from the fetched list, matches it exactly on `upstream_model`, and for every provider bound to that `template_id` sets `enabled = false` on the mapping with that upstream model. The retirement set is exactly that difference: a mapping whose model the previous template never carried, an already-disabled mapping, a model the operator deleted or ignored earlier, a manual provider and a provider bound to another template are never touched, and the sync writes no `ignored_models` record. Only the mapping's `enabled` flag changes: the row, `local_model`, `display_name`, `protocol`, `reasoning_efforts`, the provider's `default_model` and every price row stay as they were, no new persisted field is added, and a model the template only disabled while still listing it is not retired. The new template and every derived-provider update are staged on a clone and persisted once through the encrypted atomic `write_config`; a failed write leaves the previous state in place.

Retirement is one-way. The sync never re-enables an existing mapping — it only ever writes `false` to one — so a retired mapping stays disabled when a later sync returns its model to the template, while a mapping the operator explicitly re-enables through the provider dialog stays enabled when a later sync still lists its model; the existing rule still adds one enabled mapping per newly available enabled template model. Because the disabled mapping is excluded by the existing enabled-flag semantics, a retired model leaves candidate selection, `GET /v1/models`, the aggregated model view and the terminal-sync model lists without any downstream change.

The upstream-provider card explains retirement from current state. `UpstreamProviderList` receives the loaded `templates` views, resolves a provider's `template_id` to its template view and renders the existing `ProviderTemplateAvatar` from `ProviderTemplateIcon.tsx` beside the card title with the accessible `apiGatewayProviderTemplateAvatarTitle` title (`Created from template {{name}}`); a manual provider or an unresolvable `template_id` renders no avatar and raises no error. The retired-mapping hint is the set of mappings with `enabled === false` whose `upstream_model` is absent from the bound template (`isMappingDeprecated`), rendered only when non-empty as the count from `apiGatewayTemplateRetiredMappings` with the model names in the `apiGatewayTemplateRetiredMappingsTooltip` tooltip. A zero count renders nothing, and because the hint derives from current data rather than a stored event, re-enabling or deleting a mapping shrinks it immediately. `src/i18n.ts` carries both languages for the three keys and `en_keys.txt` / `zh_keys.txt` stay paired.

## Alternatives considered

- Disable every mapping whose model is absent from the template, including manual mappings: declined because a mapping whose model the previous template never carried is outside the template's contract; the retirement set is only the previous-template-minus-fetched-list difference, so a manual mapping, a provider bound to another template and a model that never matched the template stay untouched.
- Automatically re-enable a retired mapping when its model returns to the template: declined because a sync must stay one-way — `enabled` expresses the operator's intent and a sync never re-enables an existing mapping; the operator re-enables the mapping explicitly in the provider dialog, and until then the returned model keeps its mapping disabled and stops counting toward the card hint because it is present in the template again.
- Delete retired mappings: declined because deletion would discard the remote model name, the row protocol and the display name, remove the provider-scoped price row and record the model in `ignored_models`; the kept disabled row preserves the mapping data, keeps the retirement visible on the card and lets the operator re-enable it deliberately.
- Record the card hint as a persisted sync event: declined because the hint only describes current state; a stored event would survive later operator edits and need a new persisted field with its own lifecycle, while the derived hint shrinks as soon as a mapping is re-enabled or deleted and needs no migration or dismissal state.

## Consequences

- Retirement is a single `enabled = false` write on the derived mappings of the removed models: the configuration schema, the command signatures and the readability of an older `api_gateway.json` are unchanged, and an older build reads the disabled mapping as the existing value it already understands.
- Rollback needs no data migration: a reverted build never re-enables a disabled mapping, so after rollback the forwarding behavior equals the pre-change state for every row the operator did not touch.
- Behavior migration: a mapping an earlier build left enabled after a template removal already left the previous template, so it is outside the next sync's retirement set and keeps its current state until the operator disables it explicitly.
- The card hint derives from current state and therefore also counts any other mapping with the same absent-model-and-disabled shape; it is not an event log, and re-enabling a mapping remains the operator's explicit act.
