# Agent Note: Gateway Auto-Disable Recovery Uses a Cooldown Half-Open Probe, a Post-Resume Transport Grace and a Transition Broadcast

Status: implemented

English | [中文](2026-09-23-gateway-auto-disable-recovery.zh.md)

## Problem

The per-mapping runtime health delivered on 2026-09-20 removed a failing model from service and left recovery to the operator: a row auto-disabled by the failure threshold returned only through `api_gateway_reenable_provider_model` or `api_gateway_reenable_provider_models`, so a transient upstream outage could sideline a healthy model until someone noticed. Two further gaps surrounded that manual recovery. A sleeping Mac settles a burst of network failures that are not the upstream's fault when it wakes, yet those failures counted toward the threshold and could auto-disable rows. And each settlement silently changed persisted runtime state, so an open page kept stale provider cards, model list and runtime status until a tab switch or restart, and an open provider dialog kept a stale snapshot. The work therefore had to decide how a threshold-disabled row may retry itself, how a detected system resume is separated from an upstream outage, and how a persisted transition reaches the UI without a reload storm.

## Decision

A mapping row auto-disabled by the transient-failure threshold becomes a half-open probe candidate only when its provider and the row are both `enabled`, the row is still `auto_disabled`, its `disabled_at` is present and at least `AUTO_DISABLE_PROBE_COOLDOWN_SECS` (60 seconds) old, its `consecutive_failures` is at least `FAILURE_THRESHOLD`, its trimmed `disabled_reason` does not start with `HTTP 401` or `HTTP 403`, its trimmed `upstream_model` is non-empty, its trimmed `local_model` equals the requested model, its effective protocol equals the inbound protocol, and its provider is not already serving as one of the request's healthy candidates. `selection::find_probe_candidate` scans independently of `resolve_model_for_protocol` (which still skips auto-disabled rows), takes an explicit `now` so the 60/59-second boundary is deterministic, and returns at most one `ProbeCandidate` — provider, `MappingTarget` and upstream model — choosing the oldest `disabled_at` first and breaking ties by provider id, then local model, then upstream model.

Auth failures stay manual-only and the discriminator needs no persisted marker. Since the key-pool change, a 401/403 is key-scoped: it marks the attempted upstream key and rotates within the same request without disabling a mapping row or registering mapping health ([Gateway Key Pool Rotation Is Ordered, Probe-Limited and Manual-Only for Auth](2026-09-24-gateway-key-pool-rotation.md)); mapping rows therefore advance `consecutive_failures` only on `Retryable` failures, and a quota-exhausted 429 is key-scoped as well. Rows persisted by older builds could have been disabled by the former 401/403 path and reached the threshold under the previous counting rule, so eligibility additionally rejects a trimmed `disabled_reason` whose prefix is `HTTP 401` or `HTTP 403` — the format that legacy immediate-disable path wrote — while no threshold disable can produce that prefix. `FAILURE_THRESHOLD`, the failure classification and the existing manual recovery commands are unchanged.

The probe is lowest priority. `attempt_non_streaming` and `attempt_streaming` take an optional probe and attempt it exactly once, and only after every healthy candidate and every bounded retry has failed, only when the process-wide `try_acquire_probe_guard` succeeds for the trimmed mapping key (a `ProbeGuard` released on drop, including cancellation), and never queue it for retry or backoff; a streaming request probes only in its pre-first-byte phase. A successful probe serves the client and clears the row through `clear_mapping_runtime_state` (`auto_disabled`, `disabled_reason`, `disabled_at`, `consecutive_failures` and `last_error_at` all reset). A failed probe of any class re-arms the cooldown through `rearm_mapping_probe_cooldown`: the row stays auto-disabled, keeps `consecutive_failures`, and moves `disabled_at` to the attempt time; unless the failure was a transport failure suppressed by the resume grace, `last_error_at` and `disabled_reason` are refreshed too. The existing `all_providers_unavailable` 502 names the probed provider.

A zero-candidate request consults probe eligibility before writing its response. With an eligible candidate it proceeds with an empty healthy-candidate list and the probe as its only attempt, so it writes a normal named probe attempt row plus exactly one terminal row instead of the synthetic no-candidate row; with no eligible candidate the existing synthetic 502 row is unchanged. A probe-only request neither reads nor writes a session-affinity binding. A probe never revives a row whose `enabled` is false, because eligibility requires both the provider and the row to be enabled, and a failed probe never clears `auto_disabled`.

`app_runtime::runtime_services` holds a process-wide epoch-seconds resume timestamp (`0` means no resume detected, process memory only) with `SYSTEM_RESUME_GRACE_SECS = 60`, `mark_system_resume()`, `system_resume_grace_active(now)` (inclusive through the `T+60s` boundary, false at `T+61s` and with no signal) and a `#[cfg(test)]` setter; `app_runtime` re-exports the two production functions as `pub(crate)`. `ssh_tunnels::reconnect` calls `mark_system_resume()` at both existing detection points — the sleep-gap heartbeat and the macOS `NSWorkspaceDidWakeNotification` observer — before scheduling its SSH reconciliation. `runtime_http::handle_connection` evaluates the grace once when a request starts. `AttemptResult::Failure` carries a `transport` flag that the network send, body-read, stream-open and mid-stream-read error paths set while HTTP-status failures keep it false, and `RequestHealth` stores the grace result so `record_failure` skips counting only a `Retryable` transport failure inside the window: `consecutive_failures` and `last_error_at` stay untouched and no auto-disable occurs. HTTP-status failures (5xx) and every failure settled by a request that started outside the window or with no signal keep counting, while 401/403 and quota-exhausted 429 responses are key-scoped and never register mapping health ([Gateway Key Pool Rotation Is Ordered, Probe-Limited and Manual-Only for Auth](2026-09-24-gateway-key-pool-rotation.md)), and a suppressed failed probe refreshes only `disabled_at`.

`api_gateway.rs` defines `API_GATEWAY_CONFIG_UPDATED_EVENT` = `api-gateway-config-update`. `runtime_http::start_server` takes an optional `tauri::AppHandle` and stores it in a process-wide slot (`None` clears it), `autostart` forwards the handle, and `commands.rs` exposes `start_inner(app)` while the Tauri commands `api_gateway_start` and `api_gateway_autostart` gain an injected `tauri::AppHandle` as thin wrappers — command names and frontend argument shapes are unchanged and `api_gateway_stop` is untouched. The whole-configuration `ai_gateway_save_config` command with `save_config_inner` and its registration was removed by the version-gated cleanup ([Gateway Migration Is Permanent and Version-Gated](2026-09-24-version-gated-gateway-migration.md)), and the surviving configuration writes keep the same single-transition broadcast. Exactly one event is emitted after a successful configuration write that flipped any mapping row's `auto_disabled` in either direction (threshold auto-disable or probe recovery). Counter-only settlements, probe re-arms, key runtime marks (which never emit the config-update event) and failed writes emit nothing, and emission is a no-op that never affects the settlement when no handle was captured.

`src/lib/apiGateway.ts` exports the matching `API_GATEWAY_CONFIG_UPDATED_EVENT`, and the API Gateway page subscribes with `listen` (skipped outside Tauri, with the unlisten released on unmount) so the existing `load()` refreshes the provider cards, model list and runtime status card without a tab switch or restart. The page passes the latest configuration's provider as `runtimeProvider` to the provider dialog. `ProviderDetailDialog` merges only the five runtime fields (`auto_disabled`, `disabled_reason`, `disabled_at`, `consecutive_failures`, `last_error_at`) of rows whose trimmed `(local_model, upstream_model)` key matches into its local draft, comparing field by field so an unchanged snapshot causes no re-render, never resetting user-editable fields or unsaved edits, and derives its auto-disabled hint count from the local draft.

## Alternatives considered

- Keep recovery manual-only and rely on the operator to notice an auto-disabled row: declined because a transient upstream outage then keeps a healthy model out of service until someone re-enables it, which is exactly the gap this change closes.
- Probe rows disabled immediately by 401/403 as well: declined because a rejected credential cannot recover without operator action, so a probe would only spend latency and log noise; the same rationale now governs auth-marked keys in the ordered key pool, and the reason prefix keeps legacy auth-disabled rows in the manual-only set ([Gateway Key Pool Rotation Is Ordered, Probe-Limited and Manual-Only for Auth](2026-09-24-gateway-key-pool-rotation.md)).
- Persist a discriminator field that marks how a row was disabled: declined because it would add a persisted field and a migration to `api_gateway.json`, while the counter semantics plus the `HTTP 401`/`HTTP 403` reason prefix already separate threshold disables from auth disables in both directions.
- Append probes into the weighted candidate order: declined because a probe must never preempt or delay a healthy candidate and injected probes would distort the smooth weighted distribution; the probe runs only after every healthy candidate and bounded retry has failed.
- Infer a local-network outage from several providers failing at the same time and suppress counting then: declined because the gateway cannot distinguish a local network failure from several genuine upstream failures, and a false positive would hide real failures; the explicit system-resume signal is the only suppression trigger.

## Consequences

- A threshold-disabled row can return to service without operator action: after the 60-second cooldown the next request that needs it and cannot be served by any healthy candidate probes it exactly once; a success serves the client and clears the row, a failure restarts the cooldown and the caller receives the existing `all_providers_unavailable` 502 naming the probed provider. The user's `enabled` intent, the manual re-enable commands and the row's remote identity are untouched, and legacy auth-disabled or user-disabled rows are never probed.
- Counter semantics: a mapping row's `consecutive_failures` advances only on consecutive `Retryable` failures; since the key-pool change, 401/403 and quota-exhausted 429 are key-scoped and never disable a mapping row or increment its counter ([Gateway Key Pool Rotation Is Ordered, Probe-Limited and Manual-Only for Auth](2026-09-24-gateway-key-pool-rotation.md)); the threshold auto-disable still fires at `FAILURE_THRESHOLD` of 3, and the affected settlement tests were updated with that rationale.
- Sleep/wake noise no longer auto-disables rows: a `Retryable` transport failure settled by a request that starts within 60 seconds of a detected resume is uncounted and cannot trigger an auto-disable, while HTTP-status failures and out-of-window failures count as before, so a genuine outage that starts after the window still disables rows. Detection uses the existing cross-platform sleep-gap heartbeat and the macOS wake observer; Windows and Linux wake notifications remain out of scope.
- Open surfaces stay live: each auto-disable or recovery transition is broadcast once, after the successful configuration write, and the API Gateway page reloads its configuration in response; counter-only settlements emit nothing, so a busy gateway cannot cause a reload storm, and an open provider dialog merges only the runtime fields and keeps unsaved edits.
- Probe eligibility adds no schema change of its own: it reuses `disabled_at`, `consecutive_failures` and the `disabled_reason` prefix, rows persisted by older builds stay manual-only when their reason starts with `HTTP 401` or `HTTP 403`, and the resume timestamp, probe guards and session bindings are process memory only. The gateway-wide schema version and its version-gated migration are recorded by [Gateway Migration Is Permanent and Version-Gated](2026-09-24-version-gated-gateway-migration.md), and the persisted runtime state described here remains valid under it. The new Tauri event is additive, so a frontend without the listener keeps today's behavior, and a reverted build stops probing and broadcasting while the persisted runtime states remain valid.
- Supersession: partial supersession of [Gateway Per-Model Auto-Disable Settles Health on the Mapping Row](2026-09-20-gateway-per-model-auto-disable.md), which is retained and cross-linked; this change replaces only its manual-only recovery statement, its previous 401/403 counting rule and its unqualified exclusion of auto-disabled rows from every attempt, while the row-level runtime state, the threshold rule, the settlement sites, the manual recovery commands and the dialog surface stand. This record's statements that a 401/403 disables a mapping row immediately and that a quota-exhausted 429 counts as mapping health are replaced by [Gateway Key Pool Rotation Is Ordered, Probe-Limited and Manual-Only for Auth](2026-09-24-gateway-key-pool-rotation.md), which marks the attempted key and rotates within the request; the legacy reason-prefix discriminator and every other decision here stand. [Gateway Session Affinity Pins a Session and Model to One Upstream](2026-09-20-gateway-session-affinity-routing.md) is retained and cross-linked because a probe-only request attempts its probe with an empty candidate list and still neither reads nor writes a binding, so its decisions stand. [Gateway Per-Attempt Request Logging and Stored Error Text](2026-09-20-gateway-per-attempt-logging-and-error-text.md) is retained and cross-linked because a zero-candidate request with an eligible probe writes a normal attempt row plus its terminal row instead of the synthetic no-candidate row, while its granularity, terminal-row statistics and stored-error contracts stand. [API Gateway Smooth Weighted Round Robin Routes Requests and Fallback Candidates](2026-09-20-api-gateway-weighted-routing.md) is unaffected: the probe is attempted only after the weighted fallback sequence is exhausted and never enters the weighted scheduling, so no fact of that record changed and no supersession is recorded. The fast-fail, usage-stats, price, template, terminal-sync and bilingual records remain unrelated.
- `MEMORY.md`, `docs/USAGE.md` and the `api-gateway` / `api-gateway-backend` / `App Runtime Backend` navigation entries carry the probe, grace, counter and transition standards in the same change, and `navigation.md` was regenerated from the authoritative JSON.
