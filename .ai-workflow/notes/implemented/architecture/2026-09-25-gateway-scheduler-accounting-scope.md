# Agent Note: API Gateway Scheduler Accounts per Provider, Local Model and Protocol and Prunes Deleted Providers

Status: implemented

English | [中文](2026-09-25-gateway-scheduler-accounting-scope.zh.md)

## Problem

The smoothed weighted round-robin scheduler kept one current-weight per provider id in a process-global map. When one provider was reachable through several local models or through both inbound protocols, requests with different candidate sets shared that one current-weight: traffic for one model consumed the current-weight another model had accumulated, so under mixed candidate sets an equal-weight model's winner sequence skewed even though its own candidate set and weights were unchanged. A provider deleted from the configuration also left its scheduler entries in the process-global map forever, so recreating a provider with the same id resumed stale accounting, and there was no seam to observe whether entries had actually been removed.

## Decision

The scheduler key is now a `WeightedSchedulerKey` composite of the provider id, the trimmed requested local model and the inbound protocol. The local-model component applies the same normalization model resolution uses — trimmed, with a blank or missing value treated as absent — and the protocol component is the canonical endpoint suffix returned by `UpstreamProtocol::endpoint_path()` (`/chat/completions` or `/responses`), a stable `&'static str`. `selection::weighted_candidates(candidates, local_model: Option<&str>, protocol: UpstreamProtocol)` builds one key per candidate, and the request entry point passes the requested local model and the inbound protocol when it resolves the order inside the session-affinity critical section, so each provider's current-weight exists once per provider, model and protocol scope.

The SWRR algorithm itself is unchanged: each candidate's current weight is incremented by its effective weight (`weight.max(1)`), the highest current weight wins with the provider id in ascending lexicographical order as the deterministic tie-breaker, the selected candidate's current weight is reduced by the total participating weight, and the remaining candidates are sorted by descending updated current weight with the same provider-id tie-break. A zero- or single-candidate list still returns directly without mutating scheduler state, and disabled or auto-disabled providers are still pre-filtered by candidate resolution.

Scheduler entries are pruned only by a genuine deletion and only after a successful configuration publication. `write_config` and `modify_config` read the provider ids persisted at the same path before publishing (`persisted_provider_ids`), publish the new configuration, and then call `prune_removed_providers(before_ids, &published)`, which passes exactly `before - after` to `selection::prune_weighted_scheduler`; a failed write prunes nothing. An id that is absent from the published configuration but was never present before belongs to another configuration sharing the process-global scheduler — for example a parallel multi-home test process — and is deliberately left alone. The `#[cfg(test)]` accessor `weighted_scheduler_entry_count(provider_id)` counts the entries tracked for one provider id across every model and protocol scope, and the existing direct scheduler tests were adapted mechanically to the new key parameter without weakening their assertions.

## Alternatives considered

- Keep accounting keyed by provider id alone: declined because one shared current-weight across different candidate sets lets one model's or protocol's traffic skew another's distribution, which is exactly the observed failure.
- Key by provider plus local model only, or by provider plus protocol only: declined because both dimensions isolate real scopes; one provider can serve the same local model under `chat_completions` and `responses` with different peer candidates, and different local models under one protocol draw from different candidate sets, so dropping either dimension reintroduces skew on that axis.
- Key by the full candidate set or a hash of it: declined because candidate membership changes with user enable/disable and mapping edits, so the accounting would fragment or reset on unrelated edits; provider, model and protocol is the stable operator-visible scope, and the algorithm, weights and tie-breaking stay out of scope.
- Change the SWRR algorithm itself or the weight semantics: declined because the plan keeps the algorithm, the weight bounds and the deterministic tie-break unchanged; only the accounting dimension moves, and the same-set smoothness sequence is a regression test.
- Prune every provider id absent from the writer's configuration instead of the same-path diff: declined because the scheduler is process-global and shared by other configurations, such as parallel multi-home tests, so an id absent from this writer may still belong to another configuration and must not be cleared.
- Clear the whole scheduler map on every configuration write: declined because any provider edit would reset the smoothness of every unrelated provider and because a failed write must never mutate scheduler state.
- Prune lazily during candidate selection instead of after publication: declined because selection would need to compare against configuration state on the request path and would mutate scheduler state during an attempt; pruning belongs to the successful publication that proves the deletion.

## Consequences

- Mixed candidate sets no longer skew per model: with equal-weight providers A, B and C where M1 maps to {A, B} and M2 maps to {A, B, C}, M1's winner sequence alternates one-to-one between A and B while M2 rotates one-to-one-one.
- The same provider and local model under different protocols keep independent winner sequences, since the inbound protocol is part of the accounting key.
- The SWRR accumulation, selection, tie-break, remaining-candidate ordering and the zero- or single-candidate bypass are unchanged, and the same-set 3:1 smoothness sequence still holds; session affinity still resolves the order inside its critical section and its binding rules are untouched.
- A provider deleted and persisted has its scheduler entries removed after the successful publication, so recreating that id starts from fresh state; a failed write, an id that only another configuration knows, and a merely absent id never prune anything.
