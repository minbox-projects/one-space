# Agent Note: Cloud Agent Hardening Guarantees

Status: implemented

English | [中文](2026-10-29-cloud-agent-hardening.zh.md)

## Problem

The self-hosted cloud agent runs an OpenAI-compatible gateway, GitHub Issue automation, long-lived tmux/OpenCode sessions, disk maintenance and deployment on one small Linux host reached over SSH. Before hardening, the gateway accepted unauthenticated and browser-origin requests and answered with wildcard CORS, broadcast unknown model names to every active provider, tried one key per candidate while reusing cooling keys, and read upstream streams through blocking buffers that delayed small chunks. Issue automation ran any labelled Issue without checking the author's repository permission, pasted Issue text into the prompt as instructions, treated transient and permanent failures alike with no retry budget, could duplicate work when a PR-create response was lost, kept only a legacy processed list without atomic writes or corruption handling, and wrote unbounded transcripts that could expose credentials. Session commands composed shell strings, reused directories without checking worktree registration, and cleanup removed session data by default. The daemon relied on systemd's default stop behaviour, and deployment installed code before validating the remote configuration.

## Decision

The gateway is authenticated and origin-gated before any other handling. `GET /models`, `GET /v1/models`, `POST /chat/completions` and `POST /v1/chat/completions` require `Authorization: Bearer <token>`, compared in constant time against `ai_gateway.auth.token` (default `sk-onespace-cloud-agent`); `/health` and `/v1/health` stay public, and `ai_gateway.auth.require = false` bypasses only the credential check. Any request carrying an `Origin` header, including an empty value and including health and `OPTIONS`, returns 403 before authentication, body reading or forwarding; `OPTIONS` without `Origin` returns 204 and no response path emits wildcard CORS. Declared bodies above `ai_gateway.max_body_bytes` (default 10485760 bytes) return 413 before any read or upstream call, and missing, zero, negative or non-numeric `Content-Length`, empty bodies and malformed JSON return 400.

Model resolution is strict: only model-pool names, `provider/model` prefixes of active providers and explicit mappings on active providers resolve. Unknown, empty and whitespace-only names return 404 with `model_not_found` and never contact an upstream, while a known pool without a usable candidate returns 502 so operational unavailability stays distinct from an unknown name. Template synchronization builds a replacement catalog generation and publishes it under a lock, so resolution, listing and OpenCode projection each read one complete generation; provider key state is shared across generations and publication never resets cooldowns.

Failover stays inside one provider before moving on. On HTTP 429, any 5xx or a transport failure, the current key is cooled and the remaining usable keys of the same provider are tried before the next candidate; each key is attempted at most once per candidate, and a cooling key is never waited for or reused. Cooldowns are monotonic: 60 seconds for HTTP failures and 30 seconds for transport failures by default, a positive finite `Retry-After` overrides the default up to `ai_gateway.retry.max_cooldown_seconds` (default 600), and invalid values fall back to the defaults. When every configured key of every matching candidate is cooling, the gateway returns 429 with `Retry-After` set to the ceiling of the smallest remaining cooldown and makes no upstream call.

Streaming relays remain bounded. The relay reads through `HTTPResponse.read1` with a 65536-byte capacity and forwards whatever bytes are available immediately instead of waiting for a full block, preserving a short final block. Once downstream headers are committed, an upstream read failure only closes the downstream: no second JSON body and no replay through another candidate. A downstream write or flush failure ends the relay and closes the upstream without cooling the key.

Issue execution is authorized before any workspace, branch, comment or notification. `issue_worker.require_author_permission` defaults to true, and only an effective repository permission of `admin`, `maintain` or `write` permits processing; `maintain` is normalized to `write`, `triage` to `read`, and any other role name is not authorization. Permission lookups are cached per repository and author for `issue_worker.permission_cache_seconds` (default 600) on a monotonic clock; lookup failures fail closed, are logged and are never cached as authorization, while a denied preflight consumes no attempt and is not persisted as processed. At startup the worker runs `gh auth status` without `--show-token`, warns on authentication failure or excessive scopes, and the documented least-privilege guidance is `repo`, `workflow` only for workflow edits and `read:org` only for organization repositories.

Issue content is treated as untrusted data. The title and body sit inside explicit untrusted-data markers that supplied marker text cannot close, next to repository and Issue metadata, and fixed instructions state that the text is data rather than commands, forbid reading or exposing secrets, environment variables, host files and credentials, and restrict edits to the clone. These are prompt constraints, not an operating-system sandbox; root execution and `--yolo` remain, and host hardening stays an operator responsibility. Retries are classified and bounded: transient timeouts, clone/push/network failures, OpenCode nonzero exits and upstream 5xx consume up to `issue_worker.max_attempts` total attempts (default 3) with `min(30 * 2 ** (attempt - 1), 300)` second backoff, while 401/403, missing repository or Issue and closed Issue are permanent and consume one attempt. Before every clone the complete paginated open-PR list is checked for a body reference to the Issue number with numeric boundaries, and the check repeats before a retry and after a failed PR creation, so a lost response cannot cause a second execution.

Terminal state is durable. `~/.config/onespace-cloud-agent/worker_state.json` stores `version: 2` records keyed by repository and Issue-number string with `status` (`done` or `failed`), integer `attempts`, redacted `last_error` and UTC `updated_at`; legacy repository-to-number lists load as done with zero attempts, the original legacy bytes are preserved once as `worker_state.json.v1.bak` before the first v2 write, saving uses a same-directory temporary file plus `os.replace`, and corrupt or invalid state is quarantined with a unique suffix before an empty state is used. Attempt transcripts live in `~/.config/onespace-cloud-agent/logs/`, record start time, command arguments, exit codes and classification, bounded stdout/stderr and `git diff --stat` or an explicit pre-clone unavailability, redact configured tokens, credential environment values and `Authorization` values, cap each file at 2097152 bytes and retain only the global newest 20 attempt logs without touching unrelated files. Terminal notifications retry transport errors, 429 and 5xx up to three total attempts with 1- and 2-second backoff, do not retry other 4xx, keep the DingTalk and WeChat channels independent, never change the task outcome, and redact webhook credentials from errors.

Sessions and worktrees use literal argv and explicit ownership. Branch values beginning with `-` are rejected before any Git call and remaining raw branches pass `git check-ref-format --branch`; paths and valid branches reach Git as literal arguments, the OpenCode executable resolves from PATH with the existing `/root/.opencode/bin` fallback, the default tmux init command is exactly the quoted executable plus `--yolo`, and the project path travels only through tmux `-c` while `--no-yolo` and extra arguments are re-quoted from `shlex.split` with no fallback shell. A worktree is reused or restored only when Git registers both the matching path and branch. Cleanup derives worktree ownership from every tmux pane path, removes only registered, clean, session-free worktrees under `<workspace_root>/*-worktrees` without force and without deleting branches, and the stale sweep only considers registered, clean, session-free worktrees whose directory mtime is older than `guardian.worktree_retention_days` (default 7).

Data cleanup preserves sessions by default. `guardian.data_roots` defaults to `~/.local/share/opencode` and `~/.cache/opencode`, and normal cleanup removes only expired entries under `log` and `tool-output` older than `guardian.cache_retention_days` (default 7) without following symlinks outside those boundaries. `guardian.cleanup_sessions` defaults to false and retains all session files; explicit true additionally permits deleting expired legacy files under `sessions` with the same retention period, and `opencode.db*`, `repos` and `snapshot` are protected in both modes. A failed deletion is logged and processing continues, and low free space only raises a warning at the existing 2 GB threshold without shrinking retention.

The daemon owns shutdown. Disk checks run every `runtime.disk_check_interval_seconds` (default 300), including during a task, and an unexpected gateway-thread exit requests a nonzero process exit for the systemd restart policy. `SIGTERM` and `SIGINT` only record stop state and one shared monotonic deadline: no new Issue or retry starts, the gateway stays available to the current task for up to `runtime.shutdown_grace_seconds` (default 300), early completion exits normally, and expiry terminates only the owned Issue subprocess group and writes one failed shutdown terminal record with the actual attempt count. Command timeouts, backoff and notification waits consume only the remaining budget; a missing notification budget logs a skipped delivery, state-write failures are reported instead of claimed as persisted, and independent SSH/tmux sessions are untouched. The systemd unit uses `KillMode=mixed` and `TimeoutStopSec=infinity` so its own default stop behaviour cannot pre-empt the daemon-owned grace.

Deployment validates before it publishes. `deploy.sh` first runs `bootstrap.sh` for the platform gate (Linux, root, accessible systemd, amd64/arm64, and Ubuntu 22.04/24.04 or Debian 12 only when a runtime dependency is missing) and installs only the missing `python3`, `git`, `tmux`, `gh` and `opencode` from official sources while preserving existing executables; GitHub authentication is not a gate. It then uploads into a same-filesystem staging directory and validates the existing remote configuration or the bundled default with `python3 -m json.tool` before any installation, launcher change or restart. It snapshots the current installation outside the configured Agent directory, promotes the staging directory at that configured path, restores the snapshot if promotion fails, keeps existing configuration bytes, creates `config.json` from `config.default.json` only for a first installation, generates launchers and the systemd unit for the configured directory, and writes `install-info.json` with the package `VERSION` and a UTC `installed_at` only after a restart confirms an active service. It prunes snapshots to the newest three only after successful activation and metadata publication; a preflight, validation, upload or promotion failure leaves the active installation and existing snapshots untouched, publishes no success record and creates no false first backup. The desktop one-click inspection and deployment handoff, including the shared package `VERSION` and the distinction between unknown version and unrecorded time, are recorded in [Cloud Agent Desktop Deployment](../feature/2026-10-30-cloud-agent-desktop-deployment.md).

## Alternatives considered

- Fix the desktop sync on the desktop side or add a separate cloud override store: declined because desktop changes and a second configuration authority are outside this service, so the reset is documented as an operational step after that separate operation.
- Run the service as a non-root user or inside an OS sandbox: declined because it would change the retained root and `--yolo` execution model and its operational prerequisites; prompt constraints are documented as containment, not as a sandbox.
- Schedule several Issues concurrently: declined because one Issue at a time keeps the single small host predictable and the existing scheduling surface unchanged.
- Introduce a new configuration or persistence framework: declined because standard-library primitives, the existing JSON files and atomic replacement cover the bounded needs.
- Add an automatic production rollback command: declined because recovery keeps an operator-selected snapshot and explicit verification instead of guessing a version to restore.
- Relax body or authentication rules for browser clients: declined because browser-origin access is the attack surface being removed; only Origin-free `OPTIONS` answers 204.
- Delete session data by default: declined because sessions are user data; emergency deletion requires an explicit switch and an operator backup.

## Consequences

- Current defaults: loopback gateway on port 17688, token `sk-onespace-cloud-agent`, 10 MiB body limit, 60/30-second cooldowns capped at 600, 180-second Issue polling, 3 total attempts, 7-day cache and worktree retention, 5-minute disk checks, 300-second shutdown grace, and session cleanup off.
- Gateway clients must send the Bearer token on the four protected routes; generated `provider.gateway` credentials use the configured token, so a custom token has to be applied on both sides.
- Data ownership and recovery: worker state, attempt logs and task history stay under `~/.config/onespace-cloud-agent/`, the legacy backup is written once and never overwritten, and corrupt state is quarantined rather than silently overwritten.
- v2 state is not backward compatible: an older worker must receive a restored `worker_state.json.v1.bak` or a documented empty state, never the v2 file.
- A sibling `opencode.jsonc` is preserved byte-for-byte with a warning; merging or removing it remains a manual operator action because OpenCode may give it precedence.
- The existing desktop gateway sync still replaces the whole remote `ai_gateway` section, so custom authentication, body limit and cooldown settings must be reapplied afterwards.
- Emergency session deletion cannot be undone by a code rollback and requires an operator data backup; default cleanup removes no session data.
- The Linux systemd smoke check stays explicit: local tests use fake clocks, threads and transports and do not prove service start/stop, stop-timeout cooperation, snapshot retention or a first deployment on a real host.
- Verification for this decision is the full server Python unit suite plus note validation and workflow plan validation, together with the documented deployment check; no memory, latency or disk-capacity guarantee is claimed beyond the stated bounds, caps and retention periods.
