# Agent Note: Model Pools Prefer the Preceding Candidate for Same-Turn Tool Continuations

Status: implemented

English | [中文](2026-10-15-model-pool-context-hold.zh.md)

## Problem

A model pool rotates its enabled source candidates with a smooth weighted round robin, so every request of one client turn can be served by a different source even when the client is continuing the same tool call. An agent client sends a Chat Completions or Responses request, a source returns a function call, and the client appends the assistant tool call and its result without a new user message. The pool had no notion of that turn, so it advanced the rotation and moved the continuation to a sibling source. The switch discards the preceding source's prompt prefix and its upstream prefix-cache reuse, and it can change the model that answers mid-turn for no operator or client intent. Ordinary session affinity is deliberately not a pool input, because pinning a whole session to one source would defeat the rotation the pool exists to provide. The problem is therefore narrow: keep one recognized tool continuation on the source that successfully delivered the preceding tool call, without turning the pool into a session-wide binding and without relaxing which sources may serve.

## Decision

- Own the decision in a new `src-tauri/src/ai_gateway/pool_context_hold.rs` module. Candidate resolution, weighted ordering, probes, key rotation, protocol conversion and transport stay in their existing modules; this module only decides whether a currently healthy candidate moves to the front of the already planned pool order.
- Resolve a hold scope only for a request that names a current enabled pool alias. The scope combines the identity (never the credential value) of the first configured enabled local key matching either accepted credential header, the already preferred session header, the supplied nonblank `thread-id`, the pool id, its public alias and the ingress protocol. A request without a recognized session header, or without a history array for its ingress, keeps ordinary routing and produces no scope.
- Recognize a continuation structurally rather than by content equality. The retained caller history must be an exact structural prefix, the instruction/tool context must be identical, no appended user message may appear, and the appended assistant/function-call and tool-result facts must match the tool-call identities the preceding delivered response reported. Chat tool results are matched by `tool_call_id` and Responses `function_call_output` items by `call_id`, including multiple calls in one response. A changed prefix, changed instructions or tools, an unknown call identity, a repeated standalone request or any otherwise ambiguous history invalidates the preference and follows normal selection.
- Observe a caller stream incrementally at the existing write boundaries instead of buffering a whole answer. `StreamingToolObserver` scans only the bytes the gateway already writes to the caller, one SSE line at a time, reassembling a line split across chunks and accepting both LF and CRLF boundaries; it retains only the caller-protocol tool identities (Chat `choices[].delta.tool_calls[].id`, Responses `function_call` items by `call_id`). Comment, metadata, usage-only, `[DONE]` and error events carry no tool identity and are ignored, only the current partial line is buffered, and no wire byte changes.
- Publish a preference only after a confirmed completed delivered stream from the candidate that actually served it, including an allowed successful probe, and after a successfully delivered non-streaming caller-protocol response. The module reads the tool identities from a delivered non-streaming response body, or from the caller-protocol identities the streaming observer collected on a completed client stream, and stores the request snapshot, the instruction/tool context and those identities together with the exact candidate identity (pool, provider, original local/upstream pair and effective protocol) and the resolved endpoint. A completed answer with no recognizable caller-protocol tool call, streamed or not, closes the preference; a failed, incomplete, cancelled, disconnected or post-first-byte-failed request publishes nothing, refreshes nothing and is never replayed.
- Prefer the held candidate only while it is currently eligible: the provider and its mapping row are enabled and not auto-disabled, the mapping still resolves to the same effective protocol, a usable key exists, the endpoint is unchanged and the candidate is not cooling. The preference moves exactly one candidate to the front of the planned order and preserves the relative order of the remaining candidates and the existing probe position; it never adds a candidate, promotes an unavailable or probe-only candidate ahead of healthy candidates or bypasses pool alias fencing.
- Bound the retained state strictly. The store is process memory only, keyed by scope, with a monotonic idle timeout of more than 30 minutes (exactly 30 minutes remains eligible), at most 1024 entries, at most 1 MiB of retained serialized payload per entry and 16 MiB in total, with least-recently-used eviction. Over-budget evidence is never retained and no partial or truncated request is stored. No request or response body, header, credential or hold state is written to disk, logs or commands, and a new process begins with no preference.
- Admit each request as the newest turn of its scope with a monotonic admission token that also gates streaming completion. A completed preference records its entry only when its token is still the scope's latest, so an older overlapping request that finishes last can neither replace nor resurrect a newer admitted turn.
- Keep ordinary behavior unchanged. Standalone pool requests, headerless requests, new user messages and disabled, retired or otherwise ineligible aliases keep the existing smooth weighted round robin, alias fencing and ordinary session affinity. The preference only reorders an already selected candidate; it changes no request bytes, key, mapping health or accounting.

## Alternatives considered

- Pin a whole pool session to one source for its lifetime: declined because that is the ordinary session-affinity behavior this pool deliberately excludes; it would fix a multi-turn session to one source and defeat the weighted rotation the pool exists to provide, while a single tool continuation only needs the preceding source for one turn.
- Infer continuity from the user text, a content hash or a fingerprint: declined because identical or rebuilt user text is not evidence of the same turn, and a hash would hide a rewritten or truncated prefix that must invalidate the preference; a direct structural prefix and tool-identity comparison is both stricter and inspectable.
- Promote a probe-only or otherwise ineligible candidate to the front: declined because a hold must never widen the candidate set, bypass current eligibility or relax pool alias fencing; an unavailable source keeps its normal fallback position and the healthy candidates keep serving.
- Keep the retained history on disk or in the usage log: declined because the preference is ephemeral and must never persist request bodies, headers or credentials; a bounded process-memory store that starts empty on each launch is sufficient.
- Serialize requests within a scope to decide ordering: declined because the gateway must not add request concurrency limits; a monotonic admission token rejects a stale publication without holding any lock across network I/O.

## Consequences

- Within one recognized user turn, a Chat Completions or Responses tool continuation of an enabled pool alias attempts the source that successfully delivered the preceding tool call before the rotation would advance, whether that delivery was buffered or streamed, and the forwarded request keeps the tool identities, arguments and results and the public-to-real model mapping. A streamed tool-call chain over the existing protocol adapters — Chat ingress to a Responses upstream, or to a native Messages upstream — prefers the candidate that actually delivered the converted tool call, with client-visible tool identity and completion framing intact. A new user message, a repeated standalone request, a headerless request or a different scope returns to the ordinary weighted rotation immediately.
- The preference is a bounded, per-turn reordering and not a session binding: ordinary session affinity, the weighted round robin, key rotation, probes, health settlement and accounting keep their existing behavior, and a source that is removed, disabled, auto-disabled, cooling, key-less, protocol-changed or endpoint-changed is never preferred.
- The state is deliberately ephemeral and bounded: it lives only in process memory, expires on a monotonic idle timeout of more than 30 minutes, is capped at 1024 entries, 1 MiB per entry and 16 MiB in total with least-recently-used eviction, and a new process starts with no preference. A failed, cancelled or undeliverable request publishes and refreshes nothing, and an older overlapping request cannot overwrite a newer admitted turn.
