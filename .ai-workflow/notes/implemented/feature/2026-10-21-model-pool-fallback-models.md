# Agent Note: Model Pools Fall Back Through an Ordered List of Gateway Models

Status: implemented

English | [中文](2026-10-21-model-pool-fallback-models.zh.md)

## Problem

A model pool's fallback unit was one provider-specific source candidate. An operator who wanted the alias to survive exhaustion across every provider mapping of a model had to choose one mapping, duplicate its provider identity, and keep its weight and reasoning declaration synchronized by hand. That unit became stale whenever the provider set or mapping metadata changed, and it could never use the other mappings that actually served the local model. The missing decision was a fallback whose unit is the gateway local model id, expanded automatically to every mapping that serves it, while the regular candidates still own the primary choice.

## Decision

- Persist the ordered `fallback_models: Vec<String>` list on `ModelPool` under gateway configuration schema 4. Each entry is a trimmed gateway local model id, serialized only when non-empty, and a pool still requires at least one regular candidate. Entries carry no provider, upstream model, protocol, weight or fallback-local reasoning, because the referenced mappings remain the only source of truth. Save validation trims and deduplicates the list, rejects blank entries, rejects current and retired pool aliases, and requires every newly submitted model to resolve to at least one provider mapping. An unchanged saved entry stays retainable and clearable after its source disappears or becomes disabled; a failed save leaves every encrypted byte unchanged.
- Migrate once on the version-gated configuration read path. A legacy single fallback object contributes only its trimmed `local_model` as a one-entry list, then its key is removed. The legacy provider, upstream model, protocol, weight and reasoning are discarded; a missing or null legacy fallback adds nothing; a current-version file is not rewritten. The migration keeps unrelated pool values, regular candidates, declarations, weights, the default preference, providers, prices and credentials intact.
- Expand at request time. One stored model id expands to every provider mapping whose trimmed local model equals it, preserving provider and mapping order and emitting each exact source identity once. Runtime eligibility uses the existing source contract: enabled provider, enabled mapping, ingress-compatible protocol, usable key and not cooling; an auto-disabled mapping remains reachable only through the existing shared probe allowance. Status expansion includes disabled and auto-disabled mappings so their availability codes and bounded reasons stay visible.
- Preserve order and rotate providers. Every source of an earlier stored model precedes every source of a later one. Within one model, currently eligible sources share an equal-weight smooth weighted round robin scoped to the pool, that stored fallback model and the ingress protocol, isolated from the primary order and from other fallback models. The fallback stage receives one pass with the ordinary in-pass key rotation and at most one shared mapping or key probe for the whole request; it schedules no new delayed retry cycle and cannot be suppressed by a spent regular retry-wait budget.
- Skip only sources actually attempted. A request-scoped set records each exact source tried as a regular candidate, probe or fallback source; the fallback queue skips a member already present and leaves the remaining sources of the same model eligible. A healthy regular candidate means the fallback receives no call. The fallback never enters primary smooth weighted round robin, ordinary session affinity or the pool continuation hold. A fallback success closes any stale primary hold instead of publishing a fallback preference, while a successful regular delivery keeps the existing continuation behavior even when its local model also appears in the fallback list.
- Derive reasoning per expanded source. Each source's native actions come from its exact mapping's `reasoning_efforts` and effective protocol: the OpenAI effort profile for Chat Completions and Responses, and the Anthropic effort-inherit profile for Anthropic Messages. Only declared canonical efforts become mappings, and `none` becomes an explicit disable only when declared; no control is inferred from a model name and no fallback-specific declaration is persisted. Classification, the static catalog, discovery and terminal payloads use the union of regular candidates plus expanded fallback sources. A retained concrete default may keep an unchanged declaration when its source becomes unavailable, but a fallback-list change that removes the last declaration is rejected; the existing 400, 502 and output-cap rejection paths remain.
- Report an ordered per-model status separate from regular readiness. Each record carries the trimmed stored model id, a ready flag, ready and total source counts, the expanded source statuses and an optional bounded reason; regular candidate arrays and readiness stay regular-only. A source status exposes availability and cooldown only, never a key, endpoint, header or message body.
- Prune only after a successful publication. The owned identity set is the regular candidates plus every expanded fallback source in both the old and new configurations; an identity still referenced by either role, or by the new configuration, survives. A failed write changes neither encrypted bytes nor owned scheduler or cooldown state.
- Keep the operator surface ordered. The pool dialog edits a bilingual, keyboard-accessible list with add, move up, move down, remove and clear actions, shows the provider count for each stored model, keeps unavailable saved models visible and clearable, and retains unsaved drafts across status or configuration refreshes and rejected saves; cancel performs no mutation. The pool card reports the ordered models and their counts separately from regular readiness. There is no fallback-specific reasoning editor because reasoning follows the referenced mapping automatically.
- Preserve transport, accounting and routing boundaries. Both OpenAI ingresses, streaming and non-streaming, and all three upstream protocols can serve a fallback before the first client byte; after output begins the existing ingress-format error and close behavior applies with no replay and no second success terminator. A disconnect cannot produce a later fallback attempt, a false successful terminal row, or a false health or hold success. Each completed business request keeps exactly one terminal row whose `local_model` is the public alias while provider, upstream model, usage, price and native reasoning evidence identify the actual source, and the last observed upstream status, including network status 0, is retained. Disabled pools, retired aliases, native Messages pool ingress and ordinary model routes keep their existing fences.
- Record the downgrade boundary. An older binary ignores `fallback_models`, so it serves the regular pool and honors no fallback list. Recovering the legacy behavior requires restoring the pre-migration configuration for the same profile with the matching local key; no automatic backup or migration framework is introduced.

## Alternatives considered

- Keep a single provider-specific fallback candidate and let the operator pick one mapping: declined because the operator had to duplicate provider identity and could not use every current mapping of the model.
- Store provider, upstream model, protocol, weight and reasoning per fallback entry: declined because each copy would drift from the referenced mapping and could not follow provider or protocol changes automatically.
- Append expanded fallback sources to the primary weighted order: declined because they would consume primary weights and slots and could displace a healthy regular candidate.
- Retry each fallback source with a new delayed backoff cycle: declined because it exceeds the existing finite attempt and wait boundaries.
- Re-attempt a source the request already tried: declined because it would reuse the single bounded pass and cannot change the result already settled for that exact source.
- Require an explicit fallback reasoning declaration per entry: declined because the entry is a model id and must inherit current mapping metadata rather than carry a second declaration.
- Sum fallback readiness into regular arrays or counts: declined because the operator needs regular readiness to remain regular-only.
- Silently ignore an unavailable saved model or substitute another mapping: declined because the operator must retain or explicitly clear the exact stored entry.
- Add an automatic configuration backup or migration framework for downgrade: declined because the existing explicit configuration restore is sufficient and no new persistent machinery is warranted.

## Consequences

- A pool alias can now name an ordered list of gateway models as its last resort. Each model's current mappings are all eligible, so provider-set and mapping edits take effect without editing the fallback entry.
- Providers rotate equally within one stored model under the pool, model and ingress scope, while stored model order still decides which model is attempted first. Only sources actually attempted are skipped, and a healthy regular candidate keeps the fallback at zero calls.
- Reasoning support follows exact mapping metadata and protocol automatically, so classification, the static catalog, discovery and terminal payloads agree with the sources that can actually serve the request.
- Status stays legible: regular readiness remains regular-only and each ordered fallback model reports its own ready and total source counts, unavailable sources and bounded reason.
- Configuration moves to schema 4 through one read-path migration; unrelated pool values and current-version files are untouched. An older binary ignores the list, and recovering legacy behavior requires restoring the pre-migration configuration; no automatic backup exists.
- Transport, terminal accounting and continuation boundaries are unchanged: a fallback serves only before the first client byte, one terminal row identifies the real source, a fallback success closes a stale primary hold without becoming a preference, and a disconnect cannot fabricate success.

The five-file frontend vitest run passed 320 of 320 with 0 failures; scoped eslint exited 0 with 0 errors and 4 pre-existing warnings, and `npm run build` exited 0. Native Tauri IPC, live upstream inference and real terminal projection were not exercised, and no screenshot evidence is claimed.
