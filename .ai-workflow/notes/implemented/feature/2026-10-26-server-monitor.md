# Agent Note: Server Monitor Collects Linux Resources Through Read-Only SSH Commands with Independent Session Ownership

Status: implemented

English | [中文](2026-10-26-server-monitor.zh.md)

## Problem

OneSpace had no way to observe the CPU, memory, disk and network state of Linux hosts that users already reach over SSH. Installing an exporter or monitoring agent requires remote packages, a listening port, firewall changes and an ongoing service to maintain, which is often impossible on production hosts and conflicts with the project's local-first, no-remote-installation posture. The existing SSH tunnel, terminal and SFTP modules already own their own lifecycles and persisted records; making monitoring reuse those objects would couple unrelated intentions, so a stopped tunnel or a closed terminal could silently stop monitoring, and a monitoring reconnect could disturb a user's forwarding intent. Monitoring also has to keep collecting while the page is hidden, survive restarts without replaying work, and describe partial or unavailable data honestly instead of inventing values.

## Decision

Collection is a fixed, repository-owned `/bin/sh -s` script executed over SSH. The script only reads `/proc`, runs `LC_ALL=C df -l -P -k -T` and uses `uname`, `cat` and `sleep`; no user field is interpolated into remote program text. Output is framed into named sections so Rust can parse each source independently, stderr is merged into the channel output, the exit status is inspected, and one collection is bounded by a 15-second deadline. No exporter, agent, installed service, HTTP metrics endpoint or forwarding port exists on the host. The feature is Linux-only and degrades only the resources whose commands or fields are unavailable.

Monitor connections have independent ownership through a narrow adapter in `src-tauri/src/ssh_tunnels/monitor_transport.rs`. It reuses the existing SSH configuration resolution, host-key verification and authentication behavior, but owns only its own command session and never creates, starts or modifies a saved tunnel, terminal or SFTP record. Interval mode keeps one persistent session per target, runs one command channel per collection and sends an explicit 30-second idle keepalive; collection and keepalive share one mutex, so the owned session never performs two operations concurrently. Daily mode, a paused target's manual collection and a draft connection test each use a fresh one-shot session that closes after the attempt. A broken transport is discarded and may reconnect on the next ordinary trigger, while authentication, host-key and configuration failures stay blocked until an explicit retry or edit.

The process-owned scheduler runs independently of page visibility. At most four collections run at once and each target has at most one in-flight collection; a manual collection that collides with a scheduled one shares its result. Interval mode collects on startup, activation, resume and enabling automatic collection, then rearms when the collection finishes. Daily mode arms only future local times: startup, saving, target creation and resume at or after a time do not replay it. Before any network work, the scheduler durably claims a target's local date and `HH:mm` slot in SQLite, so repeated ticks, restarts and clock rollback cannot attempt the slot twice; a failed claim write starts no connection. Slots are accepted only inside their one-minute window, missed slots are skipped rather than replayed, a nonexistent spring-forward time is skipped, and a repeated fall-back time runs at most once. Pruning removes only claims before the current local date, so retention changes cannot re-enable today's slot.

Metrics are derived only from the two samples the collector takes inside one execution. CPU total comprises user, nice, system, idle, iowait, irq, softirq and steal, with guest and guest_nice excluded from the total, and usage is `100 × (Δtotal − Δidle − Δiowait) / Δtotal`. Memory used is `MemTotal − MemAvailable`. Disk values come from local persistent mounts, excluding `proc`, `sysfs`, `tmpfs`, `devtmpfs`, `overlay` and `squashfs`, and mounts are never summed. Network rates are per-interface counter deltas divided by the actual positive uptime difference inside the same collection, with `lo` excluded and interfaces never summed. Values that cannot be derived are unavailable, never zero; a collection with at least one available resource is partial, and a non-Linux host, no usable resource, a script failure or an overall timeout fails.

Configuration and history are profile-local. Targets and settings live in an encrypted `server_monitor.enc.json` written atomically with the application master password; an unreadable or undecryptable document is reported and never overwritten. Samples and slot claims live in `server_monitor.db`. Passwords stay inside the encrypted record, and safe views expose only whether a password is present. Neither file is added to iCloud or Git synchronization. Settings default to automatic collection enabled, interval mode, five minutes, `09:00` and seven-day retention, and are validated in both frontend and backend without silent correction; only the active mode controls scheduling while inactive-mode values are retained.

Generation invalidation ties the scheduler to user intent. Pause, delete, connection-source changes, mode changes, global disable and application shutdown increment a per-target generation, invalidate and close owned sessions, and cause late results to be rejected before they can publish, persist or satisfy a manual refresh. A replacement owner waits for the old target owner to release its session.

## Alternatives considered

- Installing an exporter or monitoring agent: declined because it requires remote packages, a service, a listening port and firewall changes, and it contradicts the project's no-remote-installation boundary.
- Reading an HTTP metrics endpoint or opening a forwarding port: declined because it adds network surface and configuration on the host, and forwarding belongs to saved SSH tunnels rather than monitoring.
- Reusing saved SSH tunnel records for monitoring connections: declined because a tunnel has a persisted forwarding identity and user intent, while monitoring only needs its own short-lived command session; coupling them would let either lifecycle disturb the other.
- Refactoring the whole SSH architecture into one generic connection service: declined because the delivered narrow adapter reuses the existing configuration, authentication and host-key behavior without changing unrelated tunnel, terminal or SFTP contracts.
- Deriving network rates across separate scheduled samples: declined because intervals can be paused, delayed, restarted or longer than the display claims; rates use only the approximately one-second window inside one collection.
- Summing disk mounts or network interfaces into one total: declined because mounts can describe the same device and interfaces have different roles; the tool names one mount and one selectable interface instead of inventing an aggregate.
- Treating an unknown field as zero: declined because zero is a real measurement; unavailable values remain unavailable and produce partial or failed states.
- Replaying missed daily slots after sleep or exit: declined because a late batch would misrepresent when the observation was taken and could authenticate many hosts unexpectedly; missed slots are skipped and only future times are armed.
- Storing credentials in plaintext or exposing them through snapshots: declined because the configuration store already provides master-password encryption and events must remain safe to consume; only password presence is exposed.
- Adding a charting dependency for the trends: declined because the existing lightweight SVG history is sufficient and avoids a new runtime dependency.
- Polling hidden pages or triggering remote work from navigation: declined because scheduling belongs to the backend process and hidden views must not issue page queries or duplicate collection work.

## Consequences

- The Server Monitor tool is reachable from the hub and launcher with a persistent target list, four metric cards, an interface selector, a gap-aware 24-hour/seven-day history, add/edit/delete/test/pause/resume/collect-now actions, and a Services → Server Monitor settings section whose save, reset and dirty state are independent of other sections.
- Interval mode owns one persistent session per target with serialized 30-second keepalives and rearms after each completion; daily mode owns one one-shot session per collection and leaves no session between times. At most four collections run concurrently, each target is single-flight, and a manual collision shares the scheduled result.
- Daily scheduling is future-only and durable: a target/date/time claim is written before network work, survives restarts and clock rollback, is limited to its one-minute window, and is never replayed when missed. Pruning keeps today's and future claims, so shortening retention cannot rerun a slot.
- Metrics remain self-contained: CPU, memory, disk and per-interface network values derive only from the two samples in one collection, unavailable fields stay unavailable, partial results are labeled, the last good snapshot keeps its timestamp and error, and daily mode reports waiting instead of treating a closed session as offline.
- Targets, credentials and settings are encrypted in the profile-local `server_monitor.enc.json`; samples and claims are in the local `server_monitor.db`. Safe state and events omit passwords, neither file is synchronized, and an unreadable configuration is never replaced with defaults.
- Rollback is additive and local: quitting the app releases owned sessions, reverting the feature leaves both files for a later reinstall, older binaries ignore them, and no remote service or configuration was installed. A controlled real SSH/Linux smoke ran against a local Docker Debian target at `127.0.0.1:2222` with user `monitor`, and both ignored smoke tests passed: persistent collection performed three collections on one authentication, one-shot sessions authenticated and disconnected per collection, interval collection opened a persistent connection, pause and the daily-mode switch reduced established connections to zero, re-enabling and interval restored a connection and a new sample, and shutdown closed connections; container logs recorded 5 accepted-password authentications and 5 disconnects. Native visual inspection in the packaged application at 800×600 and 1440×900, in Chinese and English and in light and dark themes, was not verified, and the user accepted it as a bounded recorded gap rather than a pass.
- Supersession assessment: neither [Toolbox Plugin Registry Replaces Hand-Maintained Tool Lists](../architecture/2026-09-25-toolbox-plugin-registry.md) nor [SSH Tunnel Reconnect Resilience Uses a Persistent Supervisor, a Round-Trip Probe, a Desired-Running Watchdog and a Wake/Window Retry Poke](../bug-fix/2026-09-30-ssh-tunnel-reconnect-resilience.md) is superseded. The registry decision remains the source of tool surfaces, and the tunnel supervisor decision remains the source of tunnel intent and supervision; monitoring adds its own adapter and records without changing either contract.
