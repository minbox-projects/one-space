# Agent Note: API Gateway Model List Tab Reuses the Shared Aggregation

Status: implemented

English | [中文](2026-09-18-api-gateway-model-list-tab.zh.md)

## Problem

The API Gateway page exposed its aggregated local models only through the `Aggregated models` metric card, which opens `AggregatedModelsDialog`: the dialog lists every served model at once, offers no search, and closes with the operator's next click. As mappings grow, an operator cannot keep the served models in view or find one quickly. The aggregation already existed as `aggregateModels`, and a new surface had to avoid becoming a second implementation whose count or model names could disagree with the card and the dialog.

## Decision

The page gains a `Model list` tab backed by the named export `ModelListPanel({ providers })` in `src/components/ApiGateway/ModelListPanel.tsx`. The panel derives one row per aggregated local model from `aggregateModels(providers)` and resolves each row's display name with the new exported `resolveAggregatedModelName(entry)`. `src/components/ApiGateway/index.tsx` adds `"models"` to `ApiGatewayTab` directly after `"providers"`, uses the `Boxes` icon, shows a badge count of `aggregateModels(config.providers).length` — the same call that feeds the `Aggregated models` metric card — and keeps the panel mounted with the existing `hidden` class pattern so the typed query survives tab switches.

To make mapping display names available to the list, `AggregatedModelProvider` gains an optional `displayName?: string`. `aggregateModels` sets it only for mapping sources whose trimmed `mapping.display_name` is non-empty, omits the property for undeclared or all-whitespace names, and never sets it on a provider's default-model source. `resolveAggregatedModelName` returns the first non-empty `displayName` in the aggregation order; when no source declares one, it returns the `upstreamModel` of the first source with `isDefault === false`, falling back to `providers[0]` and then to `entry.model` when the entry has no sources. Each row shows three columns: the model ID, the resolved model name and the upstream models, where every source appears in the existing aggregation order as the upstream provider name plus the upstream model ID and default-model sources reuse the existing `apiGatewayAggregatedModelDefaultBadge` badge.

A single search box filters rows with a `query.trim().toLowerCase()` substring match against the model ID and the resolved model name only; an empty or whitespace-only query shows every row, and upstream provider names and upstream model IDs are not searchable. The panel renders the empty state `apiGatewayModelListEmpty` when the aggregation has no rows and the no-match state `apiGatewayModelListNoMatch` when a non-empty query filters everything out. `src/i18n.ts` adds eight keys in English and Chinese: `apiGatewayModelListTab`, `apiGatewayModelListSearch`, `apiGatewayModelListSearchPlaceholder`, `apiGatewayModelListIdColumn`, `apiGatewayModelListNameColumn`, `apiGatewayModelListUpstreamColumn`, `apiGatewayModelListEmpty` and `apiGatewayModelListNoMatch`.

## Alternatives considered

- Let the panel aggregate and resolve names on its own instead of reusing `aggregateModels` and one exported name helper: declined because the tab badge, the metric card and the dialog must describe one aggregation, and a second implementation could disagree with the surface it summarizes.
- Search upstream provider names and upstream model IDs as well: declined because the tab indexes local models and a row must match only when its model ID or name contains the query; matching upstream-only text would keep rows whose model does not match, which the search scope explicitly excludes.
- Replace `AggregatedModelsDialog` with the tab or remove the dialog: declined because the metric card keeps its click-through overview without switching tabs; the tab and the dialog coexist and share the same source, so neither surface has to replace the other.

## Consequences

- The `Model list` tab, the `Aggregated models` metric card and `AggregatedModelsDialog` all derive from `aggregateModels` and the same predicate (provider `enabled`, mapping `enabled && !auto_disabled`), so their model sets cannot diverge and stay aligned with `GET /v1/models` and terminal sync, which apply the same predicate in the backend; disabling a provider, disabling a mapping or a row's automatic disabling removes the affected rows from the panel without a page reload.
- `src/lib/apiGateway.ts` publicly exports `resolveAggregatedModelName`, and `AggregatedModelProvider` carries the optional `displayName`; existing aggregated entries keep their shape because the property appears only when a mapping declares a non-empty `display_name`, so the dialog and metric-card expectations are unchanged.
- Search state lives in the always-mounted panel: typing a query, switching to another tab and switching back preserves the query and the filtered rows; with no enabled models the panel shows the empty state, and a non-empty query matching nothing shows the no-match state and no data rows.
