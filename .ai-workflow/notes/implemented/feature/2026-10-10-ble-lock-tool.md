# Agent Note: BLE Lock Tool Automates Mac Session Actions for One Bluetooth Device

Status: implemented

English | [中文](2026-10-10-ble-lock-tool.zh.md)

## Problem

OneSpace had no native way to lock the Mac when a selected Bluetooth Low Energy (BLE) device moves away and to wake it when the device returns. The tool had to be built on the project's existing macOS toolchain without copying code from, depending on, or referencing any external BLE-unlock project or its configuration. It also had to respect the app's established boundaries: the frontend owns the tray menu model and the shared runtime-status store, configuration must not enter synchronized storage, and the login password must never be persisted outside the macOS Keychain.

The behavior spans a single-device RSSI presence state machine, profile-local configuration, Keychain password storage, Accessibility-gated automatic unlock, display wake and system-sleep limits, best-effort media pause/resume, screensaver/lock/display outcomes, tray controls and localized failure feedback. The public command and event contract and the exact data boundaries therefore had to be recorded in the same change as the code.

## Decision

The tool is an independent native implementation whose frontend surface, backend runtime and data boundaries follow the frozen contract.

- Toolbox and IPC contract: `src/toolbox/plugins/ble-lock.ts` registers the `ble-lock` descriptor on the `hub` and `launcher-quick` surfaces with the alias `ble-lock` and a lazy `loadComponent`; `src/components/BleLockTool.tsx` is the tool UI and `src/lib/bleLock.ts` holds the DTOs, the `ble_lock_get_status`, `ble_lock_save_config`, `ble_lock_scan_start`, `ble_lock_scan_stop`, `ble_lock_select_device`, `ble_lock_clear_device`, `ble_lock_set_password`, `ble_lock_delete_password`, `ble_lock_request_accessibility` and `ble_lock_lock_now` wrappers, the `BLE_LOCK_STATUS_EVENT` / `BLE_LOCK_DEVICES_EVENT` constants and the platform guard. The backend publishes `ble-lock-status-updated` and `ble-lock-devices-updated`, returns `BleLockStatus` from every command, and reports failures only as a stable `BleLockError` code plus safe detail using the fixed code set (`platform_unavailable`, `bluetooth_powered_off`, `bluetooth_unauthorized`, `bluetooth_unsupported`, `device_not_selected`, `device_unavailable`, `invalid_config`, `keychain_unavailable`, `password_not_configured`, `accessibility_required`, `system_sleep`, `native_action_unavailable`, `media_control_unavailable`).
- Monitoring: `src-tauri/src/ble_lock/central.rs` owns exactly one CoreBluetooth UUID, connects and periodically reads RSSI in the default active mode, and in passive mode consumes advertisements without ever connecting; it cancels or disconnects on selection replacement and suppresses stale callbacks for a replaced device, and returns `platform_unavailable` on non-macOS targets.
- Presence: `src-tauri/src/ble_lock/state.rs` smooths with the mean of at most the five most recent valid readings, transitions to away after the lock threshold is continuously crossed for the lock delay, transitions to lost after the no-signal timeout, emits at most one lock per away/lost episode, cancels a pending lock on a valid recovery, and arms unlock only after an away/lost observation followed by a near transition.
- Configuration: `src-tauri/src/ble_lock/config.rs` persists a standalone, unsynchronized `ble_lock.json` in the current build profile's application directory (`~/.config/onespace` for Release, `~/.config/onespace-dev` for Debug) that is not part of `StorageConfig` or sync and has no password field; it validates before writing so a rejected configuration never replaces the last valid bytes, accepts RSSI thresholds only from `-95` to `-30` in `5` steps, defaults both RSSI actions and every optional toggle to disabled and defaults the lock delay to `10` seconds and the no-signal timeout to `30` seconds, requires unlock RSSI to be greater than or equal to lock RSSI only when both are enabled, accepts a lock delay of `1..=3600` seconds and a no-signal timeout of `5..=3600` seconds.
- Password and Keychain: `src-tauri/src/ble_lock/native.rs` stores the login password only as a current-user generic-password Keychain item, using the Release service `com.onespace.desktop.ble-lock` and the Debug service `com.onespace.desktop.ble-lock.dev` with non-synchronizable storage, and exposes only a configured/not-configured state. The Keychain account is resolved by the checked public `MacPlatform::current_account_name()` (Foundation `NSUserName`, `platform_unavailable` on non-macOS) instead of a handwritten passwd FFI; `BleLockPlatform::current_user_account` delegates to it and the Keychain operations reject an empty account. `BleLockNativeController::snapshot()` reads the Keychain exactly once and surfaces a stable `keychain_unavailable` in `snapshot.last_error` when the read faults (previously a silent `false`), clears only that ephemeral error when the read recovers while preserving unrelated persistent errors, and `ble_lock_get_status` exposes it without ever serializing a secret.
- Automatic unlock gates: unlock applies only to the current ordinary locked user session and only when the password is configured, Accessibility is trusted, the Keychain item is readable, the unlock threshold is enabled and a near transition occurred; at most one injection is attempted per qualifying transition, a wrong password does not create a retry loop, and wake-without-unlocking suppresses injection.
- Native seam and capability gates: `BleLockPlatform` is the single OS seam, and the controller isolates each macOS capability behind it while labelling its real availability — the Accessibility trust query, the one-shot CGEvent unlock and the IOPM user-activity assertion are public APIs, while the ordinary login-session lock-state observation, the best-effort MediaRemote pause/play and the private locked-key/display seams are private or undocumented; media control runs only for confirmed playing media and only resumes what the current lock cycle paused, an unavailable capability reports its stable code and continues the lock, and an unobserved result is never reported as success. The controller also owns the radio-feedback adapter `observe_bluetooth_state(state: BleBluetoothState)`, which maps the state to the stable `bluetooth_unsupported` / `bluetooth_powered_off` / `bluetooth_unauthorized` codes and clears only stale radio errors on `PoweredOn`; the real `BleCentralEvent::State` and `Authorization` handlers consume it, replacing the earlier duplicate inline taxonomy.
- Lifecycle: `src-tauri/src/app_runtime/run_app.rs` registers the native module through `#[path = "../ble_lock/native.rs"] pub(crate) mod ble_lock_native;` and installs the process-owned runtime once, the system wake seam rebuilds the monitor, connection and scan after sleep, and `shutdown_runtime` runs BLE cleanup through the existing idempotent `shutdown_runtime_services` path. `note_system_wake()` returns `bool` — `true` while alive, `false` once stopped, and it never clears the stopped state; the wake seam early-returns before any monitor/device rebuild on `false`, and the main-thread central dispatch checks the stopped state before allocating a central so queued main-thread work after exit cannot resurrect resources, leaving observers inert after shutdown.
- Frontend runtime and tray: the `ble-lock` service in `src/lib/runtimeStatus.ts` consumes the typed status snapshot and the `src/App.tsx` bridge subscribes `BLE_LOCK_STATUS_EVENT`, while the frontend-owned `src/lib/trayMenu.ts` gains the `ble-lock-controls` submenu with the status, Lock Now, Set Device, Unlock RSSI, Lock RSSI, Wake on Proximity, Wake without Unlocking, Pause while Locked, Use Screensaver and Turn Off Display items; outside the macOS Tauri runtime both the tool and the tray controls stay visible but resolve the unavailable snapshot and never invoke a native command.
- Manual priority: Lock Now locks independently of proximity, and a still-near device cannot unlock until OneSpace observes away or lost and then a new near transition.

## Alternatives considered

- Reusing or copying an external BLE-unlock project, its configuration or its dependency: declined because the feature had to be an independent CoreBluetooth implementation with no external address, dependency, update check or reference configuration.
- Storing BLE settings in the synchronized `StorageConfig` or the shared-profile schema: declined because device selection and thresholds are local machine preferences that must not sync across devices.
- Storing the login password in OneSpace configuration, the Secrets file, logs, frontend storage or event payloads: declined because the password is a macOS credential that belongs only in a non-synchronizable Keychain item, and the tool must never return it.
- Supporting several monitored devices or inferring a physical distance from RSSI: declined because the contract monitors at most one device, never decodes a Bluetooth MAC address and never reports a distance in meters.
- Building the controls into the Rust tray menu: declined because the tray model is frontend-owned; the user-mandated `ble-lock-controls` submenu is delivered as a scoped extension of the existing contract instead.
- Calling the macOS lock, media and display APIs directly and treating an invocation as success: declined because those capabilities can be missing or private; each is isolated behind the OS seam, reports a stable capability error and is confirmed through observed state.
- Promising detection or a whole-machine wake while macOS is in system sleep: declined because system sleep pauses the proximity decision and only the display is woken; monitoring is rebuilt after wake.
- Letting a near device immediately re-unlock after a manual lock: declined because manual lock must win until an away or lost observation followed by a near transition re-arms unlock.

## Consequences

- The delivered public paths and symbols are recorded in `MEMORY.md` and the authoritative `.ai-workflow/index/navigation.json` as the frontend `ble-lock` and backend `ble-lock-backend` features, and `docs/USAGE.md` and `README.md` document the user-facing setup and boundaries in Chinese.
- Data boundaries hold: `ble_lock.json` lives only in the profile application directory outside `StorageConfig` and sync, the Keychain item is current-user and non-synchronizable with the profile-specific service names, and no password appears in configuration, sync data, frontend storage, logs, events or errors.
- Platform and failure behavior is explicit: a non-macOS build, a browser preview or a non-Tauri WebView keeps the entry visible with `platform_unavailable` and zero native invokes, and a failure in one capability never blocks the independent configuration, status or manual actions that remain available.
- The tray and the tool read the same status snapshot, the tray threshold and toggle check marks follow that snapshot, and the App action handler applies the screensaver/display-off mutual exclusion, so the tool and tray consume the same shared snapshot.
- Manual lock keeps priority: after Lock Now a still-near device does not unlock, and eligibility returns only after away or lost followed by near.
- Verification recorded for this delivery: the inline native tests moved unchanged to the test-only `src-tauri/src/ble_lock/tests/native.rs` (registered with `#[cfg(test)] #[path = "tests/native.rs"] mod tests;`) and now cover the four review regressions (safe account lookup, snapshot Keychain read fault, Bluetooth-state radio adapter, stopped-state wake), so `cargo test --manifest-path src-tauri/Cargo.toml ble_lock --lib` exits 0 with 48 passed, 0 failed and 0 ignored (1241 filtered) — 19 monitor, presence and configuration tests plus 29 native tests (25 moved + 4 added) — replacing the earlier 44-passed run after the initial RED, active-RSSI, native-warning, threshold, device, sleep and async-media regressions; the scoped nine-file frontend run exited 0 with 331 tests in 9 files after the four platform/l10n regressions; `npm run lint` exited 0 with 0 errors and 409 pre-existing warnings with 0 problems in the new files; `npm run build` exited 0 and emitted a lazy `BleLockTool-*.js` chunk (12.02 kB, gzip 3.39 kB) separate from the App chunk.

- The macOS smoke checklist was not run after the review repairs and is not marked passing: the Bluetooth TCC prompt and off/denied states, active and passive RSSI, Keychain save/read/delete plus Debug/Release isolation, Accessibility, ordinary Lock Now and the guarded unlock, screensaver and display-off, MediaRemote playing/not-playing/unavailable, and sleep recovery with repeated exit cleanup each remain a manual procedure with expected results only. - Supersession: no full or partial supersession.
