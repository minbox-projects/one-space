# Agent Note: AI Gateway Provider Daily Usage History

Status: implemented

English | [中文](2026-10-14-ai-gateway-provider-usage-history.zh.md)

## Problem

The gateway recorded one request-log detail row per completed attempt in `ai_gateway_usage.db` and answered both usage and log queries from that detail table. The configured detail retention (default 90 days, accepted range 1–365) permanently deletes older rows on every write, so it also deleted the only basis for statistics: the oldest visible date moved forward as rows expired, per-provider totals were recomputed from whatever detail remained, and a provider could not be inspected across a period longer than the retention window. Ordinary grouping and filtering key on the recorded display name, which is neither unique nor stable, so a renamed provider split into two series, two providers that share one name merged, and a deleted provider could not be reached at all. There was no durable per-provider calendar, no stable identity, and no way to tell a day with no requests apart from a day whose records had already been deleted.

## Decision

Persist additive per-provider daily summaries beside the request-log detail in the current profile's `ai_gateway_usage.db`, and expose them through a new Provider history subtab.

| Table | Key | Stored facts |
| --- | --- | --- |
| `provider_daily_usage` | `(provider_id, day)`, where `day` is a UTC+8 `YYYY-MM-DD` | Identity and name recorded at write time, first and last request timestamps, and the additive metrics that reconcile with the detail rows |
| `provider_usage_metadata` | `continuity_start_day` | The continuous-recording boundary stamped when the summaries are first created |

Only days that recorded terminal usage are stored, and only additive metrics plus the recorded identity/name and first/last timestamps; the complete UTC+8 calendar, the zero-versus-unavailable classification and every ratio are generated on read, and cumulative totals sum the additive daily values while the cache hit rate is derived once from the summed eligible numerator and denominator, never by averaging percentages. The feature is profile-local and stores no request or response bodies, no headers and no credentials.

The usage database advances through its own `PRAGMA user_version` from 1 to 2 inside the permanent migration module, while the encrypted configuration schema stays 3. Within a `BEGIN IMMEDIATE` write transaction the migration re-checks the version after taking the write boundary, runs the legacy `result = 'cancelled'` cleanup only when the stored version is below 1, then creates the summary tables, backfills the retained terminal rows that are successful, valid-result and have a nonblank provider id, writes the continuity boundary and stamps version 2. The backfill is one transaction, so a repeated or concurrent open cannot duplicate it and a failed migration rolls back with no partial summaries and no advanced marker and is retried on a later open; original tokens, amounts and total fields are never rewritten.

Detail insertion and its eligible daily contributions commit in one transaction for both the single (`append_with_accounting`) and batch (`append_batch_with_accounting`) append paths, and retention runs only after that unit succeeds and deletes only detail rows, so a mid-batch or summary-update failure leaves neither partial detail rows nor partial summaries. Contributions reuse the existing cache-eligibility and unpriced predicates, and attempts and blank-provider rows never contribute. History reads use one consistent read transaction so totals and daily values cannot observe different append snapshots.

Two commands join the existing four: `ai_gateway_usage_providers` returns the union of configured and historical identities keyed by exact nonblank provider id (the current configured name wins, a deleted identity keeps its latest recorded name, and an unused configured provider reports `has_usage = false`), and `ai_gateway_provider_usage_history(provider_id)` returns the calendar, coverage and metrics (a blank id is an error and an unknown nonblank id returns empty history). `ai_gateway_request_logs` gains optional `provider_id` and `day` arguments: a strict UTC+8 `YYYY-MM-DD` half-open window takes precedence over the quick range and composes by AND with the existing name, status, model and grouping filters, blank or invalid values are actionable errors, an unknown nonblank id returns empty data, and omitting both keeps the existing six-key invoke payload unchanged.

On the frontend, `ProviderUsageHistoryPanel` is a third subtab inside Usage and logs. A stable-ID selector uses the identity union with duplicate-name disambiguation, deleted markers and an unused-provider empty state. It shows the earliest available day, the continuity start and the current end day, a coverage explanation when earlier retained history may be incomplete, cumulative cards, a scrollable token/request/cost trend and a complete daily table that keeps full dates across years; unavailable historical days show a placeholder rather than a numeric zero, today is marked ongoing, and only no-request days inside continuous coverage show zero. A daily row opens the existing request-log view focused on the exact provider id and UTC+8 day: the focus is one-shot, starts at page 1 with attempts visible and 50-row pagination, and returning restores the same provider history, while an explicit clear restores ordinary quick-range browsing and the model-pool shortcut clears the provider/day focus and still refilters its alias. It distinguishes an empty retained day, an ordinary no-match filter and a query error, and it rejects superseded responses and issues no query while inactive. All new text is bilingual.

## Alternatives considered

- Keep only permanent detail rows, or rescan and reprice the whole history on demand, instead of durable daily summaries: declined because permanent retention contradicts the configured 1–365 day detail boundary, and a lifetime rescan would recompute values as detail expires and as prices change, whereas a stored additive summary survives cleanup and keeps recorded amounts authoritative.
- Group the new history by the recorded provider name instead of a stable id: declined because a name is neither unique nor stable, so two providers that share one name would merge and a renamed provider would split; ordinary log grouping and filtering keep their recorded-name semantics, and the new history is the stable-ID supplement rather than a replacement.
- Classify pre-migration missing days as zero rather than as unavailable: declined because the migration can only recover the rows still present, so a missing historical day may simply have been cleaned long ago; zero is reserved for a no-request day inside known continuous coverage, and earlier retained values are qualified as possibly incomplete.
- Write detail rows and summary contributions in separate statements: declined because a crash between them would leave a detail row whose summary is missing or a summary that has no detail; one transaction for both append paths, with retention deleting only detail rows afterwards, keeps them consistent.

## Consequences

- The two summary tables and usage-database version 2 are additive; the encrypted configuration schema stays 3, no request-log column or ordinary query meaning changes, and an older binary that does not maintain summaries pauses the continuity guarantee while it writes.
- Detail retention still permanently deletes request-log rows at the configured 1–365 day window (default 90), but it no longer deletes any daily summary, so the per-provider calendar and cumulative totals survive until the database itself is removed.
- Rollback removes the feature code without a destructive down-migration and retains the additive tables; a matching current-profile database backup must be saved before downgrading, and returning to the new binary requires explicitly treating the downgraded interval as outside the continuity guarantee or restoring that backup, because deleted downgraded traffic cannot be recovered and no automatic downgrade reconciliation or gap-recording API is added.
- The commands `ai_gateway_usage_stats`, `ai_gateway_request_logs`, `ai_gateway_usage_retention_get`, `ai_gateway_usage_retention_save`, `ai_gateway_usage_providers` and `ai_gateway_provider_usage_history` are exported from `lib.rs` and registered in `app_runtime/run_app.rs`; the frontend uses typed wrappers and DTOs and does not build command strings directly.
- `MEMORY.md` and the `ai-gateway` / `ai-gateway-backend` navigation responsibilities describe this storage, identity, coverage and command contract, and `navigation.md` is regenerated from the authoritative JSON; `docs/USAGE.md` explains the third subtab, that the earliest available date is not a provider's actual first use, that only retained history is recoverable, that general statistics remain scoped to detail retention and that daily history is durable.
- Partial supersession: [API Gateway Usage Stats and Request Logs](../architecture/2026-09-17-ai-gateway-usage-logs.md) is retained and cross-linked; this record replaces only the statistics-lifetime boundary recorded there — general statistics are still computed from retained detail rows, while the new provider/day summaries persist independently of detail cleanup — and its SQLite logging, record-time price freeze, retention, `group_by` contract and `local_model` facet decisions remain in force.
- The recorded-name provider grouping and filtering decision of [Gateway Request Logs Group and Filter by Provider Name](2026-09-28-gateway-log-provider-grouping-filter.md) continues to govern ordinary request-log grouping and filtering; the stable-ID history here is supplemental and does not change that contract.
- The usage-database version advances from 1 to 2 under the permanent version gate recorded by [Gateway Migration Is Permanent and Version-Gated](../architecture/2026-09-24-version-gated-gateway-migration.md), whose migration decision and `cancelled`-cleanup gate remain unchanged.
