# Agent Note: Automatic Template Sync Notifies the Message Center on Real Mapping Changes

Status: implemented

English | [中文](2026-09-24-ai-gateway-template-auto-sync-notification.zh.md)

## Problem

The [automatic template refresh](../feature/2026-09-23-template-auto-refresh.md) synced every URL-backed provider template on the persisted interval and propagated the result to the providers bound to it, but it did so silently. An operator could not tell when an upstream catalog had actually gained or retired models for a bound provider short of opening the template and reading the mapping list, so a notification was needed — with a deliberately narrow trigger. It had to fire only on real mapping additions and never for field-only differences or failed refreshes. It also could not become a second sync implementation, and it could not expand the backend command surface or the message schema. [Core Workflows Cleanup and Optimization](../architecture/2026-10-09-core-workflows-cleanup-and-optimization.md) later moved production of the message into the backend; this record is retained for the additions-only decision.

## Decision

The backend derives the additions-only diff. `src-tauri/src/ai_gateway/templates.rs::template_sync_addition_notices(before, after, template_id)` compares the providers bound to the template between the pre-sync `before` and the post-sync `after` configuration and emits one notice per provider that gained at least one mapping. Only a mapping whose `upstream_model` was absent from the same provider before the sync qualifies; a provider not bound to the template is ignored, and the output follows the provider and mapping order of the post-sync configuration. Field-only differences (display name, effective protocol, provider name, `base_url`), mappings already disabled before the sync, models skipped by the template or listed in `ignored_models`, and templates with no bound provider all do not qualify, so a template with no qualifying change produces nothing. The diff runs inside the serialized `modify_config` mutation that already applies the sync, so the same atomic write both persists the result and captures the additions.

After the configuration write stands, `src-tauri/src/ai_gateway/commands.rs::record_template_sync_addition_message` records exactly one message per template with additions through `crate::messages::record_message_silent`. The payload is `{ source: "ai_gateway", category: "template_sync", severity: "info", target: { tab: "ai-gateway" } }` with no `dedupe_key`; its title is localized event-time text (`Provider template <name> models changed` / `服务商模板 <name> 模型已变更`), its summary is the `"; "`-joined affected-provider count and added count, and its detail is a newline-joined per-provider line listing each added mapping's `local_model`, falling back to `upstream_model` when blank.

Failure isolation is explicit. A fatal source problem (network, non-JSON, invalid structure, empty valid model set) leaves the configuration unchanged and returns before any message, so no message escapes. A missing `AppHandle` skips emission while the test seam still captures the input. A retirement-only sync produces no `template_sync` info message; it records the backend provider-scoped `template_mappings_retired` warning instead, so a template sync that only removes mappings is still surfaced. The best-effort terminal refresh runs after the message and retirement recording and never blocks them.

Both the manual `ai_gateway_sync_provider_template` command and the automatic batch now run the same `execute_template_sync` through the shared same-template guard, so a manual sync that adds mappings records the same info message. No new command, persistent format or message-schema field was added; the notification reuses the existing message store and reads the existing encrypted gateway configuration.

## Alternatives considered

- Notifying on every successful sync: declined because an unchanged catalog would produce a message on every tick, so the operator could not distinguish a real catalog change from routine churn.
- Adding a per-template `dedupe_key`: declined because repeated real changes are independent events worth their own record; a dedupe key would silently merge a later addition into an earlier message and hide the second change.
- Generating the `template_sync` info notifications in the Rust backend: declined at the time because the batch loop and failure store lived in the frontend scheduler, so a backend notification would have added a second execution path for no behavioral gain. [Core Workflows Cleanup and Optimization](../architecture/2026-10-09-core-workflows-cleanup-and-optimization.md) later adopted the backend owner and now produces the message there, so this alternative is no longer declined.
- Suppressing the info notification for the manual "sync model list" action: declined at the time because that action already reported its result synchronously. After the backend took ownership both the manual and the automatic path record the additions-only message, so the manual path now produces it too.
- Detecting changes by comparing whole mapping objects rather than `upstream_model` presence: declined because field-only propagation (display name, effective protocol) would then be misreported as a model change.

## Consequences

- Exactly one aggregated message per changed template per sync: the affected-provider count aggregates every bound provider of that template that qualified, and one sync creates one message per changed template, whether the sync was manual or automatic.
- Independent messages for repeated additions: no `dedupe_key` is set, so two consecutive qualifying cycles create two independent messages; this is deliberate and accepted.
- Failures and retirement: a failed sync creates no `template_sync` info message, and a retirement-only sync records the backend provider-scoped `template_mappings_retired` warning instead; the warning appears only after a successful configuration write.
- Message text follows the active language: the title, summary and detail are resolved at creation time through inline `crate::messages::localized` event-time strings, not through the frontend i18n bundles. The four earlier frontend `aiGatewayTemplateSyncNotification*` keys remain in both bundles but are unused by production after [Core Workflows Cleanup and Optimization](../architecture/2026-10-09-core-workflows-cleanup-and-optimization.md) moved message production to the backend.
- No backend command, persistent-format or message-schema change: the info notification reuses the existing message store and only reads the existing encrypted gateway configuration.
- Verification: the delivered behavior tests are `src-tauri/src/ai_gateway/tests/auto_refresh.rs` and `src-tauri/src/ai_gateway/tests/templates.rs` for the additions-only diff and the message record path, `src-tauri/src/ai_gateway/tests.rs` for the shared command behavior, and `src/components/AiGateway/AiGateway.test.tsx` / `src/i18n.test.ts` for the surviving keys and the manual path.
