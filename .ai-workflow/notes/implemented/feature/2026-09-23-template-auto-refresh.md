# Agent Note: Provider Templates Refresh Automatically on a Persisted Interval

Status: implemented

English | [中文](2026-09-23-template-auto-refresh.zh.md)

## Problem

Provider templates with a configured `models_url` fetched their model list only when the operator clicked the sync action on the template card. While the app stayed open, the upstream catalogs drifted and every derived provider kept serving the stale list until someone remembered to click. An automatic refresh therefore had to update every URL-backed template on a schedule while the app runs, but it could not become a second sync implementation: user-disabled mappings had to stay disabled, `ignored_models` entries were never to be resurrected and price rows were not to be created or edited. Two decisions had to be settled first — where the schedule lives and how a failed unattended refresh surfaces without spamming the operator — and the interval itself had to persist, default to 60 minutes for existing files, accept `0` as disabled and stay validated on both sides. This record originally delivered the schedule in the frontend; [Core Workflows Cleanup and Optimization](../architecture/2026-10-09-core-workflows-cleanup-and-optimization.md) later moved ownership to the Rust process and is the authority for the current lifecycle.

## Decision

The interval is persisted as `GatewayConfig.template_auto_refresh_minutes: u32` in `src-tauri/src/ai_gateway/types_config.rs` with `#[serde(default = "default_template_auto_refresh_minutes")]` and is always serialized, so a file without the field reads as 60 (an older file is upgraded once by the version-gated migration) and a pre-feature build ignores the unknown field. Public constants `DEFAULT_TEMPLATE_AUTO_REFRESH_MINUTES = 60`, `MIN_TEMPLATE_AUTO_REFRESH_MINUTES = 10` and `MAX_TEMPLATE_AUTO_REFRESH_MINUTES = 1440` pin the contract. Read-time normalization (`normalize_template_auto_refresh_minutes`) keeps `0` and 10–1440 values as stored and falls back to 60 for anything else; save-time validation (`validate_template_auto_refresh_minutes`) accepts only `0` or 10–1440 and rejects everything else with an actionable error before any write. The commands `ai_gateway_template_auto_refresh_get`, `ai_gateway_template_auto_refresh_save(minutes: i64)` and `ai_gateway_template_auto_refresh_status` in `src-tauri/src/ai_gateway/commands.rs` are registered in `src-tauri/src/app_runtime/run_app.rs`; the save returns the persisted value it re-read after writing and calls `auto_refresh::request_rearm()`, which re-arms the process schedule without running an immediate batch.

The Settings `ai-gateway` partition in `src/components/SettingsView.tsx` adds a whole-minute input: `0` disables, otherwise 10–1440, and it displays the persisted value, so a config without the field shows 60. `parseTemplateAutoRefreshInput` blocks empty, non-numeric and out-of-range input before any command is invoked and reports `apiGatewayTemplateAutoRefreshInvalid`; a backend rejection is mapped to the same localized message instead of the raw error string. After a successful save the view re-reads `aiGatewayTemplateAutoRefreshGet()` and calls `notifyTemplateAutoRefreshIntervalChanged()`. That frontend notification seam is retained in `src/lib/aiGateway.ts`, but the process scheduler is re-armed by the backend command, not by the frontend subscription.

The schedule is owned by the Rust process in `src-tauri/src/ai_gateway/auto_refresh.rs`. `start_scheduler` is installed exactly once from `src-tauri/src/app_runtime/run_app.rs` after gateway autostart; installation reads the persisted interval, so a positive value arms the schedule and runs exactly one immediate startup batch, while `0` installs a parked control that a later `request_rearm` can arm without a batch. One batch runs at a time (a tick arriving during a batch is skipped), iterates the eligible templates (non-empty trimmed `models_url`) sequentially in template order, and calls the same `execute_template_sync` path as the manual action. The automatic batch and the manual `ai_gateway_sync_provider_template` share the `start_template_op` / `TemplateOpOwner` / `TemplateOpFollower` guard: an automatic contender skips a busy template, a manual contender awaits and reuses the owner's in-flight result instead of fetching again, and the guard entry is cleared only while it still points at the finishing operation. The batch therefore reuses the manual fetch, replace and propagation semantics verbatim: one atomic encrypted write per template, incremental updates only while fields still equal the previous template values, user-disabled mappings stay disabled, `ignored_models` is never resurrected, no price row of a kept model is created or edited while the price rows of retired models are deleted, and the manual-sync fatal set (network failure, timeout, non-2xx, non-JSON, missing model array, empty valid model set) leaves that template and its derived providers unchanged while sibling successes in the same batch persist.

Failures never toast. Per-template failures live in process memory only: `set_template_failure` records a reason on failure, `clear_template_failure` removes it on success, and `failure_snapshot` exposes the map in template-id order. They are delivered to the UI by `ai_gateway_template_auto_refresh_status() -> TemplateAutoRefreshStatus { failures: [{ template_id, reason }] }` and by `AI_GATEWAY_TEMPLATE_AUTO_REFRESH_UPDATED_EVENT = "ai-gateway-template-auto-refresh-updated"`, emitted only when the failure set actually changes; `synced_at` stays untouched because only a successful sync writes it, and an app restart starts clean. `src/components/AiGateway/useTemplateAutoRefresh.ts` is now a read/subscription adapter: it performs one status read on mount and subscribes to the update event, replacing the whole map each time, with no timers, no sync calls, no in-flight registry and no message builders; `useTemplateAutoRefreshFailures()` keeps its `Record<string, string>` shape. `src/lib/aiGateway.ts` adds `aiGatewayTemplateAutoRefreshStatus`, the `TemplateAutoRefreshFailure` / `TemplateAutoRefreshStatus` types and the event literal. `src/i18n.ts` retains `apiGatewayTemplateAutoRefreshLabel`, `apiGatewayTemplateAutoRefreshInvalid` and `apiGatewayTemplateAutoRefreshFailed` in both languages.

## Alternatives considered

- A Rust-side in-process interval scheduler in the Tauri backend: declined at the time because the backend would need its own runtime loop to start, stop and re-arm on config changes, while the orchestration the batch needs already lived in the frontend command layer. [Core Workflows Cleanup and Optimization](../architecture/2026-10-09-core-workflows-cleanup-and-optimization.md) later adopted this option and moved ownership, failure state, messages and the lifecycle into the process, so this alternative is no longer declined.
- A scheduler mounted only while the `api-gateway` view is visible: declined because refreshes must continue while the operator works in other views; the schedule is process-owned and independent of the mounted page.
- OS-level scheduling (launchd or another system timer): declined because it only fires while the app runs anyway, and it would execute the sync outside the app's locked configuration store and in-memory failure surface, adding a second, unobservable execution path for the same writes.
- Per-template switches or per-template intervals: declined because refresh frequency is a deployment preference rather than a template property; one global interval keeps a single schedule, a single disable value (`0`) and a single validation rule, while a template that should not be fetched can keep its `models_url` blank.
- Background failure toasts matching the manual-sync error channel: declined because an unattended batch would pop one toast per failing template with no operator action to take; the inline reason on the card keeps the failure next to the sync it belongs to, needs no popup and holds no persisted state.

## Consequences

- Interval contract: a config without the field reads as 60, a current-version read does not rewrite the file, and an older file is upgraded once by the version-gated migration; stored `0` and 10–1440 values are reported unchanged and any other stored value normalizes to 60; saves accept only `0` or 10–1440, reject `5`, `-1`, `1441` and non-integers with an error naming the accepted values and write nothing; `0` disables the schedule, and deleting the field restores the 60-minute enabled default rather than disabling it.
- Automatic refresh is the manual sync under a timer: each template fetch, replace and derived-provider propagation goes through the shared `execute_template_sync` / `apply_template_sync_with` path, so user-disabled mappings are never re-enabled, `ignored_models` entries are never resurrected, no price row of a kept model is created or edited while the price rows of retired models are deleted, and a failing template leaves its stored entry and derived mappings unchanged while sibling templates in the same batch still apply; a failed refresh never touches `synced_at`.
- Schedule lifecycle is process-owned: installation runs exactly one immediate startup batch for a positive persisted interval; a Settings save re-arms without an immediate batch; `0` parks the control; a tick during an in-flight batch is skipped; a same-template automatic contender is skipped while a manual contender reuses the in-flight result; templates run sequentially in the listed order; hidden windows do not stop the schedule.
- Failure display: automatic failures are in-memory only and render inline on the matching template card as `Auto refresh failed: <reason>` / `自动刷新失败：<原因>`, never as a toast; the backend clears a template's reason on its next success and an app restart shows no stale reason.
- Listener lifetime and shutdown: `RunningServer` carries a monotonic `generation`, so a faulted listener publishes `running=false` and can restart on the same port while an old exiting task can never clear a replacement; `shutdown_runtime_services` idempotently stops the gateway listener and the template schedule.
