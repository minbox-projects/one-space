# Agent Note: Provider Templates Refresh Automatically on a Persisted Interval

Status: implemented

English | [中文](2026-09-23-template-auto-refresh.zh.md)

## Problem

Provider templates with a configured `models_url` fetched their model list only when the operator clicked the sync action on the template card. While the app stayed open, the upstream catalogs drifted and every derived provider kept serving the stale list until someone remembered to click. An automatic refresh therefore had to update every URL-backed template on a schedule while the app runs, but it could not become a second sync implementation: user-disabled mappings had to stay disabled, `ignored_models` entries were never to be resurrected and price rows never written. Two decisions had to be settled first — where the schedule lives (a Rust-side runtime loop or the frontend that already orchestrates template syncs) and how a failed unattended refresh surfaces without spamming the operator — and the interval itself had to persist in `api_gateway.json`, default to 60 minutes for existing files with no migration, accept `0` as disabled and stay validated on both sides.

## Decision

The interval is persisted as `GatewayConfig.template_auto_refresh_minutes: u32` in `src-tauri/src/api_gateway/types_config.rs` with `#[serde(default = "default_template_auto_refresh_minutes")]` and is always serialized, so an older `api_gateway.json` reads as 60 without migration and a pre-feature build ignores the unknown field. Public constants `DEFAULT_TEMPLATE_AUTO_REFRESH_MINUTES = 60`, `MIN_TEMPLATE_AUTO_REFRESH_MINUTES = 10` and `MAX_TEMPLATE_AUTO_REFRESH_MINUTES = 1440` pin the contract. Read-time normalization (`normalize_template_auto_refresh_minutes`) keeps `0` (disabled) and 10–1440 values as stored and falls back to 60 for anything else; save-time validation (`validate_template_auto_refresh_minutes`) accepts only `0` or 10–1440 and rejects everything else with an actionable error before any write. The commands `api_gateway_template_auto_refresh_get` and `api_gateway_template_auto_refresh_save(minutes: i64)` in `src-tauri/src/api_gateway/commands.rs` read and replace only that field, are registered in `src-tauri/src/app_runtime/run_app.rs`, and the save returns the persisted value it re-read after writing.

The Settings `ai-gateway` partition in `src/components/SettingsView.tsx` adds a whole-minute input: `0` disables, otherwise 10–1440, and it displays the persisted value, so a config without the field shows 60. `parseTemplateAutoRefreshInput` blocks empty, non-numeric and out-of-range input before any command is invoked and reports `apiGatewayTemplateAutoRefreshInvalid`; a backend rejection is mapped to the same localized message instead of the raw error string. After a successful save the view re-reads `apiGatewayTemplateAutoRefreshGet()` and calls `notifyTemplateAutoRefreshIntervalChanged()`. The wrappers `apiGatewayTemplateAutoRefreshGet` / `apiGatewayTemplateAutoRefreshSave` and the notification seam `notifyTemplateAutoRefreshIntervalChanged` / `subscribeTemplateAutoRefreshIntervalChanged` live in `src/lib/apiGateway.ts`.

The scheduler is `useTemplateAutoRefresh()` in `src/components/ApiGateway/useTemplateAutoRefresh.ts`, mounted once in `src/App.tsx` so it is independent of which view is mounted. It reads the persisted interval on mount and again on every notified change, stops the timer when the value is not a positive integer, and otherwise schedules `setInterval` at `minutes * 60_000`. A single in-flight batch guard (`batchInFlightRef.current`) makes a tick that arrives during a batch a no-op. Inside a batch it lists `apiGatewayProviderTemplates()` once, then sequentially skips templates whose `models_url` is blank or whitespace-only, skips templates with an in-flight manual sync through the `setTemplateSyncInFlight` / `isTemplateSyncInFlight` / `clearTemplateSyncInFlight` registry that `src/components/ApiGateway/index.tsx` writes when its own sync starts and settles, and calls the unchanged `apiGatewaySyncProviderTemplate(id)` for the rest. The automatic path therefore reuses the manual fetch, replace and propagation semantics verbatim: one atomic encrypted write per template on a configuration clone, incremental updates only while fields still equal the previous template values, user-disabled mappings stay disabled, `ignored_models` is never resurrected, no price row is ever written, and the manual-sync fatal set (network failure, timeout, non-2xx, non-JSON, missing model array, empty valid model set) leaves that template and its derived providers unchanged while sibling successes in the same batch persist.

Failures never toast. A failed template listing abandons the batch silently; a per-template failure is recorded in memory by `setTemplateAutoRefreshFailure(templateId, reason)` and the matching card renders it inline through `apiGatewayTemplateAutoRefreshFailed` with the interpolated `reason`, while `synced_at` stays untouched because only a successful sync writes it. `useTemplateAutoRefreshFailures()` feeds `ProviderTemplateSection.tsx`, a later automatic success or a manual sync success clears that template's reason, `clearTemplateAutoRefreshFailures()` clears every reason, and the state is module memory only, so an app restart starts clean. `src/i18n.ts` adds `apiGatewayTemplateAutoRefreshLabel`, `apiGatewayTemplateAutoRefreshInvalid` and `apiGatewayTemplateAutoRefreshFailed` in both languages.

## Alternatives considered

- A Rust-side in-process interval scheduler in the Tauri backend: declined because the backend would need its own runtime loop to start, stop and re-arm on config changes, while the orchestration the batch needs (listing templates, ordering the batch, deferring manual syncs) already lives in the frontend command layer; keeping the schedule in `App.tsx` and persistence in the backend gives the same behavior with one execution path and no second lifecycle to reconcile with app startup and shutdown.
- A scheduler mounted only while the `api-gateway` view is visible: declined because refreshes must continue while the operator works in other views; the hook is mounted once in `App.tsx` and its timer does not depend on the mounted page.
- OS-level scheduling (launchd or another system timer): declined because it only fires while the app runs anyway, and it would execute the sync outside the app's locked configuration store and in-memory failure surface, adding a second, unobservable execution path for the same writes.
- Per-template switches or per-template intervals: declined because refresh frequency is a deployment preference rather than a template property; one global interval keeps a single schedule, a single disable value (`0`) and a single validation rule, while a template that should not be fetched can keep its `models_url` blank.
- Background failure toasts matching the manual-sync error channel: declined because an unattended batch would pop one toast per failing template with no operator action to take; the inline reason on the card keeps the failure next to the sync it belongs to, needs no popup and holds no persisted state.

## Consequences

- Interval contract: a config without the field reads as 60 with no migration and reading does not rewrite the file; stored `0` and 10–1440 values are reported unchanged and any other stored value normalizes to 60; saves accept only `0` or 10–1440, reject `5`, `-1`, `1441` and non-integers with an error naming the accepted values and write nothing; `0` disables the schedule, and deleting the field restores the 60-minute enabled default rather than disabling it.
- Automatic refresh is the manual sync under a timer: each template fetch, replace and derived-provider propagation goes through the unchanged `api_gateway_sync_provider_template` / `apply_template_sync_with` path, so user-disabled mappings are never re-enabled, `ignored_models` entries are never resurrected, no price row is ever written, and a failing template leaves its stored entry and derived mappings unchanged while sibling templates in the same batch still apply; a failed refresh never touches `synced_at`.
- Schedule lifecycle: the timer is derived from the persisted interval at startup and recomputed immediately after a Settings save notifies the seam; a `0` value stops it; a tick during an in-flight batch is skipped; a template with an in-flight manual sync is deferred to a later tick; templates run sequentially in the listed order.
- Failure display: automatic failures are in-memory only and render inline on the matching template card as `Auto refresh failed: <reason>` / `自动刷新失败：<原因>`, never as a toast; that template's next success, automatic or manual, clears the reason, and an app restart shows no stale reason.
