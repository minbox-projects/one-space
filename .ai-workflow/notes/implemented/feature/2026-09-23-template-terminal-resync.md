# Agent Note: Template Sync Best-Effort Refreshes Previously Synced Terminal Tools

Status: implemented

English | [中文](2026-09-23-template-terminal-resync.zh.md)

## Problem

Provider-template sync and terminal sync could drift apart. `api_gateway_sync_provider_template` — the shared command behind the manual "Sync models" action and the [automatic refresh scheduler](2026-09-23-template-auto-refresh.md) — refreshed a template's model list and propagated it incrementally to every derived provider, but it wrote no tool-side configuration. A tool that had already been synced through the terminal panel (opencode and/or codex holding a marked `API Gateway` provider record) therefore kept a gateway record built from the previous mapping set until the operator re-ran the terminal sync by hand, so the tool-side model list could lag behind the mappings the gateway had just gained or lost. Closing the gap had two constraints: the propagation had to serve both the manual action and the unattended scheduler without duplicating terminal-sync rules, and a secondary terminal failure had to stay incapable of failing the template sync that had already persisted.

## Decision

`api_gateway_sync_provider_template` now takes an injected `app: tauri::AppHandle` (Tauri supplies it; the frontend-visible argument shape stays `templateId` only) and delegates to `apply_template_sync_with_terminal_refresh` in `src-tauri/src/api_gateway/commands.rs`. The wrapper applies `apply_template_sync_with` first and returns early on failure, so no terminal work starts when the template sync did not succeed. Only after the template sync persisted does it check that at least one upstream provider carries that `template_id`, collect `previously_synced_terminal_tools` and, when the list is non-empty, await one injected terminal-sync call for exactly those tools, swallowing the result.

`previously_synced_terminal_tools` reuses `terminal_targets_from`, so the refresh applies the same "synced" predicate the terminal target list exposes: a supported tool (`opencode`, `codex`, in `SUPPORTED_TERMINAL_TOOLS` order) counts only while it still holds a marked managed gateway record, and the ledger alone never claims an unmarked user provider. The command wires the injected closure to the existing `apply_terminal_sync`, so the refresh is the ordinary terminal sync carrying the full current mapping set: the same marker and ledger rules, default-key resolution, `local_base_url`, opencode activation plus `opencode.json` projection, codex manual activation, and the guarantee that user records, keys and price rows are never rewritten. Tools that were never synced and templates with no bound provider trigger no terminal write.

The service-provider payload read that decides which tools were synced sits inside the best-effort region: its failure degrades to an empty payload, so the refresh is skipped instead of failing the command. Every terminal-refresh error — no enabled local key, tool-provider upsert failure, opencode activation or projection failure — is swallowed, so the template view and its `synced_at` update always stand and no error is surfaced for the secondary step.

## Alternatives considered

- Frontend orchestration: run the terminal sync from the ApiGateway view or `useTemplateAutoRefresh` after the sync promise resolves. Declined because both callers would need the same bound-provider and synced-tool gating plus in-flight bookkeeping, the scheduler would depend on tool state it does not own, and the shared backend command is the only place that already reads the persisted template config and the tool provider list in one flow; keeping the propagation there also leaves both call sites and the wrapper arguments untouched.
- Hard failure: propagate the terminal-refresh error and fail the command. Declined because the refresh is secondary to the model-list sync; an upsert or projection problem would turn a persisted template update with a fresh `synced_at` into a visible failure, and terminal problems stay visible through the explicit terminal commands instead.
- Unconditional refresh: call the terminal sync after every successful template sync regardless of bound providers or synced tools. Declined because unbound templates and never-synced tools have nothing to receive, and the automatic scheduler would churn tool configuration files for templates nobody uses.
- Change detection: refresh only when the fetched model list differs from the stored one. Declined as a second decision surface with no behavioral need: a bound template with synced tools always refreshes, matching the manual terminal sync's replace-wholesale semantics without a comparison that would have to model display names, protocols, enabled flags and incremental propagation.

## Consequences

- Both callers gain the propagation without frontend edits: the manual "Sync models" action and the automatic refresh scheduler run the same command, so a successful sync of a bound template refreshes its previously synced tools, and the frontend's existing post-sync reload shows the new sync time on the terminal panel.
- Write order and preconditions: the template state and derived mappings persist first through the existing single atomic encrypted write; the terminal refresh runs afterwards at most once, and only when a bound provider exists and the synced-tool list is non-empty. Zero bound providers or zero synced tools mean zero terminal calls, and a failed template sync never reaches the refresh stage.
- Best-effort contract: the service-provider payload read failure degrades to "no synced tools" and any terminal-refresh error is swallowed, so the returned template view and the `synced_at` update always stand and no secondary error is surfaced. The refresh adds no new terminal-sync rules: it reuses `apply_terminal_sync`, so [Gateway Reasoning Efforts Sync to OpenCode Model Variants](../architecture/2026-09-20-gateway-reasoning-efforts-in-terminal-sync.md) and the existing ledger and marker semantics apply unchanged.
- Contracts: no schema change, no new persisted field, and the frontend contract stays `templateId`; the added `AppHandle` is Tauri-injected. Rolling back restores template-only syncing; already synced tool records stay valid and can be refreshed manually at any time.
- Supersession: partial. This record partially supersedes the explicit-click write trigger of [API Fusion Terminal Sync Writes an Independent Gateway Provider](2026-09-17-api-fusion-terminal-independent-provider.md), which stated that every write happens only on the user's explicit click — a successful template sync now triggers the terminal write path as well, while its independent gateway provider, marker and ledger decisions remain in force and are reused unchanged. It also partially supersedes the sync write boundary of [Provider Templates Drop Built-in Model Catalogs and Prices](../architecture/2026-09-19-provider-template-manual-model-sync.md), whose "never `terminal_syncs`" claim now holds only for the template-sync stage, and the unchanged-command premise of [Provider Templates Refresh Automatically on a Persisted Interval](2026-09-23-template-auto-refresh.md), whose scheduler now also receives the terminal propagation; every other decision of both records remains in force. The terminal-sync behavior of [Gateway Reasoning Efforts Sync to OpenCode Model Variants](../architecture/2026-09-20-gateway-reasoning-efforts-in-terminal-sync.md) is not superseded; the refresh reuses it unchanged.
- `MEMORY.md` and the `api-gateway-backend` entry in `.ai-workflow/index/navigation.json` record the best-effort refresh, its trigger preconditions and the injected `AppHandle` in the same change, and `navigation.md` is regenerated from the authoritative JSON.
