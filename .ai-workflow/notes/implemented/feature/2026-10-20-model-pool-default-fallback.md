# Agent Note: Model Pools Use an Explicit Last-Stage Fallback Source

Status: implemented

English | [中文](2026-10-20-model-pool-default-fallback.zh.md)

## Problem

A model pool could rotate only its regular candidates. When every regular source was cooling, disabled, missing, key-less or exhausted during the request, the public alias returned the existing all-unavailable error even when the operator had one more real mapping intended to serve those requests. Falling through to an ordinary paid default or a gateway-wide default was deliberately forbidden because it would silently leave the operator-selected pool boundary. The missing decision was a single optional source that the operator selects explicitly, that is used only after the regular stage is exhausted, and that can never compete with or displace a healthy regular candidate.

## Decision

- Add the optional `ModelPool.fallback: Option<ModelPoolCandidate>` under the existing schema 3 record. It carries the same exact source identity as a regular candidate — trimmed provider id, original local model, upstream model and effective protocol — reuses the pool-local reasoning declaration, and keeps the candidate weight range of 1 through 100 with a stored default of 1. Its weight never enters primary scheduling. The fallback copies no credential, endpoint or sibling source. A pool still needs at least one regular candidate; a new reference must resolve against the latest configuration, while an unchanged saved reference may be retained after its source disappears or is disabled, stays visible as unavailable, and can be cleared without substituting a sibling. A fallback that duplicates a regular identity, an empty regular selection, a blank identity or an invalid protocol, reasoning declaration or weight is rejected atomically before any encrypted configuration byte changes.
- Route the fallback as a distinct last stage rather than as another regular candidate. It is reached after the regular runtime set is already empty or excluded at admission, following any permitted regular probe, and after regular finite attempts and their permitted shared probe during forwarding. The fallback receives one pass with the existing in-pass key rotation and at most one shared mapping or key probe for the whole request. It starts no additional delayed retry cycle, and a spent regular retry-wait budget cannot suppress its first pass. It never enters the smooth weighted round robin, the ordinary session-affinity binding or the pool continuation hold.
- Keep healthy and recovered regular candidates first. A compatible healthy regular candidate means the fallback receives no call, and after a fallback delivery or regular recovery the next request gives an eligible regular candidate priority again. A successful fallback closes any stale primary hold instead of publishing a fallback preference; successful regular deliveries keep the existing continuation behavior. The fallback remains limited to current enabled pool aliases, so disabled pools, retired aliases and native Messages pool ingress keep their existing fences, and ordinary model routes never use a pool fallback.
- Reuse the real-source contract for the fallback attempt: exact resolution, enabled state, usable key, health and candidate cooldown including permitted recovery probes, the existing protocol conversion, candidate-local reasoning injection, the caller's effective output limit, and the existing candidate-, key- and mapping-scoped failure settlement. Candidate cooldown ownership stays on the real source. Removing or replacing a fallback identity prunes that identity's owned in-memory cooldown only after successful configuration publication; a failed write prunes nothing.
- Classify a concrete reasoning preference over the configured union of regular candidates plus the fallback, independently of transient readiness, so fallback-only declared support remains reachable. The same union feeds the static catalog in backend status, discovery and OpenCode payloads and the frontend catalog helpers, while regular readiness and candidate status arrays stay regular-only and the fallback is reported as a separate optional status. `auto` injects no controls, and the portable strict-tool validation considers a configured Anthropic fallback as it considers an Anthropic regular candidate. A client validation error or an upstream `ReturnToClient` result ends the request under its existing classification instead of activating another stage.
- Preserve both OpenAI ingresses, streaming and non-streaming, across the three upstream protocols. Transparent fallback is possible only before the first client byte; after output begins the existing ingress-format error and close behavior applies with no replay and no second success terminator. A client disconnect cancels an active attempt or wait and prevents a later fallback attempt, a false successful terminal row, or a false health or hold success. Each completed business request keeps exactly one terminal row: the public alias stays `local_model`, while provider, upstream model, usage, price and native reasoning evidence identify the actual fallback source, and the last observed upstream status, including network status 0, is retained.
- Expose one optional localized “Default fallback model” selector with a none choice, real provider mappings that exclude current regular selections, keyboard operation and the reused reasoning editor. The pool card shows the fallback's provider, source and protocol with its availability and reason separately from regular readiness, including the case of zero ready regulars and a ready fallback. A missing or disabled saved reference stays visible, retainable and clearable, unsaved target and reasoning drafts survive status or configuration refreshes and rejected saves, and cancel performs no mutation. Every new label and validation message exists in English and Chinese with synchronized key lists.
- Preserve compatibility. A missing or null fallback reads as no fallback without migration or a read-time configuration write, so an older pool keeps its existing behavior and schema. An older binary may discard the unknown field when it saves. Disabled or retired pool aliases and ordinary routes keep their existing boundaries, and pool saving preserves providers, prices, credentials and sibling pools.

## Alternatives considered

- Append the fallback to the regular candidate list and let the weighted scheduler decide: declined because it would consume primary weights, order and probe allowance, and could let a last-resort source win a request that a healthy regular candidate should serve.
- Fall through to an ordinary paid default or a gateway-wide default when the pool is exhausted: declined because it silently escapes the operator-selected pool boundary and is not an explicit operator choice.
- Give the fallback a new delayed retry cycle or a second pass: declined because it would exceed the existing finite retry and wait boundaries and duplicate an already bounded attempt policy.
- Store a separate provider, key and endpoint inside the fallback, or borrow a sibling mapping: declined because it would duplicate credentials and break the single source of truth for the real mapping's identity, health and price.
- Promote a successful fallback into the next turn's preference or keep a fallback hold: declined because recovered and healthy regular candidates must regain priority, and a fallback is not a primary source.
- Sum fallback readiness into the regular candidate arrays or readiness counts: declined because the operator needs the regular pool's readiness to stay regular-only, with fallback availability reported as a separate optional status.
- Omit fallback-only reasoning support from the static catalog or strict-tool validation: declined because a configured and reachable source must be advertised consistently and a stored Anthropic fallback can actually serve the request.
- Silently ignore an unavailable saved fallback or infer a substitute source: declined because the operator must retain or explicitly clear the exact saved reference and must never receive an unselected provider.

## Consequences

- A pool alias can now name one real source as a last resort while its regular candidates keep their existing weighted order, finite retries, key rotation and permitted probe. The fallback serves after an empty or excluded regular runtime set and after in-request exhaustion, with one bounded pass and no extra delayed retry cycle.
- The fallback cannot win primary scheduling, ordinary session affinity or a pool continuation hold. A fallback success closes any stale primary hold, while a healthy or recovered regular candidate takes priority again on the next request and successful regular deliveries keep their existing continuation behavior.
- Configuration remains additive under schema 3: no migration and no read-time rewrite, missing or null values read as none, and unchanged saved references survive source removal or disablement for inspection and clearance. New references are exact, duplicate regular and fallback identities are rejected, and at least one regular candidate is still required. Removed fallback cooldowns are pruned only after a successful publication, so a failed save changes neither encrypted bytes nor owned runtime state.
- Observability agrees across surfaces: the static reasoning catalog includes the configured union while regular status stays regular-only, the fallback has its own optional status, discovery and OpenCode rows publish the same static support, and unfiltered readiness never decides a catalog. Fallback attempts retain the public alias and real source identity in one terminal row with the last upstream status, including network status 0.
- Transport boundaries are unchanged: both OpenAI ingresses and all three upstream protocols can serve a pre-output fallback, a post-first-byte failure never replays, and a disconnect cannot produce a later attempt, a false success, health or a hold.
- The operator surface provides a separate optional selector and a separate card line, keeps missing or disabled saved references retainable and clearable, preserves drafts across refreshes and rejected saves, and provides bilingual, keyboard-accessible labels.
