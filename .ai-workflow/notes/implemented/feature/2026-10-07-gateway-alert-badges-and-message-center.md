# Agent Note: Gateway Alert Pills Dismiss per Instance and Archive Provider-Scoped Warnings

Status: implemented

English | [中文](2026-10-07-gateway-alert-badges-and-message-center.zh.md)

## Problem

The two warning pills on AI Gateway provider cards — "N mapping(s) removed from template" and "N mapping(s) auto-disabled" — were permanent read-only hints. They stayed visible for as long as the underlying runtime state held and gave the operator no way to acknowledge a problem that was already known, so a card accumulated stale amber chips. At the same time a mapping row that actually entered `auto_disabled`, or a derived mapping that a template sync retired, was visible only inside an open AI Gateway page: closing the page lost the event, and an operator who never opened the page never learned about it. The automatic template-refresh info message did not close that gap — it counted retired mappings together with additions, so a retirement produced an `info` entry beside the warning the operator actually needed, and even a disable-only sync still produced an info message. The change therefore had to make each pill transient and dismissible per problem instance, remember a dismissal across restarts while showing a resolved-and-recurred problem again, and have the backend record exactly one warning per provider and category without changing the gateway configuration schema, the message schema or the command surface.

## Decision

The front end owns dismissal state in the new module `src/lib/aiGatewayAlertBadges.ts`, persisted as a JSON string array under `AI_GATEWAY_ALERT_BADGES_STORAGE_KEY = "ai-gateway-alert-badge-dismissals"`. Every problem instance is addressed by an opaque key: `autoDisabledAlertInstanceKey(providerId, localModel, upstreamModel)` returns `auto:<provider>:<localModel.trim() || upstreamModel>:<upstream>`, and `retiredMappingAlertInstanceKey(providerId, templateId, upstreamModel)` returns `retired:<provider>:<template>:<upstream>`. `readDismissedAlertInstanceKeys` parses and validates the stored array, `dismissAlertInstanceKeys` merges keys in and persists, and `reconcileDismissedAlertInstanceKeys` keeps only keys that are still current problems and rewrites the stored set only when something was pruned. Every read, parse and write is wrapped, so a missing, corrupt or unavailable storage degrades to session-only memory and never blocks rendering.

`UpstreamProviderList` derives `currentInstanceKeys` from the loaded providers and template views — auto-disabled rows, plus mappings whose `enabled === false` and `isMappingDeprecated(mapping, template)` holds — initializes `dismissedKeys` with `reconcileDismissedAlertInstanceKeys`, and re-reconciles whenever that set changes. An instance that stops being a problem is therefore forgotten and a later recurrence appears again, while a probe re-arm of a still-disabled row keeps the same instance key and therefore the dismissal. Both pills render a keyboard-focusable close control (`type="button"`, localized `aiGatewayAlertBadgeDismissAria`, `stopPropagation` so the card is neither selected nor toggled). Each still-pending pill auto-dismisses `AI_GATEWAY_ALERT_AUTO_DISMISS_MS = 8000` milliseconds after it appears through a `setTimeout` cleared on unmount; the effect is keyed on the joined pending-instance key string, so an unrelated re-render does not restart the countdown while a newly pending instance does. Pill counts and tooltips (`aiGatewayProviderAutoDisabledModelsTooltip` for the auto-disabled pill and the existing `aiGatewayTemplateRetiredMappingsTooltip` for the retired pill) list only the un-dismissed instances.

The backend records one provider-scoped warning when a mapping row actually transitions into `auto_disabled` after a successful configuration write. Both settlement paths in `src-tauri/src/ai_gateway/runtime_http.rs` share the builder: `apply_failure` covers the immediate non-credential 403 disable and the request-end threshold settle is the second path. A transition is detected only for a `false`/absent to `true` flip; once every mutation has settled, the code reads the affected provider's complete current auto-disabled set through `auto_disabled_models` (trimmed `local_model`, falling back to `upstream_model`) and emits `mapping_auto_disabled_message_input`: source `ai_gateway`, category `mapping_auto_disabled`, severity `warning`, provider-scoped dedupe key `ai_gateway_mapping_auto_disabled:<provider_id>`, target tab `ai-gateway` with the provider as `entity_id`, bilingual `messages::localized` title and summary, and the joined set as `detail`. `emit_mapping_auto_disabled` persists exactly one input through `messages::record_message_silent` against the captured application handle; a probe re-arm of an already disabled row, a no-change settlement and a failed write emit nothing. The test-only seam `MAPPING_AUTO_DISABLED_MESSAGE_INPUTS` records the literal inputs.

A successful template sync returns one `ProviderRetirementNotice` per bound provider that newly retired at least one derived mapping in that sync (enabled before the sync, disabled because its upstream model left the template) from `propagate_to_derived` through `apply_template_sync_with_notices` and `apply_template_sync_from_body` in `src-tauri/src/ai_gateway/templates.rs`; `apply_template_sync_with` keeps its old signature as a wrapper that drops the notices. The production `ai_gateway_sync_provider_template` command in `commands.rs` stages the sync inside `modify_config` and records `record_template_mappings_retired_messages` only after the configuration write succeeds, building each entry with `template_mappings_retired_message_input`: source `ai_gateway`, category `template_mappings_retired`, severity `warning`, provider-scoped dedupe key `ai_gateway_template_mappings_retired:<provider_id>`, the provider as target `entity_id`, and a bilingual `localized` title/summary naming the provider and listing its full currently retired set at event time — every mapping that is `enabled == false` and whose `upstream_model` is absent from the current template, in configuration row order. A failed sync, a template with no bound provider and a provider with no newly retired mapping record nothing; the manual and the automatic path both run this command, so both record identically. The test-only seam `TEMPLATE_MAPPINGS_RETIRED_MESSAGE_INPUTS` records the inputs.

The automatic-refresh info message is additions-only. `computeTemplateSyncChange` in `src/components/AiGateway/useTemplateAutoRefresh.ts` qualifies only a real mapping addition (an `upstream_model` absent from the previous configuration); a disable-only sync qualifies nothing. The info summary and detail no longer carry a disabled count or a disabled detail line, and the unused `aiGatewayTemplateSyncNotificationDisabledCount` key was removed from both i18n bundles. The info severity, the template title, the capture-time language resolution and the failure-isolation rules are unchanged.

## Alternatives considered

- Remembering a dismissal only for the session: declined because the pill would return on every restart for a condition the operator already acknowledged, so the feature would not reduce recurring noise.
- Permanently suppressing a provider or category once dismissed: declined because a problem that resolves and later recurs is a new event the operator must see; only per-instance dismissal with reconciliation keeps that distinction.
- Recording one message per retired or auto-disabled mapping instead of one per provider: declined because a catalog retirement or a failure burst usually touches several rows of the same provider at once, so per-mapping entries would multiply one event; the provider-scoped aggregation with the full current set is the chosen granularity.
- Building the retirement notification in the front end: declined because a retirement must survive the AI Gateway page not being open, and only the backend sees the command that performs the sync; the backend owns every retirement record.
- Retroactively backfilling problems that already existed before this change: declined as an explicit non-goal; it would rewrite history the Message Center never observed and is unnecessary for the new transitions.

## Consequences

- A dismissed or auto-dismissed pill stays hidden across reloads until its instance resolves and recurs: dismissals are reconciled when the gateway configuration and template views load, so a problem that resolves and recurs entirely between two loads keeps its card dismissal while the backend still records the new message, and a problem observed healthy at a load is pruned and shows again when it returns.
- Two provider-scoped warning categories are added: `mapping_auto_disabled` and `template_mappings_retired`, each recorded only after the configuration write succeeds. The message store's one-hour dedupe window merges repeated transitions for the same provider under its `dedupe_key`, counts them in `occurrences` and refreshes the summary/detail to the latest complete set. No backfill and no resolution or closure message is produced.
- The automatic-refresh info message is additions-only, so a retirement is archived once by the backend warning instead of being duplicated as an info entry; a retirement-only sync creates no `template_sync` entry.
- No interface, schema or migration change: the front end adds only its own JSON dismissal set in local storage, which older builds ignore, and the backend reuses `messages::MessageCreateInput`, `record_message_silent`, the dedupe window and `localized` exactly as the existing key-auth notification does; no Tauri command signature, `ai_gateway.json` schema, usage-log schema or Message Center schema changed.
