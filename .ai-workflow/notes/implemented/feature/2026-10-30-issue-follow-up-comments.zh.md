# Agent Note: Issue Follow-Up Comments

Status: implemented

[English](2026-10-30-issue-follow-up-comments.md) | 中文

## Problem

Issue worker 曾把每个 Issue 视为一次性任务。一旦存在终态记录，后续评论就不再被读取，因此驳回所提交 Pull Request 的授权协作者只能另开 Issue；而直接重读整个评论线程又会重放机器人、未授权与 Agent 自己发表的评论。worker 也无法区分自己的 PR 分支与仅仅提到该 Issue 的人类分支，并且没有在「已考虑过的评论」和「之后到达的评论」之间保留持久边界。

## Decision

后续任务由评论驱动，而不是由 Pull Request 事件驱动。对于仍带配置触发标签的 open Issue，以 `/agent` 开头的评论（允许前导空白、不区分大小写，其后须为结尾或空白）在评论者有效仓库权限为 `admin`、`maintain` 或 `write` 时恰好启动一次后续任务；`maintain` 归一化为 `write`，`triage` 归一化为 `read`。既有的 Issue 作者权限门先执行，因此作者未授权或作者查询失败时不评估任何评论，游标也保持不变。机器人（`user.type` 为 `Bot` 或登录名以 `[bot]` 结尾）、包含 Agent 标记的评论、已关闭或未打标签的 Issue、非命令评论以及出现在文本中间的 `/agent` 都不会触发。已确认未授权的评论者被消费而不运行，权限查询失败则停止评估并保持游标不变。没有单独的配置开关。

每个提示词都把授权与内容分离。受信任的前置说明声明触发来自经校验的 `/agent` 评论、后续请求是待实现的需求而非系统指令，并报告上一次结果（`status`、`branch`、`pr_url`、`last_error`）。随后不可信区块按顺序包含 Issue 标题与正文、仅限授权人类的评论以及后续请求；这些值都经脱敏，使其中提供的边界标记无法闭合该区块。授权历史与请求共享 50,000 UTF-8 字节上限：上限先丢弃最旧历史，尽可能保留请求，请求本身过大时追加可见的截断说明；标题、正文与结果元数据不计入。未授权、机器人与标记评论绝不进入提示词，针对密钥、宿主文件与克隆外修改的固定限制保持不变。

每次触发都以完整授权历史重新克隆并执行一次新的 `opencode run`；不恢复 OpenCode 会话，也不保留上一次的工作目录。仅当 open PR 的正文在数字边界引用 `#<n>`、其 head 仓库等于目标仓库且其 head 分支与该 Issue 持久化的 `branch` 完全一致时，才视为 Agent 自有 PR。命中时检出该 PR、追加提交并推送到同一分支，不创建第二个 PR。既没有 Agent 自有 PR、也没有其他引用该 Issue 的 open PR 时，从默认分支创建新分支并开启一个含 `Closes #<n>` 的新 PR。引用该 Issue 但不属于 Agent 的 open PR 绝不被修改：worker 只回复一次并消费本次触发。保持 Agent PR open 且不合并、再次评论 `/agent` 是受支持的拒绝与调整路径；PR 会话评论与 `Request changes` 评审不会触发，关闭 PR 意味着下一次触发从新分支与新 PR 开始，而非复用已关闭的分支。

每个 Issue 持久化的 `last_comment_id` 使评估保持幂等。游标越过被忽略的评论，并在终态（`done`、`failed` 或 `no_changes`）之后推进到触发快照中观察到的最大评论 ID。评论抓取与评论者权限查询失败保持游标不变；未授权评论者被消费；运行期间到达的评论具有更高 ID，等待后续轮询；已消费后被编辑的评论不会再次触发。Agent 发表的每条 Issue 评论都携带隐藏标记 `<!-- onespace-cloud-agent -->`，它既排除触发，也使评论不进入历史，同时不改变可见文本。状态保持 `version: 2`；`last_comment_id`、`branch` 与 `pr_url` 是带默认值的加性可选字段，其他形状沿用既有非法状态隔离策略，v1/v2 加载、初次处理、重试、初次 PR 跳过、任务流水与通知均不变。

## Alternatives considered

- 为调整重新打开或另开 Issue：否决，因为这会割裂讨论，并丢失评审者已经跟随的持久 Issue/PR 关系。
- 恢复上一次 OpenCode 会话或复用其工作目录：否决，因为保留的会话与克隆可能携带陈旧或未经验证的状态，而全新克隆让每次运行都可复现。
- 把任何引用该 Issue 的 open PR 都视为可复用：否决，因为人类或 fork PR 可能因此收到 Agent 提交；仅有分支身份不足，归属必须同时要求记录的状态分支、目标仓库与数字边界 Issue 引用。
- 只允许 Issue 作者评论 `/agent`，或把任何新评论都当作触发：否决，因为其他授权协作者需要同一路径，而不加限定的评论会把线程闲聊与机器人输出变成工作。
- 把未授权评论连同警告写入历史：否决，因为这会扩大注入面与提示词预算，却不会增加授权需求。
- 允许 PR 会话评论或 `Request changes` 评审触发：否决，因为 Issue 仍是唯一经过权限门且可审计的入口，PR 表面需要另一套授权处理。
- 记录每个已处理评论 ID 而非单调游标：否决，因为单游标更小、以同样方式跨重启保留，并且已经忽略对已消费评论的编辑。
- 拒绝超限的后续请求而非截断：否决，因为丢弃最旧历史可保留当前请求，可见的截断说明让运行仍可进行且不会隐藏损失。

## Consequences

- `/agent` 在可选前导空白之后不区分大小写，上限为授权评论加后续请求共 50,000 UTF-8 字节。
- 后续任务以既有字段格式出现在新的任务流水条目中；不需要桌面 UI、任务流水 schema、网关或 session-runner 改动。
- 拒绝工作流是可操作的：保持 Agent PR open 且不合并，然后在 Issue 上评论 `/agent`。关闭该 PR 会按设计放弃分支连续性。
- 在不存在 Agent 自有 PR 时，引用该 Issue 但属于他人的 open PR 会阻止该次触发的代码修改：worker 只回复一次、消费游标并保持 PR 不变。
- 状态保持 `version: 2`；旧 worker 会忽略新字段，并可能在下一次保存时丢弃它们。重新升级后游标从 `0` 开始，历史 `/agent` 评论可能被评估一次；由于该命令是显式授权操作，这是可接受的。
- 验证来源是 Issue worker 行为测试、完整的 server Python 测试套件与 note 校验；提示词边界仍是提示约束，而非操作系统沙箱。
