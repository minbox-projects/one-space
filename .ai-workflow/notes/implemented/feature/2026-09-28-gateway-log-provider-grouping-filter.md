# Agent Note: Gateway Request Logs Group and Filter by Provider Name

Status: implemented

English | [中文](2026-09-28-gateway-log-provider-grouping-filter.zh.md)

## Problem

The request-log panel could group by model or UTC+8 day and filter by status and model, but it could not answer which upstream provider served the traffic or isolate one provider's requests. Adding provider grouping and filtering raised questions the existing contract did not answer: every log row carries a provider id and the provider display name recorded when it was served, and the name is neither unique nor stable; the filter has to coexist with the existing single-select status and model filters; and the option list that feeds the filter must stay usable while that filter is active. The change also had to stay additive: no storage schema change, no record-shape change, and no change to the existing grouping modes, filters, pagination or totals.

## Decision

Provider grouping and filtering key on the provider display name recorded on each log row (`provider_name`), the operator-facing identity of the upstream that served the request. `group_by = "provider"` aggregates terminal rows by that recorded name, so two provider entries that share one display name merge into one group, and a provider renamed later splits its history: new rows form a new group while older rows keep the old name's group. Each group reports the request count, the failure count (`result = 'failure'` rows only) and the last-request time, ordered by most recent request descending and then by name ascending; terminal rows recorded without a provider form one blank-named group that the interface renders as `—`. The accepted `group_by` vocabulary becomes `none`, `model`, `provider` and `day`; any other value keeps returning the actionable error, which now lists all four values.

`ai_gateway_request_logs` accepts an optional `provider` argument that matches the recorded `provider_name` exactly. Empty and whitespace-only values are treated as unset; the selector composes with the active status and model filters using AND; a value that matches no row returns an empty page with zero totals instead of an error. An ungrouped response returns a `providers: string[]` facet: the distinct, non-empty, alphabetically ordered in-range `provider_name` values. Like the existing `models` facet it spans the whole resolved range independent of the current page and ignores its own filter so the selection can be changed without clearing it, and it honors the active status and model filters. The `models` facet now honors the active provider filter as well; with no provider filter its behavior is unchanged. Both facets stay empty on grouped responses, matching the existing model-list contract. The blank name (the synthetic no-provider terminal row) is excluded from the `providers` facet while it remains visible as the `—` group under provider grouping.

The panel adds `Provider` to the grouping selector and a `Provider` section to the filter popover with an `Any provider` chip and one chip per in-range name taken only from the response `providers` facet. The selection is single-select; applying it restricts both the ungrouped list and grouped aggregates, adds the name to the filter trigger label and resets paging to the first page; clearing resets status, model, provider and paging together. The provider filter stays applied while switching grouping modes. When a response carries no provider list, the section shows only the `Any provider` chip and never derives options from visible records. The bilingual keys are `aiGatewayGroupProvider`, `aiGatewayFilterProvider` and `aiGatewayFilterAnyProvider`.

## Alternatives considered

- Key the groups and the filter by `provider_id` instead of the recorded display name: declined because the display name is the operator-facing identity, a log row already freezes the name it was served by, and id keying would split two provider entries that share one visible name while leaving rows whose provider entry was later deleted without a readable label; the name's merge/rename trade-off is accepted and pinned by the delivered behavior.
- Make the provider filter multi-select: declined because the status and model conditions in the same popover are single-select, a set filter would need `IN` clauses plus its own trigger-label, "any" and clearing semantics, and the specification deliberately scopes the provider filter to one selection like the others.
- Derive the provider options from the visible records or the current page: declined because a provider whose rows lie entirely beyond the current page must still be selectable; the options come from the response `providers` facet, and the panel never derives them from visible records — a missing facet shows only the `Any provider` chip.
- Let the provider facet honor the active provider filter: declined because the current selection would disappear from the options and could not be changed without clearing the filter first; the facet ignores its own filter exactly as the model facet does.
- Offer the blank name as a selectable option: declined because the synthetic no-provider terminal row is not an upstream provider and can never match a provider filter; it stays visible only as the `—` group under provider grouping.

## Consequences

- The command contract is extended additively: the optional `provider` argument, the `"provider"` grouping value, the ungrouped `providers` facet, the model facet honoring the provider filter, and empty facets on grouped responses. A caller that omits `provider` and uses the previous grouping values observes unchanged behavior; no stored row, column, schema version or migration changes, and rollback reverts the change.
- Implementation: `LogFilter` gains `provider` and `bind` adds an exact `provider_name = ?` clause to the shared predicate; `group_logs` gains the provider branch; `query_logs` computes the `models` facet with the provider filter preserved and the `providers` facet with the provider filter cleared; `ai_gateway_request_logs` accepts and trims the argument. On the frontend `UsageGroupBy` gains `"provider"`, `UsageLogsQuery` gains optional `provider`, `UsageLogsPage` gains optional `providers`, `aiGatewayRequestLogs` forwards the key, and `UsageLogsPanel` adds the option, the single-select chips, the trigger label and the clear/reset behavior.
- Same-named provider entries merge into one group and a rename splits history; this is the documented semantic, recorded by `MEMORY.md`, `docs/USAGE.md` and the `ai-gateway` / `ai-gateway-backend` navigation entries, with `navigation.md` regenerated from the authoritative JSON.
- Nothing else changes: the usage-statistics panel, the request-log record shape and fields, the SQLite schema and retention, pagination, totals, the status and model filters themselves, and the `none` / `model` / `day` grouping output keep their current semantics.
- Supersession: partial. [API Gateway Usage Stats and Request Logs](../architecture/2026-09-17-ai-gateway-usage-logs.md) recorded the `group_by` vocabulary as `"model"` and `"day"` and the model facet as honoring the resolved range and status filter only; those two statements are replaced by this record, while its SQLite storage, per-attempt recording, record-time price freeze, retention and range-selector decisions remain in force. This record also extends the `ai_gateway_request_logs` signature recorded by [API Gateway Usage Queries Replace Day Counts with a Named Range Selector](2026-09-22-gateway-usage-yesterday-range.md) with the optional `provider` argument; its range-selector decision remains in force.
