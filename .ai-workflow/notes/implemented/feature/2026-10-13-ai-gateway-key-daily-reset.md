# Agent Note: Gateway Daily-Reset Keys Recover at the Next UTC+8 Day Boundary and the Editor Replaces Reordering with a Compact Daily-Reset Control

Status: implemented

English | [中文](2026-10-13-ai-gateway-key-daily-reset.zh.md)

## Problem

Upstream-provider keys that exhaust their daily quota were recovered only by the legacy time-based paths: a quota mark became selectable again once it was at least `KEY_QUOTA_MARK_TTL_SECS = 1800` seconds old, and the all-marked half-open probe re-tried the oldest marked key after `KEY_PROBE_COOLDOWN_SECS = 60`. Neither matches a provider whose quota resets on a calendar-day boundary: a key marked at 14:00 could be re-attempted before midnight (and re-marked, spending a request), while a key marked at 23:59 was held until the TTL expired rather than being freed at the next day. The operator also had no per-key way to say "this credential recovers each day", and the key editor's up/down controls occupied the row for a reordering action that silently changed the persisted priority order.

## Decision

`UpstreamKey` gains a `#[serde(default)] daily_reset: bool` that is always serialized and false in `Default`; a stored record without the field reads as false, and the configuration schema stays version 3 with no new migration. The setting is user intent, independent of the runtime mark, and never changes a key's `enabled` flag.

`selection::daily_quota_reset_due(key, now)` is the shared due predicate. It is true only for a user-enabled, `daily_reset` key that is runtime-marked with `failure_kind == Quota` and a known `marked_at`, when `now` falls on a strictly later fixed UTC+8 natural day than the mark. `utc8_natural_day` folds the `+08:00` offset through quotient/remainder decomposition so no timestamp (including `u64::MAX`) overflows, and the device timezone is never consulted. A same-day mark stays excluded however old it is, and a future-dated mark never becomes due early. `selection::quota_mark_expired` returns that predicate for a `daily_reset` key and keeps the inclusive 1800-second TTL for a legacy (`daily_reset = false`) key; `select_usable_key` therefore admits a due daily key through normal list-order selection while `find_key_probe_candidate` excludes every `daily_reset` key, so a same-day daily mark is never probed and a due one recovers through selection and the scanner rather than the probe.

`daily_reset::scan_due_daily_reset_marks<R: Runtime>(app: &AppHandle<R>, now: u64) -> Result<usize, String>` is the production recovery pass. It runs a `storage::modify_config` closure over the latest serialized configuration and clears only the runtime mark fields (`auto_marked`, `failure_kind`, `marked_at`, `reason`) of each due key through `clear_key_runtime_state`, preserving user flags and unrelated configuration; a pass with nothing due reports no change and rewrites nothing. After a successful persisted change it emits the existing `AI_GATEWAY_CONFIG_UPDATED_EVENT` with its `()` payload through the supplied `AppHandle` — not the listener-captured handle — and records the same notification on the existing test-observable configuration-event seam. A failed write propagates the error, leaves the previous complete bytes intact and emits nothing.

`daily_reset::start_daily_reset_scanner(app: AppHandle) -> bool` (re-exported `pub(crate)` at the `ai_gateway` root) installs the process-owned scanner exactly once and runs the immediate startup pass synchronously on the caller's thread before spawning the worker; a second call is a no-op. The worker re-reads a fresh wall clock every pass and scans every `DAILY_RESET_SCAN_PERIOD = 60` seconds while the app runs, independently of WebViews, the gateway listener and the template-refresh preference. `daily_reset::stop_daily_reset_scanner()` drops the worker's stop sender and joins the owned thread, idempotent and safe when nothing runs. Application setup starts it next to the existing template scheduler (`run_app.rs`), and `shutdown_runtime_services` stops it (`shortcuts_tray.rs`), so no overlapping writer survives shutdown.

Frontend, `GatewayProviderKey.daily_reset?: boolean` mirrors the setting and is optional so pre-feature fixtures and records stay assignable; the editor saves `daily_reset: key.daily_reset === true`, starts a new row at false, and its runtime-only merge copies just the runtime fields, so an unsaved daily-reset edit survives an incoming runtime refresh. The key row's former up/down controls, `moveKey` and their bilingual `MoveUpAria`/`MoveDownAria` labels are removed (the `ChevronUp`/`ChevronDown` imports remain for mapping expansion), and the freed area carries a compact labelled switch with `aiGatewayProviderKeyDailyReset` (`Daily reset` / `日重置`), a per-row `aiGatewayProviderKeyDailyResetAria` name and a native-title `aiGatewayProviderKeyDailyResetHint` stating the fixed UTC+8 meaning. Stored key order and append-at-end behavior are unchanged, and there is no frontend timer.

## Alternatives considered

- Reset daily keys at a rolling 24-hour age instead of a UTC+8 calendar day: declined because the operator's intent is "available again tomorrow" and the specified boundary is the UTC+8 natural day rather than a duration; a rolling window would recover mid-day and drift with each restart.
- Use the device's local timezone for the day boundary: declined because recovery must be deterministic across hosts and match the UTC+8 convention the gateway already uses for usage and pricing; the device timezone would make one configuration behave differently per machine.
- Let the all-marked 60-second probe recover daily keys like quota TTL keys: declined because a same-day daily mark must not be attempted by design and a due one recovers deterministically through selection and the scan; probing it would spend the request the feature exists to avoid.
- Recover only in the background scan without the selection predicate: declined because a request arriving after midnight must be able to use the key immediately; the scanner alone would make the first eligible request wait up to 60 seconds.
- Add an OS wake hook or a daemon to survive sleep or exit across midnight: declined because the startup and 60-second process scans already catch up, and a sleep/resume integration would widen the change beyond the gateway process.
- Keep the up/down reorder controls and add the daily control elsewhere: declined because the editor must not silently change persisted priority, and the removed button area is the natural compact home for the new control without crowding the name/value fields.

## Consequences

- A `daily_reset` key marked quota at any time in a UTC+8 day is excluded from both normal selection and the probe for the rest of that day, and becomes eligible exactly at the next UTC+8 midnight even though the 1800-second TTL has not elapsed; a mark one second before midnight is eligible one second later, a same-day mark stays excluded however old it is, and a future-dated mark is never recovered early.
- A legacy (`daily_reset = false`) key keeps the inclusive 1800-second TTL, the single 60-second half-open probe and the manual re-enable path unchanged; auth marks, keys without a known mark time and user-disabled keys are never touched by daily recovery, and the scanner rewrites nothing when no key is due.
- Recovery writes only the eligible runtime fields through the existing serialized writer, preserves user flags and unrelated configuration, and publishes the existing `ai-gateway-config-update` event after a successful persisted change; a failed write preserves the prior file, emits no event and stays due for a later scan.
- The scanner runs at startup and every 60 seconds, so exit or sleep across a day boundary catches up on the next start and the first eligible request can use the key immediately; it is independent of the gateway listener and template refresh, and shutdown joins the worker so no overlapping writer remains.
- The key editor no longer reorders keys: it preserves stored order, appends new keys, and exposes an independently operable per-key daily-reset switch with a concise bilingual label, a per-row accessible name and a native-tooltip UTC+8 hint; existing key editing, enable/disable, delete, visibility and manual re-enable actions remain.
- A recovered daily key that is still exhausted upstream is re-marked at its actual failure time, the gateway rotates to the next usable key, and the daily key is excluded again until its next day boundary; the rotation adds no mapping-failure counters for a key-domain quota failure.
- Compatibility and rollback: the only persisted extension is a serde-defaulted, always-serialized boolean under schema 3, so old records read as false and an older build can still read the remaining key fields (its later save may drop the new field). No migration, new dependency, upstream quota query or WebView polling is added, and reverting the code restores the legacy TTL/probe behavior and the previous editor controls.
