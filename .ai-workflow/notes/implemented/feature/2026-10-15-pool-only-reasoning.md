# Agent Note: Model Pools Own a Bounded Pool-Local Reasoning Policy

Status: implemented

English | [中文](2026-10-15-pool-only-reasoning.zh.md)

## Problem

A client of a model-pool public alias could not request a reasoning preference. The pool portable contract rejected every unrecognized message or request control by field, and that included every `reasoning_effort`, `reasoningEffort` and `reasoning` value, so a client that wanted more or less reasoning had no stable, provider-independent way to ask for it. Each selected candidate is a real provider mapping whose native effort identifiers differ and whose source configuration must stay unchanged, so neither a shared provider field nor a global policy could express "this public preference maps to this candidate's native control". Operators also had no place to declare a candidate's native capability, no default preference and no per-attempt evidence of the controls that were actually sent. The user explicitly required this feature to apply only to model pools and to leave existing upstream providers unaffected.

## Decision

- The public preferences are the canonical, provider-independent set `low`, `medium`, `high`, `xhigh` and explicit `none`. Chat accepts `reasoning_effort` and the compatibility spelling `reasoningEffort`; Responses accepts `reasoning.effort`. Values are trimmed and then matched against the lowercase set, so a case variant is not a public tier. Missing, null and blank values mean unspecified; two equal nonblank Chat spellings are accepted, while conflicting spellings, non-string values, unknown identifiers and the literal `auto` return the field-named `400 invalid_request` before any scheduler, key, probe or health mutation. `none` is an explicit disable and `auto` is never a request value.
- The pool default is one of the five preferences or `auto`, where `auto` omits all feature controls and uses the provider default; a missing persisted default reads as `auto` and `auto` is never sent as an effort string. An explicit request preference overrides the stored default. A newly opened pool dialog initially selects `medium`, and the operator may select `auto` instead; no mapping is invented to make that initial default valid.
- Every new declaration lives under `model_pools[*].candidates[*]` and the default under `model_pools[*]`. Neither `GatewayUpstreamProvider` nor `ModelMapping` gains a persistent field, and the upstream-provider editor gains no control. A declaration is scoped to its pool and the full candidate identity: provider id, original trimmed local/upstream pair and effective protocol. Two pools that reference the same source keep independent policies. Existing source `reasoning_efforts` may be shown as read-only reference, but a source metadata value never automatically becomes a pool mapping, a missing declaration stays unknown and a later source label edit never rewrites a pool-owned declaration.
- Mappings associate one public preference with one typed native action, and only five bounded native profiles are supported. Multiple positive preferences may share one positive native action; a missing mapping means unsupported for that candidate; a positive preference can never target disabled reasoning or omission; `none` can only map to an explicitly declared, supported disable; a native enum target must belong to the candidate's declared set. A manual budget is an integer of at least `MIN_MANUAL_REASONING_BUDGET_TOKENS = 1024` inside the candidate's declared, internally consistent range, manual budget and adaptive thinking cannot be combined, and a switch-only profile's positive mappings carry no intensity gradient. There is no arbitrary request-JSON injection mechanism.
- All profiles, mappings and defaults are validated inside the existing serialized configuration transaction, so an invalid submission preserves the original encrypted bytes. A previously stored reference that later becomes missing or changes protocol may be retained with a visible reason, but it is never served by guessing or substituting a sibling source.
- A new or changed concrete default requires at least one currently valid mapping, and a save that deletes the last mapping declaration of a retained concrete default must change that default to `auto` or to another default with a valid mapping in the same save; otherwise the save is rejected atomically. An unchanged default and declaration may be retained after their source becomes unavailable, and a request for that declared-but-unavailable preference returns `502`.

| Profile | Target | Positive control | `none` control, only when declared supported |
| --- | --- | --- | --- |
| OpenAI effort | Chat Completions | `reasoning_effort: <native value>` | `reasoning_effort: "none"` |
| OpenAI effort | Responses | `reasoning: { effort: <native value> }` | `reasoning: { effort: "none" }` |
| Anthropic effort, inherit thinking | Anthropic Messages | `output_config: { effort: <native value> }`; omit only `thinking` | `thinking: { type: "disabled" }`; omit positive controls |
| Anthropic effort, adaptive thinking | Anthropic Messages | `output_config: { effort: <native value> }` and `thinking: { type: "adaptive" }` | `thinking: { type: "disabled" }`; omit positive controls |
| Anthropic manual budget | Anthropic Messages | `thinking: { type: "enabled", budget_tokens: N }` | `thinking: { type: "disabled" }`; omit the budget |
| Chat thinking switch | Chat Completions | `thinking: { type: "enabled" }` | `thinking: { type: "disabled" }` |

- The parser, eligibility policy and native injector run only after an exact current pool alias is recognized and never on an ordinary route; disabled and retired aliases and a native Messages request for a pool alias keep the existing fenced behavior. Request shape and reasoning are validated before selection, and a concrete resolved preference is classified in a fixed order: no selected candidate declares the preference returns `400 unsupported_reasoning_effort`; declarations exist but none is valid against its profile and current source identity/protocol returns `502 all_providers_unavailable` with bounded nonsecret reasons; every valid mapping is incompatible with the request's effective output cap returns `400 reasoning_output_limit_incompatible` naming the output-limit field and the budget; otherwise the remaining candidates are filtered by the existing health, key, protocol and cooldown rules and at most one compatible probe is appended, and if none is available the result is `502 all_providers_unavailable`. An Anthropic budget must be strictly below the effective cap, Chat `max_completion_tokens` keeps precedence over `max_tokens`, Responses uses `max_output_tokens`, an omitted Anthropic cap keeps the existing 4096 default, and the gateway neither raises the client's cap nor reduces a configured budget. `auto` keeps the existing eligible candidate set and injects nothing.
- Every attempt starts from the original request with recognized entry controls extracted and removed, converts the remaining portable request with the existing adapter, and then injects exactly that candidate's native controls only behind the existing pool-candidate guard; it never reuses another candidate's modified body. `anthropic.rs` stays unchanged so the ordinary Anthropic adapter keeps its rejection rules, and the existing strict-tool constraints, the assistant `reasoning_content` trace, first-byte, success-marker and downstream-cancellation/no-replay guarantees remain effective.
- Each attempt records durable, pool-only evidence from the same constructed values as its upstream body: the existing `reasoning_effort` field keeps the client's requested value (null when unspecified) and two new nullable fields `resolved_reasoning_effort` and a native-control snapshot of `{ protocol, mode, parameters }` are appended. An explicit `high` resolves to `high`, omission with a `medium` default resolves to `medium`, and omission with `auto` or a legacy pool resolves to `auto`. An attempted `auto` records `mode: "provider_default"` with empty parameters, a synthetic row with no attempt has no snapshot, and ordinary and historical rows stay null/omitted. The snapshot uses only allowlisted controls and never contains a body, header or credential. The nullable SQLite columns are added through the existing `PRAGMA table_info` idempotent path without backfill, and token counts, cost snapshots, amounts, retention and the single-terminal-row rule are unchanged.
- A static catalog is derived only from the current stored configuration: the canonical preference order, per-candidate static serviceability (exact source identity resolution, profile matching the stored effective protocol, and a structurally valid mapping), the pool default and per-preference coverage of mapped candidates over total candidates. Cooldown, key availability, health, source enable state and the request output cap never enter this configuration count; runtime readiness is shown separately. The discovery `/v1/models` row, the model list, the status payload and the OpenCode pool row all publish the same catalog. An OpenCode pool variant uses the canonical preference as both its variant name and its `reasoningEffort` value, never exposes a native mapped value, borrows a source npm/provider override, fabricates a price, balance or credential, or creates an `auto` variant; a legacy pool without valid mappings keeps its prior no-variants shape; disabled and retired pools stay excluded; manual synchronization, payload comparison, activation and projection ownership rules are unchanged. Ordinary model rows and their existing native effort identifiers keep their exact behavior, and Codex default selection and native Claude pool exclusion are unchanged.
- The pool editor owns the default, each candidate's native profile and value/range/budget/disable declaration and the five-preference mapping matrix. It provides an explicit unmapped option, identifies unknown capabilities and switch-only behavior, and validates incorrect mappings in place without clearing the draft; each manual-budget mapping keeps its own native token count and the draft values are preserved. A rejected save preserves the whole draft, cancel writes nothing, and a runtime refresh never overwrites unsaved edits. Static coverage, computed independently of readiness, is presented separately from the runtime readiness count; the provider editor keeps no new controls. The log UI explains the requested, resolved and native values for pool rows while ordinary rows keep their existing presentation and unknown historical evidence displays as unavailable rather than inferred. Labels, errors and controls work in English and Chinese and are keyboard-accessible.
- Compatibility and isolation: only additive serde-default pool fields are added and the configuration schema stays 3 with no migration, so reading an older configuration neither rewrites it nor infers mappings. Pool create, update, enable/disable and delete preserve the semantic values of `providers` and provider-scoped prices, including source mappings, efforts, keys, defaults and runtime marks, and leave another pool untouched. A mapping or budget exclusion that happens before selection creates no attempt and mutates no health. Ordinary Chat, Responses and native Anthropic routing, validation, discovery and terminal entries never call the pool parser or injector, and provider upsert, template synchronization and the ordinary reasoning-effort union keep their contracts.

## Alternatives considered

- Adopt a global reasoning policy or add persistent reasoning fields to the provider or `ModelMapping`: declined because the user requires pool-only behavior with existing upstream providers unaffected, and the source types, template behavior and provider editor must keep their contracts, so the policy is stored inside each pool candidate and the source stays a read-only reference.
- Expose the candidate's native effort value directly in the public request or API: declined because a client needs one stable, provider-independent preference while each candidate's native identifier differs; native values stay pool-private and the canonical set stays bounded.
- Infer a candidate's profile or capability from source `reasoning_efforts`, a model name or an automatic probe: declined because source metadata is only a read-only reference and guessing would misstate a real upstream capability; the operator must declare the profile and native value set explicitly, and a missing declaration stays unknown.
- Reuse the ordinary reasoning-effort union and ordinary adapter without a pool-specific parser and injector: declined because the ordinary path must not accept or emit these controls and because each candidate needs its own native body built independently; the pool parser, classification and injector stay behind the pool alias and the ordinary Anthropic adapter stays unchanged.
- Introduce a new configuration schema version or a migration for the pool fields: declined because additive `#[serde(default)]` fields already keep older files readable, so the schema stays 3 and no migration is needed.
- Silently downgrade `none` or discard an explicit control to obtain a response: declined because a disable request must disable or fail and a positive preference must never quietly become omission; declared-but-unmapped inputs return the dedicated `400` and a disconnected declaration returns `502` instead of guessing.
- Raise the client's output cap or reduce a configured budget so a candidate becomes compatible: declined because the gateway must not alter the caller's request or the operator's configured policy; an incompatible candidate is excluded and an all-incompatible request returns the dedicated `400`.
- Add `minimal`, `max`, `ultra` or the literal `auto` as extra public tiers: declined because the public set is the bounded canonical five and `auto` is only a default/omission policy, not a request value; provider-specific native identifiers may still use other spellings inside a declared value set.
- Represent a plaintext `reasoning_content` trace as a new reasoning control: declined because the trace is provider output rather than a caller control, so the pool policy leaves the existing same-protocol preservation and converted-omission behavior unchanged instead of turning it into a configurable effort.

## Consequences

- A client of a pool alias can now request a stable canonical preference and each selected candidate receives its own explicitly configured native reasoning controls, fallbacks and probes included, while an omitted preference follows the pool default. The preference expresses relative reasoning investment; it does not promise equal intelligence, reasoning tokens, latency or cost across the selected models.
- Ordinary upstream providers and ordinary routes are unchanged: provider configuration, ordinary Chat/Responses/native-Anthropic requests and errors, ordinary discovery and ordinary terminal entries keep their baseline, and pool CRUD leaves providers, prices and sibling pools semantically identical.
- Configuration and rollback: the schema stays 3 with additive serde-default pool fields, and an old pool uses `auto` until it is explicitly configured. The new dialog's initial `medium` must be made valid or changed to `auto`. Because an older binary may drop unknown pool fields on a save and cannot serve explicit pool effort requests, returning to an older binary requires preserving the same-profile encrypted gateway configuration with its matching local key and the corresponding terminal projection. The added nullable log columns are compatible with old readers, historical usage is never recalculated, and no new backup subsystem or migration framework is introduced.
- Limits and known coverage gaps: captured mock requests and attempt-to-log comparisons prove deterministic adaptation, not that a real provider obeys a declared reasoning preference, so live provider compliance remains unverified and adaptive-thinking acceptance depends on provider support. Real native Tauri IPC, live provider inference, real terminal projection and interactive screenshots were not exercised and are reported as not executed rather than claimed; optional visual checks were optional and are not evidence for the acceptance criteria.
