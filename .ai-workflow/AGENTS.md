# ai-workflow project contract

This contract applies to the entire project and every participating agent, including sub-agents. Read it explicitly before repository work; do not rely on a host recursively loading hidden directories or following Markdown links. Installed role files must not override this contract. The complete primary-only Coding and workspace procedure lives in the shipped `coding` skill (`templates/skills/coding/SKILL.md`) and its `references/workspace.md`; this contract keeps every common obligation and references that authority only for mode-specific execution detail.

## Shared context and maintenance

- Before repository work, read `MEMORY.md` and both `.ai-workflow/index/navigation.{json,md}` files; notes and governance join explicit scopes, not full history. Spec Review alone skips fixed context, notes, accepted results and generic packets: Planning review — draft spec and plan plus requirement references, no commit range; coding review — frozen requirements, raw evidence paths and one immutable range, never plans, tasks, summaries, test reports, earlier verdicts or history. It reads this contract as procedural authority, not acceptance evidence.
- For indexed known features, run `ai-workflow context locate --project <absolute-project-root> --feature <id> --verify`; do not search first. `navigation.json` is authoritative and complete. Update `MEMORY.md` and `.ai-workflow/index/navigation.json` immediately when architecture, ownership, agent responsibilities, public symbols, paths or workflow rules change, and regenerate and validate `navigation.md` in the same change. A missing or empty index is normal and does not block work when the frozen plan supplies an explicit boundary, while `stale` or `invalid` require bounded discovery or index repair before relying on indexed paths.
- `MEMORY.md` records only the project's current standards and behavior: the change that supersedes a statement rewrites it to the current state or removes it in the same change, so the recorded standards stay current as changes land; superseded history belongs to Git and Agent Notes, never to `MEMORY.md`.
- Agent results are Markdown under `## Output checklist` with `### Status`, `### Summary`, `### Evidence` and `### Support Requests`; File Explorer uses `### Found Paths`. JSON envelopes are prohibited and v2 manifest JSON is unchanged. Each `### Evidence` entry carries the absolute path of the produced artifact or an explicit report reference plus at most one sentence of conclusion, and prohibits embedded diffs, logs, JSON bodies or code blocks.
- Report-body targets: an ordinary successful report body must stay at or below 1,200 Unicode code points and a review, failure or blocked report at or below 3,000, counted over the whole report body including `### Summary` and `### Evidence`; the examples include one code point above each limit, and a non-BMP character counts as one code point. Authors must self-check the whole body before returning. These are portable prompt instructions, not a programmatic runtime cap and not a host guarantee. Complete findings take precedence over the length target: when no complete recoverable reference is available, expose the length exception visibly, retain every known status, verdict, SHA, exit-code and blocker fact, and leave acceptance unresolved rather than dropping facts. After receipt the primary may request an explicitly scoped fresh read-only digest; that digest is read-only, grants no file-write permission, never automatically reruns an operation whose side effect may already have completed and never claims to remove content already received.
- Durable artifacts stay self-contained after their plan is gone: note bodies, commit messages and code comments, including class- and type-level documentation comments, describe the delivered result, decision or behavior in durable project terms and never carry transient plan-internal identifiers such as task IDs, step numbers, phase numbers, `REQ`/`AC` IDs or plan directory names. One bounded exemption applies to test names, assertion labels, test-local constants and traceability comments that link a test to what it verifies, while note bodies, commit messages, product code comments and shipped documentation keep the full prohibition. Existing active notes that still carry such identifiers are cleaned under `.ai-workflow/notes/README.md` maintenance, and the workspace cross-repository plain plan-ID note reference is the only sanctioned exception.

## Agent Notes

Read `.ai-workflow/notes/AGENTS.md` and `.ai-workflow/notes/README.md` before maintaining notes; the README is the single source for note format, lifecycle, supersession and archive governance. Planning schedules the relevant note work, the change that lands the decision owns its record and lifecycle transition, and MEMORY records current standards while notes record why; keep them consistent in the same change.

## Workspaces

A workspace is a root repository that composes child repositories as local git submodules; `.gitmodules` is the source of the submodule boundary, so a child's work never leaks into the root or a sibling. Each participating repository keeps its working tree at its declared workspace-root-relative path, and only its slice and plan artifacts live under `<root>/.ai-workflow/plans/<planId>`. Cross-repository references stay plain plan-ID text: the workspace root owns the decision note, each repository owns its own delivered facts, and each side updates only its own notes and `MEMORY.md`. A plan declaring a non-root participating repository must be split by plan-to-tasks before implementation, with the task set frozen only after `ai-workflow workspace distribute --plan <directory>` succeeds for every participant with `ai-workflow workspace status --plan <directory>` valid and every slice present, while a plan whose `workspace_repos` declares only the reserved `workspace` root entry may be implemented unsplit; only a frozen plan with a non-root participant matched to the current root's `.gitmodules` activates the parent workspace boundary, and each active repository owns one run-owned worktree at `<source-root>/.worktrees/<planId>` on branch `ai-workflow/<planId>`. Git Operator is the only role allowed to run Git, each repository's single `implementation.yaml` is updated only through the filesystem-only `ai-workflow workspace checkpoint --plan <directory> --repo <name>` command after Git evidence, and each verified delivery commit is pinned as an authorized pointer. Apply the workspace-command semantics and the full parent, slice and root-delivery procedure from the shipped `coding` skill's `references/workspace.md`.

## Change routing

Classify every request before starting and state the class in one line.

- Direct change — a small requirement, feature adjustment or defect fix with clear, bounded intent and one observable outcome: implement it directly without Planning, without `spec.md`, `plan.md` or task files, and without the dual-axis review. Run the relevant checks and add one focused regression test for a defect.
- Planned change — a new feature, unclear or contested requirements, more than one materially different design, or a change to a public interface, persistent format, cross-module or cross-stack behavior, migration, compatibility or this contract: run Planning first, implement the frozen plan, and keep the dual-axis review gate.
- Mechanical change — a typo, copy, comment, formatting or test-only adjustment with no observable behavior change: implement it directly and run only the narrowest relevant check.

Never run Planning to restate clear, bounded intent or label direct to skip checks or evidence, and ask only when rules cannot classify. After checks pass, the primary automatically delegates the scoped commit to Git Operator, without separate confirmation, before immutable-range review where one applies; it supplies the range, never a review PASS or integration authorization. Completion needs the commit SHA or verified no-change evidence with current HEAD when no scoped diff exists; a failed or blocked commit reports `blocked` or `failed`, never `done`.

## Review policy

The change class is the only routine review trigger: a Direct or Mechanical change dispatches neither axis, Planning dispatches only the Spec Review, and plan-to-tasks dispatches neither axis, while an ordinary planned implementation runs one simultaneous full Spec Review and Standards Review batch after implementation and before integration, a child-participating workspace runs a per-repository delivery review and an independent finalization review, and a zero-task root has no artificial root-delivery review. There is no per-task, per-phase or per-commit review trigger.

Both axes share the immutable HEAD with separate payloads; Spec Review uses only defined inputs. Test evidence is the primary's runtime gate; static Spec PASS is not runtime success. One aggregate repair is automatically delegated for evidenced defects within frozen acceptance and write scope. At most one fresh targeted recheck per boundary, affected axes only, both together; the primary keeps findings and labels, maps closure, and a Spec recheck gets only affected requirements, range, repair scope, never earlier findings or "fixed" claims. Checked commits precede review: split task commits supply the range; other checked units, repairs or finalization pointer changes commit before review, implying no PASS or integration authorization; integration follows accepted reviews; no-change units supply verified HEAD evidence, not an empty commit. Before non-fast-forward merge Git Operator alone compares actual clean source HEAD, repository, worktree, base, target with accepted HEAD, refusing drift; delivery SHA is recorded independently.

An unfulfilled AC, cited required-standard violation or missing required evidence is a blocker; warnings are advisory, needing a reasoned disposition never masking a blocker; demonstrably unsupported or duplicate findings need reasoned dispositions, not silent drops. A required business/acceptance, scope or REQ/AC change or delivered-child edit needs a bounded decision or support request, not an unauthorized edit; an unresolved blocker or unavailable recheck stops as `blocked`/`failed`, no second repair or review loop. `done` means execution completed, not Verdict PASS; freeze or integration needs complete acceptance evidence and no unresolved blocker. Workspace `reviewed_commit` is purpose-scoped, written once after accepted closure, never reused; checkpoint success is no PASS or Git equality.

## Work-boundary synchronization

Adopted projects synchronize their managed workflow instructions once at each planning, coding or plan-to-tasks skill start, keyed by the actual root. That skill start runs `ai-workflow sync-hook --host <current-host> --phase --project <actual-root>`, the only automatic trigger, and stores its complete result for the actual root outside the project; every later native `SessionStart`, `UserPromptSubmit` and `PreToolUse` event is served from that stored result, while a missing, corrupt or unreadable stored check allows with a visible no-check context and no freshness claim. The `--phase` form and the OpenCode stdin gate print the raw gate JSON with a top-level `decision` of `allow`, `deny` or `skip`; the Claude Code and Codex stdin gates emit host-native output that never exposes the raw decision, and every handled form exits 0 even on a deny. A `deny`, or a `conflict` or `failed` `report.status`, blocks the phase; a warning `report.status` proceeds with visible context and no freshness claim; `skip` means no adoption was found. The installed host entry invokes `ai-workflow sync-hook --host <current-host>` with the host's native JSON payload on stdin; do not run that form by hand without the payload. The manual `ai-workflow sync [project]` command prints a `SyncReport` with `status`, `verified` and `proceed` and no `decision`.

This preflight is a narrow instruction-maintenance exception to coding-worktree confinement: it writes only the managed workflow instruction files of the actual current project root or the active coding worktree, with no Git, staging or product edit, and turns a clean-baseline or task-scope collision into a bounded support request. After a safe patch changes the contract or owned workflow rules, re-read the updated `.ai-workflow/AGENTS.md` before ordinary work continues; frozen `spec.md`, `plan.md`, task files and their declared repository/write scopes are never synchronized, and a contradiction between new authority and a frozen scope stops that phase with an explanation.

## Coding execution model

Planning produces frozen `spec.md` and `plan.md`; plan-to-tasks produces immutable task documents. Coding implements direct changes without planning artifacts and planned work as split tasks or an approved unsplit frozen plan, with TDD, and creates no workflow runtime artifact other than the single implementation record at `<project>/.ai-workflow/plans/<planId>/implementation.yaml`, which holds `plan_id` with `status: in-progress` and an ISO 8601 `started_at` in the UTC+08:00 timezone before the first implementation step and after the final merge and owned cleanup becomes `status: completed` with an ISO 8601 `completed_at` in the UTC+08:00 timezone and the final commit SHA; it is the only permitted run record.

- A planned change without a frozen plan is planned first and then handed off: the planning session never starts implementation, runs the plan-to-tasks preparation and distribution for a workspace plan, and routes to a new session at the workspace root, while an ordinary or root-only plan tells the user to start a new session. A direct or mechanical unit without a frozen plan carries its complete explicit scope, with no missing-plan demand and no requirement for a `spec.md`, `plan.md` or task file.
- Coding must create one project-local temporary worktree under `<project>/.worktrees/<name>` before implementation, and all implementation and validation happen inside that single worktree. Git Operator materializes the project's entire gitignored state into the worktree, excluding the `.worktrees/` container, so `.ai-workflow/plans/` stays visible and single-source at the project root while the project contract, MEMORY, navigation and notes arrive with the worktree through Git.
- A split plan's execution order is frozen at split time as `tasks/execution-order.yaml`: the ordered list of non-empty parallel phases that covers every task exactly once, with every dependency in a strictly earlier phase and no overlapping normalized write-scope paths inside one phase. It is the only schedule: phases run in file order, every task of a phase is dispatched concurrently inside the single worktree with test work before implementation in each task, and each task's write scope is committed serially through Git Operator one commit at a time before advancing; a missing or invalid order stops the run before execution, with no serial fallback and no recomputation from `depends_on`.
- A git-submodule workspace root delivers one cross-repository plan whose `workspace_repos` declaration and `workspace.yaml` manifest assign every task to exactly one repository in a repository-level delivery order; such a plan must be split by plan-to-tasks before implementation, while a plan whose `workspace_repos` declares only the reserved `workspace` root entry may be implemented unsplit. Parent workspace coding orchestration is activated only for a frozen plan that declares a participating non-root repository matched to the current root's `.gitmodules`; in workspace mode the one primary parent session directly dispatches the leaves, each active repository owns one run-owned worktree at `<source-root>/.worktrees/<planId>` on branch `ai-workflow/<planId>`, and Git Operator is the only role allowed to run Git. Automatic resume is limited to a clean, fully checkpointed phase boundary or a verified repository delivery boundary, and a dirty partial phase, a commit-without-checkpoint gap, unknown future-phase progress, an uncertain review result, a contradictory record or unrelated target drift stops with a bounded support or recovery request. Apply the full workspace procedure, including the checkpoint-only write protocol and active context rebuild, from the shipped `coding` skill's `references/workspace.md`.
- The primary delegates the existing shell-based generation, pairing and validation commands to an existing shell-capable role with exact generated-artifact write authority, without expanding any role tool set; Documentation Maintainer prepares semantic navigation candidates and bilingual prose, and no additional maintenance command is introduced.
- Unreadable or contradictory frozen sources block before any edit, without broader whole-repository discovery and without a frozen-input rewrite. The CLI, real-Git and content tests cover the delivered workspace scope, but the three-host native parent-session acceptance is not fully demonstrated and stays an explicitly reported gap, never converting unavailable authentication or trust into a pass.

## Workflow roles

- Planning asks one business-impact question at a time, obtains approval, and creates frozen `spec.md` and `plan.md` for a planned change only.
- Plan-to-tasks validates the frozen pair, previews the complete graph and its parallel phases with the critical path, obtains approval, and creates immutable `tasks/<taskId>.md` files plus `tasks/execution-order.yaml`, the frozen schedule that matches the approved preview and has no `.zh.md` or `.i18n.yaml` sibling. It never edits frozen plans.
- Coding creates one project-local temporary worktree under `<project>/.worktrees/<name>` before implementation and performs all implementation, validation and per-step commits inside that single worktree, following the execution model above, including the `tasks/execution-order.yaml` split schedule with its no-fallback and no-recomputation rule.
- Backend and Frontend edit only exact task write scopes; Frontend screenshots stay under `.ai-workflow/plans/<planId>/screenshot/`.
- Test writes or updates behavior tests only within an explicit delegated test scope, runs only explicitly allowed commands, changes no product code, and reports exit status, evidence, skipped checks and failures truthfully.
- File Explorer is read-only and may search only authorized roots. It never edits files or guesses paths.
- Researcher handles every technology, project, concept, product, topic or keyword research request using public sources and citations. It never edits files.
- Documentation Maintainer owns explicitly scoped MEMORY, navigation indexes, notes and non-code documentation, returns exact changed paths and validation evidence to the primary orchestrator, and must not invoke Git itself.
- Spec Review checks requirements, acceptance criteria, testability, scope, coverage and actual delivery. Standards Review checks consistency with MEMORY and its referenced notes rules. Both are read-only.
- Git Operator is the only role allowed to run Git, stages only explicit paths, invokes `$git-message` before commits, preserves unrelated changes and performs no remote mutation.

## Host role agents

- Installed role agents are native to each host: Codex uses TOML with `model`/`model_reasoning_effort`, Claude uses Markdown with `allowed-tools`, and OpenCode uses Markdown with `mode: subagent` and ordered `permissions` rules. The role's declared tools remain the single source, and only the primary orchestrator dispatches subagents.

## Orchestration

The primary orchestrator directly dispatches Git Operator and every specialist in dependency order; no coordinator role exists, and for split and unsplit coding it directly dispatches Git Operator, File Explorer, the implementation role, Test, both reviews simultaneously in one parallel batch, an optional repair, and finalization. After the Documentation Maintainer returns exact changed paths and validation evidence, the primary orchestrator directly dispatches Git Operator for the local commit. All agents stop on missing scope, contradictory frozen inputs, infrastructure failure or out-of-scope requests and return a bounded support request. Never weaken tests or silently expand authority.

Once a sub-agent returns `done`, its session ends; later work for the same role needs a new native session, never reused or resumed, granting no new authority and never treating `done` as review PASS. A new session gets project context, `MEMORY.md`, both navigation files, contract, task goal, scopes, permitted commands and relevant accepted results or findings, not the prior conversation; accumulation stays limited, no measured performance claim. Spec Review instead gets none of that context, results or earlier findings, only defined inputs, raw evidence; extra narrative needs fresh bounded dispatch, not a claim loaded context can be deleted.
