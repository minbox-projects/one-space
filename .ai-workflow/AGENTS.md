# ai-workflow project contract

This contract binds the entire project and every agent, including sub-agents. Read it explicitly before repository work; do not rely on a host loading hidden directories or following Markdown links. Installed role files never override it. The primary-only Coding and workspace procedure lives in the shipped `coding` skill (`templates/skills/coding/SKILL.md`) and `references/workspace.md`; this contract keeps every common obligation and points there only for mode-specific detail.

## Shared context and maintenance

Context loading is role-scoped. Every participating role explicitly loads its repository's full applicable project contract; every non-Spec role also loads `MEMORY.md` for current standards. Read scope is permission, not a mandatory read list or eager-read checklist, and there is no generic requirement to eagerly read both navigation files in a new session. Spec Review alone skips fixed context, notes, accepted results and generic packets: Planning review gets draft spec and plan plus requirement references, no commit range; coding review gets frozen requirements, raw evidence paths and one immutable range, never plans, tasks, summaries, test reports, earlier verdicts or history. It reads this contract as procedural authority, not acceptance evidence.

| Role or activity | Required context |
| --- | --- |
| Primary orchestration | Full applicable contract, `MEMORY.md`, complete frozen spec/plan once and current-phase task bodies; catalog or locator when locating affected features. |
| File Explorer | Contract, `MEMORY.md`, supplied locator or fallback and catalog as needed; only authorized discovery roots. |
| Researcher | Research objective and authorized inputs plus the full applicable contract and `MEMORY.md`; public sources and citations only. |
| Backend, Frontend, Test, Git Operator, Documentation Maintainer | Contract, `MEMORY.md`, current delegated task or step and necessary exact source or evidence. |
| Standards Review | Contract, `MEMORY.md`, authorized note standards and immutable review material; no generic navigation bundle. |
| Spec Review | Procedural contract and only its mode-authorized requirement, draft or raw-evidence inputs; no MEMORY/navigation bundle. |
| Authorized index maintenance or investigation | Relevant index entries or full JSON when necessary for the actual authorized work. |

`navigation.json` is the authoritative machine index and `navigation.md` its generated catalog view. Primary or discovery uses the catalog when locating a feature and verifies a known feature with `ai-workflow context locate --project <absolute-project-root> --feature <id> --verify` before source discovery. Read the JSON only for a needed bounded entry, an authorized index maintenance or investigation, or a locator fallback the matrix allows; notes and governance join explicit scopes, not full history. A known-feature `hit` supplies exact indexed paths without widening a frozen write scope. Missing or empty index permits explicit frozen plan paths; `stale`, `invalid` or `ambiguous` results require bounded resolution or index repair before reliance. Update `MEMORY.md` and `.ai-workflow/index/navigation.json` immediately when architecture, ownership, agent responsibilities, public symbols, paths or workflow rules change, and regenerate and validate `navigation.md` in the same change.

A current verified locator result may be supplied with repository, worktree and version provenance. Reuse is valid only in the same session and repository while that provenance and the relevant anchor, authority, index and task content remain current; a relevant repository, worktree, anchor, authority, index or task change, or uncertainty about currency, invalidates the affected reuse and requires bounded rereading or reverification before reliance. A fresh session never counts a parent's read or another session's read as its own. A demonstrably complete current authorized injection is acceptable; partial or uncertain injection is not. Primary or an authorized shell-capable role runs lookup; a role without shell requests the primary to arrange the lookup and gains no tool. An old task scope that contains navigation JSON remains valid reading authorization, and existing task formats and scope authorization remain compatible.
- `MEMORY.md` records only the project's current standards and behavior: the change that supersedes a statement rewrites it to the current state or removes it in the same change, so the recorded standards stay current as changes land; superseded history belongs to Git and Agent Notes, never to `MEMORY.md`.
- Agent results are Markdown under `## Output checklist` with `### Status`, `### Summary`, `### Evidence` and `### Support Requests`; File Explorer uses `### Found Paths`. JSON envelopes are prohibited and v2 manifest JSON is unchanged. Each `### Evidence` entry carries the artifact's absolute path or an explicit report reference plus at most one sentence of conclusion, and no embedded diffs, logs, JSON bodies or code blocks.
- Report-body targets are distinct from contract-document length and are not a contract quota: an ordinary successful body must stay at or below 1,200 Unicode code points and a review, failure or blocked body at or below 3,000, counted over the whole report body including `### Summary` and `### Evidence`; examples include one code point above each limit, and a non-BMP character counts as one code point. Authors must self-check the whole body before returning. These are portable prompt instructions, not a programmatic runtime cap or host guarantee. Complete findings take precedence over length: when no complete recoverable reference exists, expose the exception visibly, retain every known SHA, exit-code, verdict and blocker fact, and leave acceptance unresolved rather than dropping facts. After receipt the primary may request a scoped fresh read-only digest; it is read-only, grants no file-write permission, never automatically reruns a completed operation whose side effect may already have happened, and never claims to remove content already received.
- Durable artifacts stay self-contained after their plan is gone: note bodies, commit messages and code comments, including class- and type-level documentation comments, describe the delivered result, decision or behavior in durable terms and never carry transient plan-internal identifiers such as task IDs, step numbers, phase numbers, `REQ`/`AC` IDs or plan directory names. One bounded exemption covers test names, assertion labels, test-local constants and traceability comments linking a test to what it verifies, while note bodies, commit messages, product code comments and shipped documentation keep the full prohibition. Notes still carrying such identifiers are cleaned under `.ai-workflow/notes/README.md` maintenance; the workspace plain plan-ID note reference is the only sanctioned exception.

## Agent Notes

Read `.ai-workflow/notes/AGENTS.md` and `.ai-workflow/notes/README.md` before maintaining notes; the README is the single source for note format, lifecycle, supersession and archive governance. Planning schedules relevant note work, the change that lands the decision owns its record and lifecycle transition, and MEMORY records current standards while notes record why; keep them consistent in the same change.

## Workspaces

A workspace is a root repository composing child repositories as local git submodules; `.gitmodules` defines the submodule boundary, so child work never leaks into the root or a sibling. Each participant works at its workspace-root-relative path, and only its slice and plan artifacts live under `<root>/.ai-workflow/plans/<planId>`. Cross-repository references stay plain plan-ID text: the root owns the decision note and each repository its delivered facts, updating only its notes and `MEMORY.md`. A plan declaring a non-root participating repository must be split by plan-to-tasks before implementation, with the task set frozen only after `ai-workflow workspace distribute --plan <directory>` succeeds for every participant with `ai-workflow workspace status --plan <directory>` valid and every slice present, while a plan whose `workspace_repos` declares only the reserved `workspace` root entry may be implemented unsplit; only a frozen plan with a non-root participant matched to the current root's `.gitmodules` activates the parent workspace boundary, and each active repository owns one run-owned worktree at `<source-root>/.worktrees/<planId>` on branch `ai-workflow/<planId>`. Git Operator is the only role allowed to run Git; each repository's single `implementation.yaml` is updated only by the filesystem-only `ai-workflow workspace checkpoint --plan <directory> --repo <name>` command after Git evidence, and each verified delivery commit is an authorized pointer. Apply the full procedure from the `coding` skill's `references/workspace.md`.

## Change routing

Classify every request before starting and state the class in one line. A new feature or user-visible capability is always a Planned change, even when its scope looks small or has one observable outcome.

- Direct change — a bounded adjustment to existing behavior or defect fix with clear intent and one observable outcome that adds no new user-visible capability: implement it directly without Planning, `spec.md`, `plan.md` or task files, and without the dual-axis review. Run the relevant checks and add one focused regression test for a defect.
- Planned change — a new feature or user-visible capability, unclear or contested requirements, more than one materially different design, or a change to a public interface, persistent format, cross-module or cross-stack behavior, migration, compatibility or this contract: run Planning first, implement the frozen plan, and keep the dual-axis review gate.
- Mechanical change — a typo, copy, comment, formatting or test-only adjustment with no observable behavior change: implement it directly and run only the narrowest relevant check.

Direct and Mechanical still execute the full coding execution unit: one mandatory project-local temporary worktree at `<project>/.worktrees/<name>`, implement, validate and commit inside it, then merge back into the recorded target branch; only Planning artifacts and the dual-axis review are skipped.

Never run Planning to restate clear, bounded intent or label direct to skip checks or evidence; ask only when rules cannot classify. After checks pass, the primary automatically delegates the scoped commit to Git Operator without separate confirmation, before immutable-range review where one applies; it supplies the range, never a review PASS or integration authorization. Completion needs the commit SHA or verified no-change evidence with current HEAD when no scoped diff exists; a failed or blocked commit reports `blocked` or `failed`, never `done`.

## Review policy

The change class is the only routine review trigger: a Direct or Mechanical change dispatches neither axis, Planning dispatches only the Spec Review, and plan-to-tasks dispatches neither axis, while an ordinary planned implementation runs one simultaneous Spec Review and Standards Review batch after implementation and before integration, a child-participating workspace runs a per-repository delivery review and an independent finalization review, and a zero-task root has no artificial root-delivery review. No per-task, per-phase or per-commit trigger exists.

Both axes share the immutable HEAD with separate payloads; Spec Review alone uses defined inputs. The initial review completes all assigned coverage even after finding a blocker and reports all concrete findings and unreviewed coverage. Test evidence is the primary's runtime gate; static Spec PASS is not runtime success. The primary uses the coding skill's `references/review.md` packets, keeps original findings and labels, and maps closure. A coding recheck receives the original `base_commit`, the immediately preceding reviewed `previous_head`, updated `head_commit`, the complete delivery diff, the separate previous-to-current repair diff and necessary immutable blobs. Spec gets only affected requirements and repair scope with these raw inputs, never earlier findings or "fixed" claims; Standards also receives factual findings, applicable standards and fresh check evidence. Reviewers distinguish gaps present at the previous head, repair-induced gaps and unknown provenance; the primary maps unresolved findings, review omissions, regressions and unsupported or out-of-scope requests without concealing real defects.

Each boundary permits at most two repair/recheck cycles after its single full review. One aggregate repair is automatically delegated for evidenced in-scope blockers per cycle, followed by fresh checks, commits and a fresh targeted recheck batch. Dispatch only affected axes selected by actual repair impact, both simultaneously when both are affected; finding origin alone never selects axes. A second cycle requires a concrete correction and new defect evidence or demonstrable closure progress; no progress and no new evidence stops repetition. Missing raw material at an unchanged head is evidence completion and consumes no repair cycle. If the budget is exhausted with an unresolved blocker, stop as `blocked`/`failed` with the remaining trigger and evidence; a new session never resets the budget. A targeted PASS covers its assigned scope and head only, and carrying forward unaffected coverage requires an explicit repair-impact justification. Checked commits precede review: split task commits supply the range; other checked units, repairs or finalization pointers commit before review without implying PASS or integration; integration follows accepted reviews; no-change units supply verified HEAD evidence, not an empty commit. Before a non-fast-forward merge Git Operator alone compares actual clean source HEAD, repository, worktree, base and target with accepted HEAD, refusing source drift while accepting a target-branch advance; delivery SHA is recorded independently.

An unfulfilled AC, cited required-standard violation or missing required evidence is a blocker; warnings are advisory, needing a reasoned disposition that never masks a blocker; demonstrably unsupported or duplicate findings need reasoned dispositions, not silent drops. A required business/acceptance, scope or REQ/AC change or delivered-child edit needs a bounded decision or support request, not an unauthorized edit; unavailable required evidence or an unavailable recheck stops as `blocked`/`failed`. Never start a second full review or accept an unresolved blocker because the repair budget ran out. `done` means execution completed, not Verdict PASS; freeze or integration needs complete acceptance evidence and no unresolved blocker. Workspace `reviewed_commit` is purpose-scoped, written once after accepted closure, never reused; checkpoint success is no PASS or Git equality.

Standards Review reads only packet-authorized changed paths, the supplied diff, bounded source context at the immutable range, MEMORY and supplied evidence; it never searches, runs Git or tests, edits, invents requirements or reports uncited style taste. It judges delivered code for logic and boundary gaps, security risk needing a written explanation, and removable redundancy plus missing comments on non-obvious key logic. A logic or boundary finding names an exact path or symbol, a concrete triggering input, state or sequence, observed and expected behavior, a cited public-contract, invariant or required-standard basis, supported-use reachability and a correction. Reachable incorrect behavior, an unhandled boundary, state corruption or a resource leak is an error even when rare; non-defect improvements stay advisory. Security findings require a plausible threat under the actual trust boundary; speculative or unreachable concerns are not actionable findings, and missing necessary context requires bounded support rather than an invented requirement.

## State domains and progression

Status values are explanatory records, not permissions: a successful-looking value in one domain never authorizes a later gate, and missing proof never advances one. These domains are distinct: a gate `decision` is not a `SyncReport` status, a `SyncReport` status is not a locator result, and a locator result never expands an authorized write scope.

| Domain | Existing values | Owner | Required evidence | Permitted next action |
| --- | --- | --- | --- | --- |
| Delegated execution | `done`, `blocked`, `failed` | The delegated leaf | Exact changed paths, attempted checks and reported failures | `done` completes that delegation only; a completed review may report execution `done` with a non-PASS conclusion, missing required inputs are `blocked` and an execution failure is `failed`. |
| Review judgment | `PASS` or a non-PASS verdict | The independent reviewer | Assigned requirements at the immutable head plus a reasoned disposition for every retained advisory | `PASS` with advisories visible is allowed when no unresolved blocker remains and every retained advisory has a reasoned disposition; an unresolved blocker, unavailable required evidence or unresolved advisory disposition stops acceptance and integration. |
| Test observation | expected RED, required GREEN, execution failure or infrastructure failure | Test | The named intended observable failure with its actual nonzero exit, or the required passing result | An expected RED delegation completes with its nonzero exit and leaves the GREEN obligation open; a required GREEN failure blocks delivery even after a static Spec PASS, infrastructure inability is `blocked` and an unexpected execution failure or unexpected test failure is `failed`. |
| Implementation record | `in-progress`, `completed` | The primary through the existing record | `started_at` before the first step, then `completed_at` and the final commit after merge and owned cleanup | Start precedes implementation; completion follows the final merge and owned cleanup; no failure status exists. |
| Checkpoint and workspace readiness | Checkpoint event types `start`, `task`, `reviewed`, `delivered` and `finalized` are actions, not readiness values; the read-only status report supplies `valid`, slice `missing`/`divergent`/`present`, record `missing`/`in-progress`/`completed`, `tasks_delivered`, `ready_for_finalization`, `next_repository` and the `execution` projection with `phase`, `pending_tasks`, `awaiting_delivery`, `blockers` and `completed` | The primary applies each checkpoint event through the filesystem-only checkpoint command; `ai-workflow workspace status` owns the readiness report | Git evidence for the recorded SHA, or exact verified HEAD for a no-change task, plus the complete status report for readiness | Checkpoint success or workspace readiness alone proves neither acceptance, review nor runtime-test success; a reported status success is not acceptance and never replaces a review verdict. |
| Gate decision | `allow`, `deny`, `skip` | The synchronization gate | The stored `SyncReport` and its `verified` and `proceed` fields | A `decision` of `deny`, or a nested `report.status` of `conflict` or `failed`, blocks the phase; a warning `report.status` proceeds with visible context and no freshness claim; `skip` means no adoption. |
| Synchronization report | `synchronized`, `unverified`, `needs_attention`, `pending`, `conflict`, `failed` with `verified`, `proceed` and `check` | The manual synchronization command | The complete report and its warnings and conflicts | Only `synchronized` with `verified: true` claims current artifacts; a manual synchronization warning reports exit 2 and still proceeds with visible context, while `pending`, `conflict` and `failed` stop. |
| Locator result | `hit`, `miss`, `missing_index`, `stale`, `invalid`, `ambiguous`, `blocked` | The context locator | The resolved feature, entries and read order, or the fallback packet and its authorized roots | A `hit` supplies exact indexed paths without widening a write scope; a miss or missing index permits only the frozen boundary or authorized bounded discovery, and stale, invalid or ambiguous results need bounded resolution. |

Review acceptance (`PASS` or non-PASS) and test observations are explanatory categories, not new serialized values; no schema, command output or persistent field gains a value from this section. `reviewed_commit` is purpose-scoped and written once after accepted closure for that purpose, never reused for another purpose or a changed head. The reviewed source SHA and the non-fast-forward delivery merge SHA remain separate. The existing record lifecycle stays unchanged: start precedes the first implementation step, a task checkpoint follows scoped Git verification, delivery follows accepted integration and owned cleanup, finalization requires child and root delivery evidence, completed reentry verifies read-only without replay, a root task delivery stays `in-progress` with `root_tasks_commit`, and a zero-task root has no artificial delivery.

Published counterexamples:
- A completed review may report execution `done` with a non-PASS conclusion, and a `PASS` with a failed required test never advances delivery.
- An expected RED with a nonzero exit is a valid reproduction, not a delivery success.
- `valid: true` with a missing slice is not workspace readiness.
- A handled `sync-hook` exit 0 with `deny` is still a denial.

## Work-boundary synchronization

Adopted projects synchronize their managed workflow instructions once at each planning, coding or plan-to-tasks skill start, keyed by the actual root. That start runs `ai-workflow sync-hook --host <current-host> --phase --project <actual-root>`, the only automatic trigger, and stores its complete result for the actual root outside the project; every later native `SessionStart`, `UserPromptSubmit` and `PreToolUse` event is served from that stored result, while a missing, corrupt or unreadable stored check allows with visible no-check context and no freshness claim. The `--phase` form and the OpenCode stdin gate print raw gate JSON with a top-level `decision` of `allow`, `deny` or `skip`; Claude Code and Codex stdin gates emit host-native output that never exposes the raw decision, and every handled form exits 0 even on a deny. A `deny`, or a `conflict` or `failed` `report.status`, blocks the phase; a warning `report.status` proceeds with visible context and no freshness claim; `skip` means no adoption was found. The installed host entry invokes `ai-workflow sync-hook --host <current-host>` with the native JSON payload on stdin, not by hand. The manual `ai-workflow sync [project]` command prints a `SyncReport` with `status`, `verified`, `proceed` and `check`, no `decision`; a manual warning report exits 2 and still proceeds with visible context.

This preflight is a narrow instruction-maintenance exception to coding-worktree confinement: it writes only the managed workflow instruction files of the actual current project root or the active coding worktree, with no Git, staging or product edit, and turns a clean-baseline or task-scope collision into a bounded support request. After a safe patch changes the contract or owned workflow rules, re-read the updated `.ai-workflow/AGENTS.md` before ordinary work continues; frozen `spec.md`, `plan.md`, task files and their declared repository/write scopes are never synchronized, and a contradiction between new authority and a frozen scope stops that phase with an explanation.

## Setup recovery

Setup and upgrade require explicit user authorization. Setup is never authorized by the preflight or by the presence of `.ai-workflow/`. A project with no existing adoption uses ordinary `ai-workflow init <project-root>` after that authorization; ordinary init creates the contract, `MEMORY.md` and navigation, so it never requires nonexistent workflow files first. An existing adoption with those upgrade prerequisites present uses `ai-workflow init <project-root> --upgrade`; it requires the `.ai-workflow/` directory, `MEMORY.md`, `.ai-workflow/index/navigation.json` and `.ai-workflow/index/navigation.md`. Missing prerequisites return an exact-path support request without overwriting local data. An upgrade `SyncReport` of `needs_attention` with `proceed: true` is a warning outcome with no upstream-freshness claim; a manual warning report exits 2, and exit 2 alone is not an execution failure.

## Coding execution model

Planning produces frozen `spec.md` and `plan.md`; plan-to-tasks produces immutable task documents. Coding implements direct changes without planning artifacts and planned work as split tasks or an approved unsplit frozen plan, with TDD, and creates no workflow runtime artifact other than the single implementation record at `<project>/.ai-workflow/plans/<planId>/implementation.yaml`: `plan_id`, `status: in-progress` and an ISO 8601 `started_at` in UTC+08:00 before the first implementation step, then after the final merge and owned cleanup `status: completed` with an ISO 8601 `completed_at` in UTC+08:00 and the final commit SHA. It is the only permitted run record.

- A planned change without a frozen plan is planned first and handed off: the planning session never starts implementation, runs the plan-to-tasks preparation and distribution for a workspace plan, and routes to a new session at the workspace root, while an ordinary or root-only plan tells the user to start one. A direct or mechanical unit without a frozen plan carries its complete explicit scope, with no missing-plan demand and no requirement for `spec.md`, `plan.md` or task files.
- Coding creates one mandatory project-local temporary worktree under `<project>/.worktrees/<name>` before implementation, and all implementation and validation happen inside that single worktree. At worktree creation Git Operator records the branch checked out at that moment and its starting commit as the integration target; after checks pass it merges the worktree branch into that recorded target branch with a non-fast-forward merge and records the delivery merge SHA separately. A target-branch advance is not source drift; the source HEAD, repository and worktree identity must still match accepted evidence. A detached starting checkout has no target branch and stops before implementation with a bounded support request. Git Operator materializes the gitignored state into it, excluding the `.worktrees/` container, so `.ai-workflow/plans/` stays visible and single-source at the project root while the contract, MEMORY, navigation and notes arrive with the worktree through Git.
- On a merge conflict Git Operator reconciles every conflicted hunk by preserving both sides' changes and never chooses ours or theirs wholesale; it never rebases, forces, resets or amends, and the affected checks rerun after resolution. If both sides cannot be preserved or any post-resolution check fails, it aborts only the in-progress merge, retains the owned worktree and branch, and reports blocked with the conflicted paths, resolution evidence and the failing check. The delivery merge SHA is recorded separately and need not equal the accepted source HEAD.
- A split plan's execution order is frozen at split time as `tasks/execution-order.yaml`: the ordered list of non-empty parallel phases covering every task exactly once, with every dependency in a strictly earlier phase and no overlapping normalized write-scope paths inside one phase. It is the only schedule: phases run in file order, every task of a phase is dispatched concurrently inside the single worktree with test work before implementation, and each task's write scope is committed serially through Git Operator one commit at a time before advancing; a missing or invalid order stops the run before execution, with no serial fallback and no recomputation from `depends_on`.
- Within one accepted task, the primary may repeat fresh scoped Test, implementation and verification delegations for each vertical behavior boundary rather than batching each role's work once for the entire task, proceeding RED1, implementation1, GREEN1, RED2, implementation2 and GREEN2 as needed. Frozen phase order and serial scoped task commits stay unchanged. An expected RED delegation can complete while recording the intended observable failure, the actual nonzero exit and the remaining GREEN obligation; an unrelated failure does not qualify, and an initially passing reproduction is investigated before implementation. Routine slices and verification do not consume or expand the bounded aggregate repair and targeted recheck budget reserved for post-review defects.
- A git-submodule workspace root delivers one cross-repository plan whose `workspace_repos` declaration and `workspace.yaml` manifest assign every task to exactly one repository in a repository-level delivery order; a non-root-participating plan is split and frozen as described under Workspaces, while a plan whose `workspace_repos` declares only the reserved `workspace` root entry may be implemented unsplit. In workspace mode the one primary parent session dispatches the leaves under the Workspaces boundary. Automatic resume is limited to a clean, fully checkpointed phase boundary or a verified repository delivery boundary; any dirty partial phase, commit-without-checkpoint gap, unknown future-phase progress, uncertain review result, contradictory record or target drift stops with a bounded support or recovery request. Apply the full workspace procedure, including the checkpoint-only write protocol and active context rebuild, from the `coding` skill's `references/workspace.md`.
- The primary delegates the existing shell-based generation, pairing and validation commands to an existing shell-capable role with exact generated-artifact write authority, without expanding any role tool set; Documentation Maintainer prepares semantic navigation candidates and bilingual prose, and no additional maintenance command is introduced.
- Unreadable or contradictory frozen sources block before any edit, without broader whole-repository discovery or a frozen-input rewrite. CLI, real-Git and content tests cover the delivered workspace scope, but three-host native parent-session acceptance is not fully demonstrated and stays an explicitly reported gap, never converting unavailable authentication or trust into a pass.

## Workflow roles

- Planning asks one business-impact question at a time, obtains approval, and creates frozen `spec.md` and `plan.md` for a planned change only.
- Plan-to-tasks validates the frozen pair, previews the complete graph and parallel phases with the critical path, obtains approval, and creates immutable `tasks/<taskId>.md` files plus `tasks/execution-order.yaml`, the frozen schedule matching the approved preview with no `.zh.md` or `.i18n.yaml` sibling. It never edits frozen plans.
- Coding creates one project-local temporary worktree under `<project>/.worktrees/<name>` before implementation and performs all implementation, validation and per-step commits inside that single worktree, following the execution model above, including the `tasks/execution-order.yaml` split schedule with no fallback or recomputation.
- Backend and Frontend edit only exact task write scopes; Frontend screenshots stay under `.ai-workflow/plans/<planId>/screenshot/`.
- Test writes or updates behavior tests only within an explicit delegated scope, runs only explicitly allowed commands, changes no product code, and reports exit status, evidence, skipped checks and failures truthfully.
- File Explorer is read-only and may search only authorized roots. It never edits files or guesses paths.
- Researcher handles technology, project, concept, product, topic or keyword research using public sources and citations, and never edits files.
- Documentation Maintainer owns explicitly scoped MEMORY, navigation indexes, notes and non-code documentation, returns exact changed paths and validation evidence to the primary orchestrator, and must not invoke Git itself.
- Spec Review checks requirements, acceptance criteria, testability, scope, coverage and actual delivery. Standards Review checks consistency with MEMORY and its referenced notes rules, and reviews delivered code in the immutable range for logic and boundary correctness, security risk with a written explanation, redundancy and key-comment quality; a defect-capable finding is an error, otherwise an advisory warning. Both are read-only.
- Git Operator is the only role allowed to run Git, stages only explicit paths, invokes `$git-message` before commits, preserves unrelated changes and performs no remote mutation.

## Host role agents

- Installed role agents are native per host: Codex uses TOML with `model`/`model_reasoning_effort`, Claude uses Markdown with `allowed-tools`, and OpenCode uses Markdown with `mode: subagent` and ordered `permissions` rules. The role's declared tools are the single source, and only the primary orchestrator dispatches subagents.

## Orchestration

The primary orchestrator directly dispatches Git Operator and every specialist in dependency order; no coordinator role exists, and for split and unsplit coding it directly dispatches Git Operator, File Explorer, the implementation role, Test, both reviews simultaneously in one parallel batch, an optional repair, and finalization. After Documentation Maintainer returns exact changed paths and validation evidence, it directly dispatches Git Operator for the local commit. All agents stop on missing scope, contradictory frozen inputs, infrastructure failure or out-of-scope requests and return a bounded support request. Never weaken tests or silently expand authority.

Once a sub-agent returns `done`, its session ends; later work for the same role needs a new native session, never reused or resumed, granting no new authority and never treating `done` as review PASS. A new session gets the context its role row requires, including the current project contract and, for every non-Spec role, `MEMORY.md`, plus the task goal, scopes, permitted commands and relevant accepted results or findings, not the prior conversation; it does not inherit the parent's reads, and navigation is loaded only for an authorized lookup or a needed bounded entry, from `.ai-workflow/index/navigation.json` or its `.ai-workflow/index/navigation.md` catalog. Accumulation stays limited, with no measured performance claim. Spec Review instead gets none of that context, results or earlier findings, only defined inputs and raw evidence; extra narrative needs fresh bounded dispatch, not a claim that loaded context can be deleted.
