# 采用 Refinery 管理 SQLite 迁移

## 规格元数据

- plan-id: `adopt-refinery-sqlite-migrations`
- status: `approved`

## 问题陈述

当前源码已有自定义迁移器，并通过 `MIGRATIONS` 注册和执行 v1 至 v4。该现状需要演进为由 Refinery 接管同一组 v1 至 v4 迁移的目标状态，以统一、可信且全局单调递增地管理共享 SQLite 数据库的版本，并可靠处理新数据库和已有数据库的结构演进。

## 目标与成功标准

- 引入 Refinery 统一管理共享 SQLite 数据库的全局、单调递增迁移版本。
- 升级 rusqlite 至与 Refinery 兼容的版本，继续使用 bundled SQLite。
- 新数据库与可验证的旧数据库均能升级到最新结构，且所有消费者只会在迁移完成后访问数据库。
- 以严格校验和启动失败机制保障迁移历史可信度。

## 用户与用户故事

- 作为应用使用者，我希望空数据库首次启动即可建立完整结构和基础种子数据。
- 作为已有数据库的使用者，我希望旧版有效数据库能够无损接管并升级到最新版本。
- 作为运维人员，我希望迁移异常、数据库版本不兼容或多实例锁等待超时时，在服务开放前获得明确的阻塞错误和详细日志。

## 功能需求

- 现有 v1 至 v4 的 SQL 内容保持不变，采用 Refinery 规范命名并编译进应用，不增加外置 SQL 资源。
- 新数据库必须由 Refinery 执行 v1 至 v4 迁移，并包含现有基础种子数据。
- 必须兼容旧数据库的 v1 至 v4 任意有效连续前缀：严格校验旧记录及对应 schema 后，登记已执行版本并补齐剩余迁移。
- 必须保留 `app_schema_migrations` 作为只读历史，并新增 Refinery 独立历史表；后续迁移历史仅写入新表。
- 旧迁移记录缺号、包含未知版本、存在未知子系统或 schema 不符时，必须拒绝接管。
- 必须启用 checksum 分歧和历史迁移缺失检查；已发布 SQL 不可修改，修复只能新增迁移。
- Refinery 仅可在应用启动时运行；迁移成功前不得开放 IPC、HTTP runtime 或后台任务。
- 多实例迁移必须依赖 SQLite 写锁串行化，最长等待 5 秒。
- 迁移失败、数据库版本高于应用支持版本或锁等待超时时，必须显示原生阻塞错误对话框、记录详细日志并退出。

## 非功能需求

- 每个迁移版本必须在独立事务中执行，单个版本失败时完整回滚。
- 不提供逆迁移或自动备份。
- 迁移判断必须可重复执行，已接管数据库后续启动不得重复执行已完成迁移。
- 启动门禁必须确保数据库消费者仅看到迁移完成的 schema。

## 范围

- 共享 SQLite 数据库的 Refinery 迁移接入。
- v1 至 v4 既有迁移与基础种子数据的编译内置和升级接管。
- 旧迁移历史及 schema 的有效性校验、Refinery 历史登记和后续迁移执行。
- 启动阶段的迁移门禁、并发锁等待和阻塞错误处理。

## 接口与数据

- `app_schema_migrations` 保留为只读历史数据，不再接受后续迁移写入。
- Refinery 使用独立历史表记录已执行的迁移版本及其校验信息。
- 迁移版本在全局范围内单调递增；v1 至 v4 的既有 SQL 语义与基础种子数据保持不变。
- 应用启动流程以迁移成功为 IPC、HTTP runtime 和后台任务的开放前置条件。

## 失败模式

- 旧历史缺失连续版本、出现未知版本或未知子系统、或数据库 schema 与历史不符时，拒绝接管并退出。
- 已执行迁移发生 checksum 分歧或历史迁移资源缺失时，拒绝启动并退出。
- 数据库版本高于应用支持版本时，拒绝启动并退出。
- 任一迁移版本失败时，回滚该版本事务，不开放服务并退出。
- 多实例场景下，SQLite 写锁等待超过 5 秒时，不开放服务并退出。
- 所有上述阻塞失败均显示原生错误对话框并记录详细日志。

## 验收标准

- 空库启动后形成完整 v1 至 v4 schema、基础种子数据及 Refinery 历史。
- 旧 v1、v2、v3、v4 数据库均可无损接管，保留业务数据并升级至最新版本。
- 已接管数据库重复启动时不重复执行迁移。
- 非法旧历史、结构漂移、checksum 分歧、缺失迁移和未来版本均在服务开放前失败。
- 单版本迁移失败时完整回滚；多实例迁移不会并发执行。
- Rust 迁移专项测试、完整 Rust 测试、格式检查和编译检查均通过。

## 兼容性与迁移

- 支持旧 v1 至 v4 的任意有效连续迁移前缀。
- 接管前必须验证旧记录与 schema；仅验证通过的数据库可登记既有版本并继续升级。
- 已发布迁移 SQL 不得修改；后续修复仅通过新增迁移版本交付。
- 不支持从高于应用已知版本的数据库降级或继续启动。

## 范围外事项

- 不新增迁移 CLI。
- 不拆分种子系统。
- 不处理未知私有 schema。
- 不修改前端业务功能。

## 假设

- 现有 v1 至 v4 的 SQL 及基础种子数据已被视为已发布内容，其语义无需变更。
- SQLite 写锁可用于同一共享数据库的多实例迁移串行化。
- 以更严格的启动失败换取迁移历史可信度是可接受的取舍。
- 仅在启动时执行迁移检查，并以启动门禁保证所有消费者看到已完成的 schema，是可接受的运行方式。
